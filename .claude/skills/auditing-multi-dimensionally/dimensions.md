# 차원별 점검 항목 · 자동 스크린 · 제외 목록

관점(perspective) 1개 = 에이전트 1기. 아래 차원 태그는 과거 감사 산출물과 대조 가능해야 하므로 **바꾸지 않는다**: `security` `concurrency` `data` `correctness` `perf` `a11y` `design` `consistency`

기준선: OWASP Top 10:2025 · 2025 CWE Top 25 · WCAG 2.2 AA · Core Web Vitals(INP 200ms). **WCAG 3.0은 Working Draft라 미채택.**

---

## D1 · security — 인가·비밀·주입

이 스택의 구조적 급소: **`executeAs: 배포자`라서 시트 ACL이 앱 사용자를 막지 못한다.** 인가는 전적으로 서버측 게이트가 담당한다. OWASP A01(1위, SSRF 흡수) + CWE-862 Missing Authorization(4위)이 정확히 여기.

- **전역 함수 × 게이트 매트릭스**: 각 앱의 `.gs` 전역 함수(밑줄 없는 것 = `google.script.run`으로 호출 가능) 전수 → `assertAdmin_`/`getAdminContext` 유무. **UI 숨김은 인가가 아니다** — 판정 규칙으로 고정.
  - ⚠ `_` 접미사는 RPC를 막지만 **GAS 에디터 실행 드롭다운에서도 사라진다**. 관리자가 수동 실행하는 함수에는 쓰면 안 되고, 서버 게이트를 써야 한다.
- **CWE-639 (User-Controlled Key)**: 클라가 보낸 키(행번호·id·draftId)로 서버가 대상을 고를 때 **소유·권한 재검증**을 하는가.
- **비밀**: service 키·API 키가 Script Property에만 있는가(코드·git 금지). `ScriptApp.getOAuthToken()` 결과를 클라로 보내는 코드가 있는가(1줄 grep).
- **A02 Misconfiguration(5→2위 급등)**: `appsscript.json`의 `access`/`executeAs`/`oauthScopes` 최소성, `.claspignore` 화이트리스트 누락으로 미배포되는 신규 파일.
- **A03 Supply Chain(신설)**: CDN 의존의 SRI + 버전 고정 유지 여부.
- **A09 "Logging and *Alerting*"(개명)**: 로그만 있고 알림이 없으면 가치가 없다. **파괴적 작업(전삭제·트리거 삭제·재시드·마이그레이션)에 통지가 붙는가.**
- **주입**: WYSIWYG 산이타이저 우회 경로, `innerHTML=` 사용처, **CSV/수식 인젝션**(선두 문자 필터만으로는 불충분 — 구분자·따옴표로 새 셀을 열 수 있고, 일본어 환경에서는 전각 `＝＋－＠`도 검토 대상).
- **Supabase**: SQL/마이그레이션으로 만든 테이블은 **RLS가 자동으로 켜지지 않는다**(에디터로 만들 때만). 테이블 전수 RLS 상태 + policy가 사실상 무제한인지. anon 키로 REST를 실제로 찔러 노출을 판정(1회 curl).
- **익명 노출 엔드포인트**(있다면): 서명 검증·타임스탬프 창·**리플레이 중복제거**.

## D2 · concurrency — 동시성·멱등성

과거 확정 결함이 가장 많이 나온 차원. **서버-클라를 함께 보지 않으면 원리적으로 안 보인다.**

- **Lost update 패턴 전수**: "스냅샷을 읽고 → 자기 몫만 병합 → **맵 전체를 덮어쓴다**". 무잠금 read-modify-write.
- **낙관락 계약**: rev 비교 + base 셀 비교가 **모든 쓰기 경로**에 있는가. **읽기 응답의 rev를 클라가 채택하면 stale을 "최신"으로 위장**시킨다 → "rev 전진 시 boot 재취득"을 불변식으로.
- **TOCTOU**: 체크와 사용 사이에 다른 실행이 끼어들 수 있는가. 스캔+추기가 같은 락 안인가.
- **멱등성**: 재시도·재전송이 중복 생성/중복 발송을 만드는가. 안정 키가 있는가. **처리 전에 마킹하면 실패 시 정당한 재시도가 영구 유실**된다(실패 시 마킹 해제 필요).
- **락 운용**: `LockService` 재진입 금지(비재진입), `waitLock` 타임아웃, 락 안에서 flush 후 release. 클라측 busy 플래그는 **동일 사용자 연타만** 막고 異유저 경합은 못 막는다.
- **부분 실패 원자성**: 다중 저장 중 하나가 실패하면 pending·rev·캐시가 어떤 상태로 남는가. 롤백이 있는가.
- **게이트/워터마크 전진**: 쓰기가 실패했는데 "처리 완료" 표식이 전진하면 그 구간은 **영구 결락**된다(재시도 경로가 없어짐).
- **캐시 세대**: 상대 시각·사용자 상태에 의존하는 캐시 키를 영속화하지 않았는가.

### D2-c · 클라이언트측 레이스·멱등성 (서버측과 **별도로** 본다)

⚠D2 상단은 전부 서버측이다. **클라 쪽은 원리가 달라서 같은 눈으로 보면 안 보인다** —
락이 없고, 사용자가 언제든 다시 누르고, 응답이 순서대로 오지 않는다.
아래는 전부 이 리포에서 **실제로 발생한** 형태다(2026-07-30 라운드).

- **재진입**: 비동기 조작(저장·삭제·생성)이 끝나기 전에 다시 눌리는가.
  in-flight 가드가 있는가. ⚠**가드가 모든 분기에서 풀리는가**(에러 경로 포함) —
  안 풀리면 그 뒤로 영구히 안 눌린다. ⚠미해결 Promise 를 남기지 않는가.
  (전례: `position flushSave` 재진입 → 이중 확인 다이얼로그 + 미해결 Promise)
- **⚠out-of-order 응답**: 늦게 도착한 **옛 요청의 응답이 새 결과를 덮어쓰는가.**
  요청 시점의 키(날짜·필터·검색어)를 응답 처리 시 **다시 대조해 폐기**하는가.
  이건 「가끔 옛 데이터가 뜬다」로만 나타나서 재현이 어렵고, 코드를 봐야만 보인다.
- **낙관적 UI 의 롤백**: 서버 실패 시 로컬 상태를 되돌리는가.
  되돌리지 않으면 **화면과 서버가 조용히 어긋난 채** 사용자는 성공했다고 믿는다.
- **재렌더가 사용자 상태를 지우는가**: 필터·정렬·갱신으로 목록을 다시 그릴 때
  선택·체크·스크롤 위치·포커스가 사라지는가. 특히 **선택 후 필터 변경 → 삭제** 흐름.
  ⚠반대로 유지한다면 **「고른 것 중 지금 안 보이는 건수」를 반드시 말할 것** —
  보이지 않는 대상을 지우는 것이 가장 위험하다.
- **인덱스로 조작하는가**: 목록을 띄운 시점의 **행 번호/배열 인덱스**로 서버 조작을 지시하면,
  그 사이에 데이터가 늘거나 줄었을 때 **엉뚱한 대상**을 건드린다.
  → **안정 키**(id)로 대조할 것. 서버 삭제는 **인덱스 내림차순**으로(오름차순은 뒤 항목이 밀린다).
- **중복 생성·중복 삭제**: 같은 조작을 두 번 하면 두 번 일어나는가.
  네트워크 재시도가 중복을 만드는가. 클라가 만든 안정 키를 서버가 대조하는가.
- **파괴적 조작의 계약**: 프리뷰 건수와 실제 실행이 **같은 판정 함수**를 쓰는가
  (따로 쓰면 「N건 지웁니다」라 말하고 다른 수를 지운다). 실행 결과 **건수를 반환**하는가
  (0건을 묵묵히 돌려주면 「지워졌다」와 구별 불가). 찾지 못한 대상을 보고하는가.

**검증법**: 코드 읽기로만 판정하지 말 것. 실브라우저에서
①연타 ②느린 응답 중 조건 변경 ③서버 실패 주입 ④필터 변경 후 조작 — 4가지를 실제로 해 본다.

## D3 · correctness — 예외·경계·계약

OWASP **A10 Mishandling of Exceptional Conditions(신설)** 가 이 차원의 표준 근거. 이 코드베이스에서 적중률이 높다.

- **`catch {}` 무음 삼킴** — 실패가 성공처럼 보이는 경로.
- **fail-open**: 레이트리밋·권한·검증이 예외 시 통과되는가(fail-closed여야 하는 곳).
- **오류 메시지 정보 노출**(CWE-209), 내부 사유 문자열이 사용자 문서에 실리는 경로.
- **경계조건**: 빈 셀·월 전환·롤링 윈도 경계·지평 밖 날짜·부분 데이터(당일 도중).
- **서버↔클라 해석 규칙 동기**: 같은 셀을 서버와 클라가 다르게 파싱하면 조용히 어긋난다.
- **데이터 정직성(도메인 특유)**: 예측을 실적처럼 보이게 쓰지 않는가. 결측을 0으로 만들지 않는가. 데이터가 없을 때 **수치를 지어내지 않는가**.

## D4 · perf — 성능·렌더링

- **왕복이 지배적이다.** GAS RPC 왕복 수·직렬 호출·부트 시 필요 이상 페치. 캐시 TTL과 SWR 경로.
- **INP 200ms 기준**, 진단은 **3분해로 어디인지 먼저 특정**: input delay / processing / **presentation delay**. 클릭·탭·키만 해당(스크롤·호버 제외).
  - ⚠ **페인트 비용이 GPU 래스터에 있으면 devtools timeline·headless로 안 잡힌다.** headful + 실 GPU 트레이스가 필요하다(전례 있음: dashed border × border-radius, `background-attachment:fixed`).
- **long task 50ms** 기준, 양보점 부재.
- 대량 DOM·표 전체 repaint를 유발하는 셀 단위 transition, `will-change`에 레이아웃 속성(`left/top`) 지정.
- **CrUX 필드 데이터는 적용 불가**(로그인 뒤라 존재하지 않음). 임계치만 랩 측정 기준으로 차용.

## D5 · a11y — 접근성 (WCAG 2.2 AA)

**비용 대비 최적 순서**: WebAIM Million 기준 오류의 96%가 6유형 — **저대비**(홈페이지의 83.9%)·alt 누락·라벨 없는 폼·빈 링크·문서 언어·빈 버튼. 여기서 시작한다.

- **대비**: 본문 4.5:1 / 대형·UI 3:1. **라이트·다크를 각각 독립 판정**(토글 존재는 충족이 아니다). 실제 배경 토큰으로 계산할 것.
  - ✅**대비는 이 도구로 재라**: `tools/contrast_sweep.py`(실 DOM 픽셀 샘플링). 정적 CSS 스크린은 별칭 토큰·부모/자식 분리·런타임 주입색(`--rc`)을 구조적으로 놓친다(실측: 같은 라운드에서 정적 스크린 통과 후에도 27건이 남았다). 도구 상단에 **네 번의 오측정 이력**(조상 합성/full_page/요소 박스/가려짐)이 적혀 있으니 새 측정기를 만들 땐 반드시 먼저 읽을 것.
  - ⚠**측정 함정①**: 온보딩 투어·모달의 dim 레이어가 화면 전체를 덮으면 **픽셀 대비가 전부 어둡게 나온다**(실제로 겪음). 스크린샷 기반 측정 전에 투어 완료 플래그를 주입해 dim을 제거하고, 가능하면 **계산값(토큰)과 픽셀 실측을 함께** 제시할 것.
  - ⚠**측정 함정②(transition 미착지)**: 이 리포는 색에 `transition`이 걸린 요소가 많다. **테마 전환 직후나 hover 직후에 computed style을 읽으면 중간값**이 나와 위양성이 뜬다(실측: hover 후 120ms에 4.48 "실패" → 700ms 후 4.53 통과. 다른 감사자도 테마 전환 직후 3.84로 오판했다가 정착 후 5.01로 정정). **상태를 바꾼 뒤 최소 0.5초는 기다리고**, 경계값(4.4~4.6)이 나오면 반드시 재측정할 것.
  - ⚠**측정 함정③(캐스케이드 무시)**: 규칙의 선언만 뽑아 프로브 요소에 먹이면 **다른 규칙의 상쇄가 반영되지 않아** 이미 고쳐진 곳까지 실패로 센다(실측: 44건 중 6건이 별도 다크 오버라이드로 이미 해결돼 있었다). 반대로 클래스를 임의로 붙여 만든 요소는 **원래 규칙이 안 걸리는 요소**를 재게 된다(실측: 활성 클래스를 다른 탭에 옮겨 붙였다가 엉뚱한 값으로 "통과" 판정). **DOM의 자연 상태를 우선해 읽고**, 합성이 불가피하면 합성했다는 사실을 결과에 표시할 것.
  - ⚠**정적 치환 스크린은 별칭을 따라가야 한다**: `background: var(--tone)`처럼 **커스텀 프로퍼티가 의미색에 바인딩된 별칭**을 경유하면 직접 참조 검색에 안 걸린다(실측: 라이브 대시보드 4장이 미변환으로 남음). 또 **CSS 파일만 훑으면 JS의 인라인 `style.cssText`를 통째로 놓친다**(실측 1건). 치환 대상은 `Stylesheet` + `JS의 인라인 스타일` + `별칭 1단계 해석`까지 훑을 것.
  - ⚠**계조가 있는 시각화**(농도 램프·히트맵)는 한 점이 아니라 **전 구간을 스캔**한다. "어느 잉크로도 통과 못 하는 농도 구간"이 있으면 잉크 교체가 아니라 **램프 상한 압축**이 답이다 — 잉크만 바꾸면 그 구간은 계속 실패한다.
- **포커스 가시성**: `:focus-visible`에 `outline:none`을 쓰면 **반드시 대비 3:1 이상의 대체 표시**를 제공해야 한다(배경색 미세 변화는 표시가 아니다). 공용 폴백을 `:where()`(명시도 0)로 두면 앱의 `outline:none` 한 줄에 조용히 무력화된다.
- **WCAG 2.2 신규 SC 중 이 스택에 물리는 것**: **2.4.11 Focus Not Obscured(AA)** — sticky 헤더·컴팩트 헤더가 포커스된 셀을 가리는가 / **2.5.8 Target Size(AA)** 24×24 / **2.5.7 Dragging(AA)** — 드래그에 포인터 대안이 있는가(DnD·간트·범위 선택) / **3.2.6 Consistent Help(A)** — 도움말·투어 위치가 앱 간 일관된가. (4.1.1 Parsing은 폐기)
- **키보드 도달**: 클릭 가능한데 Tab이 안 닿는 요소, `role=button`인데 keydown이 없는 "죽은 버튼", dblclick 전용 동작.
- **탭 스톱 폭주**: 그리드에 tabindex를 뿌리면 접근성이 오히려 악화된다(로빙 tabindex로).
- **⚠ 개선안으로 "ARIA 추가"를 남발하지 마라.** ARIA를 쓴 페이지가 안 쓴 페이지보다 오류가 더 많다. 네이티브 요소가 우선.
- 자동 검사는 이슈 볼륨의 약 57%만 잡고, **WCAG 2.2 SC 기준으로는 약 30%만 완전 자동화 가능** — 나머지는 사람이 판정한다.

## D6 · design — UI/UX·디자인 시스템·모션

- **토큰 먼저.** 기반 토큰이 실패하면 그 위 컴포넌트가 전부 상속한다 → 컴포넌트 감사 전에 토큰 감사 1회.

### D6-b · 행동 UX (시각 인코딩과 **별개**로 본다)

- **필터로 0건이 되었을 때** 「데이터가 없다」로 읽히지 않는가(「조건에 맞는 것이 없다」여야 한다).

### D6-c · 애니메이션·모션 (D6 의 「모션」 한 줄을 여기서 전개)

## D7 · consistency — 앱 간 일관성·유지보수성

앱 내부에서는 원리적으로 안 보이는 부류. **별도 슬라이스가 반드시 필요하다.**

- **공용 정본 드리프트**: 정본과 앱 사본의 해시 대조.
- **병렬 진화**: 같은 이름·같은 역할의 파일이 앱마다 독립 구현되어 있으면, **한 앱에서 고친 버그가 나머지에 남아 있다**(전례: 확정 결함 32건 중 6건이 동일 파일명 계열).

- 문서 ↔ 코드 정합: 규약 문서가 두 벌이면 드리프트한다.

## D8 · domain — 전력시장 정합성 (2026-07-30b 신설 · **첫 투입에서 최대 성과**)

이 리포는 전력소매(PPS) 업무 도구다. **다른 어떤 차원으로도 안 잡히는 부류가 여기 있다** —
코드는 정상이고 테스트도 통과하는데 **숫자의 의미가 제도와 다른** 결함이다.
먼저 `Skill(jp-power:core)` 를 부르고 필요하면 `ops`(calc.md)·`markets` 로 **제도 정본을 확인한 뒤 코드와 대조**한다.
⚠**도메인 스킬은 「무엇이 옳은가」를 알려줄 뿐 「이 코드가 그런가」는 아니다** — 코드 대조는 반드시 별도로.

- **コマ(30분) 규약**: 1..48 인가 0..47 인가. コマ N 이 **개시**인가 종료인가.
  ⚠**DB 에 `time` 열이 있으면 「생산(쓰는) 앱의 서식이 정본」**이다. 소비 앱이 자기 식으로 재계산하면 어긋난다.
  실측: `position/Reserve.gs` 만 `slot*30`(종료)이고 energy·chat-notify 는 `(slot-1)*30`(개시) → **30분 어긋남**.
  게다가 같은 함수가 DB값과 자체계산을 **섞고** 있었다.
- **⚠모크가 결함을 숨긴다**: 소비측 해석으로 모크를 만들면 **소비측 버그가 자기일관되게 보여** 프리뷰·E2E 를 통과한다.
  → **모크는 항상 생산측 앱의 서식을 재현할 것.**
- **단위**: kW ↔ kWh(30분 코마의 「量」), 円/kWh ↔ 円/MWh, 万kW/MW/GW.
  ⚠**Σ(합계)는 전력량 단위(kWh/MWh)만 정의된다.** 일합계를 MW 로 표시하면 일평균의 48배가 된다(실측).
- **제도식의 하드코딩**: インバランス 보정식·容量市場 対象年度·비화석 연도가 근사식·리터럴로 굳어 있지 않은가.
  ⚠**「근사」라 주석에 적혀 있어도, 결과를 제도값처럼 화면에 내면 근사는 변명이 안 된다.**
  ⚠**LLM 프롬프트에 제도 설명을 사람이 두 번 쓰지 마라** — 결정론 코드와 AI 가 서로 다른 제도를 말하게 된다(실측).
  제도 정수 **1곳에서 프롬프트를 생성**할 것.
- **에리어 수 9 vs 10**: 오키나와 포함 여부가 화면마다 다른가.
  ⚠**독립계통(오키나와)을 본토 집계의 min/max 에 섞지 마라** — 1에리어의 逼迫이 무관한 에리어 값을 끌어올린다(실측).
- **경계 규칙 ↔ 표시 반올림의 방향**: 「8% **미만**」 목록에 반올림으로 `8.0%` 가 뜨면 규칙과 모순돼 보인다 → **절사로 통일**.
- **데이터 정직성**: 예측을 실적처럼 쓰지 않는가. **결측을 0 으로 만들지 않는가**(⚠`Number(null)===0`).
  ⚠**같은 앱 안에서 `0` 의 의미가 쓰는 쪽과 읽는 쪽에서 갈리지 않는가**(실측: 취込은 0=「데이터 없음」, 열람은 0=「수요 0」).

### ⚠**GREEN 인 테스트가 감사 대상이다** (2026-07-30b · P1 두 건이 정확히 이 두 구멍으로 빠져나갔다)

「테스트가 통과한다」는 「그 부류를 검사했다」가 아니다. 라운드마다 **다음 셋을 먼저 훑어라**:

1. **하네스가 자백한 「甘さ」 목록은 사각지대의 지도다.**
   `shared/_test_gas_stub.js` 는 스스로 `既知の甘さ: 型変換をしない（日付/数値文字列が Date/number にならない）` +
   `⚠ここが実 Sheets より甘いと、テストが通っても本番で壊れる` 라고 적어두었다. **정확히 그 일이 일어났다**
   (Sheets 가 날짜 문자열을 Date 셀로 강제 → 읽기측이 `String()` 을 먼저 해 매칭 실패).
   → **자백된 관대함 하나하나를 「그래서 무엇이 안 잡히는가」로 전개**할 것.
2. **스텁에 없는 API 는 그 경로가 한 번도 실행된 적 없다는 뜻이다.**
   스텁에 `appendRow` 가 없어서 신규 쓰기 함수는 **어떤 node 테스트도 실행한 적이 없었다**.
   → 신규 코드가 쓰는 API 를 스텁 구현 목록과 대조하라.
3. **교차앱 계약을 한쪽에서만 검증하는 테스트는 거짓 안심을 준다.**
   `ok('日付つきディープリンク', /tab=reserve&date=/.test(card))` 는 GREEN 이었지만,
   **수신 앱에는 `date` 를 읽는 코드가 아예 없었다.** 발신측 단독 검증은 계약을 보증하지 못한다.
   → 「A 가 만든 것을 B 가 실제로 읽는가」는 **양쪽 소스를 함께 보는 테스트**로만 고정된다.

같은 계열: **확인용(테스트 발송) 경로가 본번을 재현하지 못하면, 사람이 하는 유일한 확인 루프가
구조적으로 결함을 통과시킨다.** 실측: 테스트 발송은 항상 2일치를 만들어 P1 을 **원리적으로** 재현할 수 없었다.

⚠**마크업 grep으로 "없다"고 단정하지 마라.** 이 스택은 요소를 **런타임에 JS로 만든다** — `type="email"` 입력이 정적 HTML엔 0건이지만 `inMail.type='email'`로 생성되고 있었고, 그래서 "대상 없음"이라는 오판이 나왔다. 셀렉터·속성·클래스를 찾을 때는 **정적 마크업 + 생성 코드(`createElement`·`.type=`·`.className=`·템플릿 문자열) + 렌더된 DOM** 세 곳을 함께 본다.

**스크린은 손실이 있다.** 실측: 파괴성을 API 호출 패턴(`deleteSheet`·`setValues`…)으로 판정했더니 **이미 확정된 무게이트 파괴 함수 하나가 목록에서 빠졌다**(그 함수는 다른 API를 썼다). 그래서 **호출 패턴 스크린과 이름 스크린을 반드시 병행**한다: `setup*` `repair*` `migrate*` `reseed*` `cleanup*` `trash*` `purge*` `rebuild*` `diag*` `*Tick`.

또한 **무게이트 ≠ 결함**이다. 도메인 전원 편집이 설계인 앱에서는 `save*`가 열려 있는 게 정상이다. 판정 질문은 "게이트가 있는가"가 아니라 **"일반 사용자의 정상 업무를 넘어서는 작업인가"**(정비·마이그레이션·트리거 조작·외부 발송·비용 발생).

|---|---|
| 무게이트 전역 함수 | `.gs`의 `^function [a-zA-Z]`(밑줄 없는 이름) 목록 → `assertAdmin_\|getAdminContext` 유무 대조 → 위 이름 스크린으로 보강 |
| 토큰 유출 | `getOAuthToken` 가 클라로 전달되는 경로 |
| 무음 예외 | `catch\s*\([^)]*\)\s*\{\s*\}` |
| XSS 후보 | `innerHTML\s*=` (정적 문자열 제외) |
| 포커스 표시 제거 | `focus-visible[^{]*\{[^}]*outline:\s*none` → 대체 표시 유무 확인 |
| 공용 정본 드리프트 | 정본 ↔ 앱 사본 해시 비교 |

| 거대 단위 | 파일·함수 라인수 상위 목록(리팩터 후보이지 결함은 아님 — 심각도 부여 금지) |
| **토큰 전환이 무력화됐는지** | 새 토큰을 쓰는 규칙 vs 안 쓰는 규칙을 **명세도(a,b,c)·소스 순서**로 비교해 "지는 쌍"을 열거 |

⚠**`node --check`는 스코프 오류를 못 잡는다.** `shared/SharedUI.html`은 여러 IIFE가 각자 `var SU = W.SharedUI = ...`로 SU를 다시 잡는 구조인데, 새 IIFE에서 이를 빠뜨렸더니 `typeof SU.rovingGrid`가 **ReferenceError**를 던져(typeof는 맨 식별자만 보호하고 속성 접근은 보호하지 않는다) **같은 `<script>` 블록의 뒤쪽 정의가 전부 사라졌다**. 구문 검사는 통과했고 화면도 그럭저럭 떠서 놓칠 뻔했다. 공용 파일에 코드를 더한 뒤에는 **반드시 `pageerror`를 보고, 그 파일이 노출하는 함수가 실제로 존재하는지** 확인할 것.

**토큰/테마 전환 라운드의 필수 스크린.** CSS 변수로 색을 갈아끼우면 **규칙은 바뀌었는데 화면은 안 바뀌는** 실패가 난다 — 더 높은 명세도의 기존 규칙이 그대로 이기기 때문이다. 실측 2건:
- `.region-pill:not([style*="--rc"]).active` (0,3,0)가 기존 `html[data-theme="dark"] .region-pill.active` (0,3,1)에 져서 **다크만 수정 전 그대로**였다(라이트는 고쳐져 있어 더 안 보였다).
- `.dash-card-head .dc-more:hover`가 `.dash-card[class*="tone-"] .dc-more:hover` (0,4,0)에 져서 accent 카드만 미수정으로 남았다.

이 스크린의 실패 모드 2가지도 같이 기억할 것:
1. **경쟁 판정을 토큰 교집합으로 하면 노이즈가 폭발한다**(`:hover` 하나 겹쳤다고 `.mn-btn.is-add:hover` ↔ `.mn-btn.is-del:hover`를 충돌로 본다 — 361건 중 대부분). **마지막 컴파운드의 포함관계**(⊆)로 좁히면 29건까지 내려간다.
2. **`@media` 블록을 평탄화하면 문맥이 사라져** `forced-colors`/`prefers-reduced-motion` 안의 정당한 오버라이드가 "동일 셀렉터가 뒤에서 덮음"으로 잡힌다. 히트를 볼 때 **들여쓰기/블록 소속을 반드시 확인**한다.

⚠ 명세도는 **b(클래스·속성·의사클래스)를 c(요소)보다 먼저** 비교한다 → (0,4,0)이 (0,3,1)을 이긴다. 조상 클래스 하나를 앞에 붙이는 것만으로 이길 수 있고, 그게 `!important`보다 낫다.

⚠**"모달이 떴는가"를 스텁·`hidden`·히트테스트로 판정하지 마라 — 셋 다 "가려짐"을 원리적으로 못 본다.**
확인 다이얼로그(z 181)를 진행률 오버레이(`.su-prog-ov` z 3200)가 **완전히 덮고 있는데도** 다음이 전부 "정상"이라 답했다:
1. `APP.confirmDialog`를 **스텁으로 갈아끼운 테스트** — 「호출됐는가」만 보므로 렌더 결과를 볼 수 없다. **자기가 검증하려는 대상을 스텁하면 그 대상은 검증되지 않는다.**
2. `pop.hidden === false` — 열려 있는 건 맞다. 보이는지는 별개다.
3. `elementFromPoint(버튼 중심)` → 버튼이 반환됨. **`trapFocus`의 `isolateBackground`가 앞의 오버레이를 `inert`로 만들면 히트테스트가 素通り**하기 때문. 결과적으로 "보이지 않는데 누를 수 있는" 최악의 상태가 "정상"으로 보고된다.
4. `offsetParent !== null`로 가시성 판정 — `position:fixed` 요소는 **항상 null**이라 무조건 "안 보임".

→ 판정은 **클립 스크린샷 목시**(`page.screenshot(clip=팝업 rect)`) + **경쟁 오버레이가 실제로 닫혔는지**(`.su-prog-ov`의 computed display/opacity/rect)로 한다. 클릭은 `element.click()`(히트테스트 우회)이 아니라 **실마우스 좌표**로.
같은 사고의 일반형: **"누를 수 있는가"와 "읽을 수 있는가"는 다른 질문**이다. 동의를 받는 UI에서는 후자가 본질이며, 리뷰어가 전자만 검사해 "문제없음"으로 반증할 수 있다(실제로 1차 리뷰가 그렇게 통과시켰다).

⚠**앱의 `Stylesheet.html` 을 고쳤는데 화면이 안 바뀌면, 그 규칙은 `shared/SharedUI.html` 에 있다.**
include 순서가 `Stylesheet` → `SharedUI` 라서, **같은 명세도면 shared 가 뒤에 와서 이긴다**. 실측: `.brand-txt .hm-eyebrow`(0,2,0)가 양쪽에 있어 energy 쪽 값을 바꿔도 비율이 4.20 그대로였다. 색 토큰이 아니라 **리터럴 색**을 고칠 때는 반드시 `shared/` 도 함께 grep 할 것. 고쳤으면 `sync_shared.py` 를 잊지 말 것(안 하면 9앱 중 1앱만 고쳐진다).

⚠**`color-mix(..., transparent)` 지 위의 문자는 「조상에 따라 비율이 달라진다」.** `.pk-tag` 는 자기 지가 accent 16%+투명이라, 밝은 카드 위에서는 통과하고 어두운 컨텍스트에서는 4.09 로 떨어졌다. 스윕이 잡은 지점을 로컬에서 재현하려 해도 샘플 지점이 어긋나 재현되지 않는 일이 있다(실측). → **지를 불투명하게**(`transparent` 대신 `var(--surface)`) 만들어 조상 의존을 끊는 편이, 원인을 특정하는 것보다 확실하다.

✅**forced-colors 는 이 도구로 재라**: `tools/forced_colors_sweep.py`(계산값 비교). CSS 로 처방을 써 둔 것과 그 모드에서 실제로 구별되는 것은 별개다.

⚠**이 차원에서 픽셀 샘플링은 잘못된 도구다.** 초판을 contrast_sweep 처럼 픽셀로 만들었더니 **위양성만** 나왔다(선택 요소가 sticky 헤더 뒤로 스크롤아웃·페어링 인덱스와 좌표 어긋남). forced-colors 는 **used value 자체가 시스템 색으로 치환**되므로 `getComputedStyle` 이 결과를 그대로 돌려준다 → 계산값 비교면 스크롤·가려짐·좌표 문제가 원리적으로 사라진다. **「같은 도구를 다른 차원에 재사용」이 함정이었다.**

⚠**0 건 ≠ 결함 없음 — 비교 건수를 반드시 함께 봐라.** 실측: 초판이 「9앱 0건」이라 보고했을 때, 검사 B·C 는 **한 번도 실행되지 않았고**(대상이 부트 DOM 에 없음) A 도 약 12쌍만 비교했으며 master·chat-notify 는 **마커 0개로 통째로 미감사**였다. 어휘를 이 리포의 실제 상태 클래스(`.is-on/.is-sel/.is-cur/.on`)까지 넓히고 A 에서 가시성 요구를 빼자 **12→62쌍**이 되며 결함이 드러났다. 「0건」을 보고할 땐 **무엇을 몇 번 쟀는지**를 같이 적는다.

⚠**측정에서 걸러야 하는 두 부류**(넣지 않으면 위양성이 난다): ① **표시 토글**(탭 패인 등 — 구별을 담당하는 것이 색이 아니라 `display`) ② **자손이 상태를 나르는 경우**(부모 skin 은 같고 자식 pip/스위치만 다름 → 자손 다이제스트도 함께 비교).

⚠**면적이 큰 선택에 `background: Highlight` 를 쓰지 마라.** 탭·칩처럼 텍스트가 직계인 요소엔 맞지만, 카드처럼 자손이 많으면 **자손의 색이 개별로 CanvasText 로 강제**되어 「Highlight 지에 검은 글자」가 된다(실측 약 1.3:1). 큰 면은 **내측 링**(`outline: 3px solid Highlight; outline-offset: -3px`)이 안전하다.

⚠**도구가 못 보는 곳은 손으로 확인한다.** 이 스윕은 「통상에서도 구별 안 되면 별건」으로 넘기고, **부트 화면에 없는 상태**(선택된 카드·모달·탭 전환 후)는 애초에 못 본다. 실제로 wiki `.kn-card.is-sel` 은 스윕을 0건으로 통과했는데, 상태를 **만들어서** 재보니 강제 배색은 물론 **통상 다크에서도 선택이 완전히 구별 불가**였다(`[data-theme="dark"] .kn-card` 가 같은 명세도로 뒤에 와서 선택 규칙을 통째로 덮음). 선택 상태는 앱마다 클래스를 실제로 grep 해서 **상태를 합성해 확인**할 것.

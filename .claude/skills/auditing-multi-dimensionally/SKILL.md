# 다방면 감사

## Overview

넓은 감사는 예측 가능한 방식으로 실패한다: **커버리지가 "어쩌다 부른 검사자"를 따라가고**(부른 쪽이 디자인 감사자면 보고서가 디자인으로 쏠린다), 발견사항에 **재현조건과 검증법이 빠져** 다음 라운드에서 같은 코드를 다시 읽게 된다.

이 스킬은 셋을 고정한다 — **관점 집합**(무엇도 조용히 빠지지 않게), **발견사항 계약**(모든 항목이 같은 슬롯을 채우게), **반증 게이트**(확정이라 부르기 전에).

**핵심 원칙: 합의는 증거가 아니다.** 누군가 죽이려 시도했는데 살아남았을 때만 `확정`이다. 리뷰어 10명이 만장일치로 승인한 취약점이 실제로는 존재하지 않았던 사례가 보고되어 있다.

## When to use

- 광범위 검토 요청 / 릴리스 전 점검 / 과거 감사 재검증 / 큰 라운드 직후 회귀 확인
- **쓰지 말 것**: 단일 diff 리뷰(`review-specialist`), 재현되는 특정 버그(systematic-debugging), 기능 설계(brainstorming)

## 인자

```
/auditing-multi-dimensionally [ultracode] [범위…]
```

| 인자 | 효과 |
|---|---|
| **(없음) — 기본값** | **손으로 Agent 를 띄운다**(관점 1개 = 에이전트 1기). Workflow 를 쓰지 않는다 |
| `ultracode` (동의어: `workflow`) | Workflow 를 **써도 된다**(→ 「실행 방식」절). ⚠**허가이지 명령이 아니다** — 아래 판정을 거친다 |
| 그 밖의 토큰 | 범위 힌트로 해석한다 — 앱 이름(`energy`·`position`…) / 차원 태그(`security`·`design`…) / `diff`(직전 커밋 이후 변경분만) |

**판정 규칙 — 2단 게이트**

인자 문자열을 소문자화해 공백으로 쪼갠다.

**① 허가 게이트**: `ultracode` / `workflow` 토큰이 **없으면 Workflow 를 쓰지 않는다.** 예외 없다.
⚠**임의로 승격하지 마라.** 감사 대상이 커 보인다는 이유로 쓰는 것은 옵트인 위반이다.
대신 손으로 진행하면서 **「워크플로로 돌리면 무엇이 좋아지는지 + 대략의 비용」을 한 줄로 제안**한다.

**② 효율 게이트**(허가가 있어도 통과해야 함): ⚠**인자는 허가이지 명령이 아니다.**
아래를 **먼저 세어 보고**, 값이 없다고 판단되면 **쓰지 않고 그 이유를 한 줄로 말한 뒤 손으로 진행**한다.

| Workflow 가 값을 하는 신호 | 값을 못 하는 신호(= 손으로) |
|---|---|
| 관점 × 코드군이 **5기 이상**으로 갈린다 | 대상이 1앱·1차원·작은 diff — 에이전트 2~3기면 끝난다 |
| 발견이 많이 나올 것 같아 **반증 팬아웃이 커진다** | 결정적 스크린(grep·테스트)만으로 답이 나온다 |
| 에이전트 보고가 길어 **메인 컨텍스트를 밀어낼** 것 같다 | 단계 사이마다 **내 판단이 끼어야** 한다(설계 결정·사용자 확인) |
| 오래 걸려서 **중간에 사람이 지켜볼 필요가 없다** | 탐색적이라 다음 단계가 앞 결과를 보고서야 정해진다 |

⚠**세어 보지 않고 「크니까 워크플로」라고 하지 마라.** 관점 수·대상 파일 수를 실제로 센 뒤 판정하고,
**판정 근거를 한 줄로 보고**한다(예: 「관점 7 × 코드군 2 = 14기, 보고 길이 큼 → Workflow」).

⚠**`ultracode` 를 받았다고 반증·이중검토를 얇게 만들지 마라.** 늘리는 것은 찾는 쪽이 아니라
**죽이는 쪽까지 같이**다(근거는 「실행 방식」절).

- 범위 힌트가 없으면 **전 앱 × 전 차원**이 기본이다. 원장이 범위를 줄이게 두지 않는다(§1).

예: `/auditing-multi-dimensionally ultracode diff` — 직전 커밋 이후 변경분. 단 diff 가 작으면
②에서 걸러 **손으로** 진행하고 그렇게 말한다.

## 절차

### 1. 원장을 먼저 읽고, 원장을 믿지 마라

감사 시작 전 **기지 부채 원장**을 로드한다 — 과거 감사 산출물(`_audit_*.md`)·로드맵 문서·`docs/superpowers/specs`·개인 메모리. 코드에 `TODO` 주석이 없는 리포지토리에서는 이 문서가 유일한 부채 기록이다.

**그다음 원장을 git 이력과 대조한다.** 원장은 낡는다. "미검증"으로 적힌 항목이 이미 수정되어 있을 수 있다(실제 사례: 47건 중 39건이 이미 수정 완료였고, 그걸 모른 채 재감사해 라운드 하나를 낭비했다).

> 이 단계를 건너뛴 감사는 **의도적 트레이드오프를 Critical 신규 결함으로 보고한다.** 관측된 사례: 어떤 저장 경로가 rev를 올리지 않는 것을 최상위 결함으로 올렸으나, 실제로는 위양성 충돌을 피하려 의식적으로 뺀 것이었고 후속 과제(캐시 세대 분리)까지 기록되어 있었다. 원장을 읽었다면 `판단済` + 우선순위 재검토로 분류됐을 항목이다.

#### ⚠그러나 **원장이 커버리지를 줄이게 두지 마라** (2026-07-31 개정)

초판은 여기서 「**살아있는 것만** 감사 대상. 이연 항목은 재보고하지 않는다」라고 썼다. **그건 과했다.**
원장이 「보지 않을 것」의 목록이 되면, 원장이 틀린 만큼 그대로 사각지대가 된다 —
그리고 **이 원장은 실제로 자주 틀린다**(같은 리포에서 P3 22건 중 3건이 이미 수정 완료였고,
반대로 직전 라운드에는 원장의 범위·근거가 실제와 어긋난 사례가 3건 있었다: 경로 절반 누락·앱 절반 누락·원인 오기).

> **원장은 「어디를 볼지」의 힌트이지, 「무엇을 보지 않을지」의 명령이 아니다.**
> **점검은 전수로 한다. 원장이 줄이는 것은 「보고」뿐이다.**

산출은 **3분류**로 낸다(대상을 줄이는 게 아니라 라벨을 붙인다):

| 분류 | 의미 | 다룰 때 묻는 것 |
|---|---|---|
| `신규 확정` | 이번에 새로 나왔고 반증을 견뎠다 | 통상의 발견사항 계약(§3) |
| `기지(재확인)` | 원장에 있고 상태가 그대로다 | **정말 그대로인가**(코드로 확인). 상태가 변했으면 신규로 승격 |
| `판단済` | 사양으로 확정된 트레이드오프 | ⚠**「결함인가」가 아니라 「판단이 서 있는 전제가 아직 참인가」** |

⚠**`판단済` 의 전제를 원장에 적어두게 하라.** 「현상 유지로 결정」만 적혀 있으면 다음 라운드는
그 판단이 언제 뒤집혀야 하는지 알 수 없다. 예: 「스팟 예측 CAP 유지」의 전제는
**「JEPX 스팟에 제도상 가격 상한이 없다」**이므로, 제도가 바뀌면 판단도 바뀐다.

⚠**「전제 재확인」을 형식적으로 하지 마라.** 코드로 다시 확인한 것만 근거다.

⚠**원장이 「안 잰 것」을 「0건」으로 보이게 하지 마라.** 라운드마다
**재지 못한 범위를 원장에 명시**한다(예: 「대비는 9앱 중 2앱만 측정」). 안 적으면
다음 라운드가 커버리지를 오판한다 — 이 리포가 반복해 데인 「0건 ≠ 잰 게 없음」의 원장판이다.

### 2. 파일이 아니라 관점으로 분할한다

관점기반 읽기(PBR)는 체크리스트 읽기보다 **고유 결함을 더 많이, 결함당 더 싸게** 찾는다. 관점끼리 발견 집합의 중복이 작기 때문이다 — 뒤집으면 **관점 하나를 빼면 그만큼이 통째로 사각지대**가 된다.

- 차원 목록과 각 차원의 점검 항목은 `dimensions.md`.
- ⚠**D2 와 D6 은 각각 두 개로 쪼개서 배정한다**(2026-07-30 추가). 한 에이전트에 묶으면
  뒤쪽이 반드시 얕아진다 — 실제로 그렇게 놓쳤다:
  - **D2(서버측 동시성)** ↔ **D2-c(클라이언트측 레이스·멱등성)** … 원리가 다르다.
    서버는 락·TOCTOU, 클라는 재진입·out-of-order 응답·낙관적 UI 롤백·재렌더가 지우는 사용자 상태.
  - **D6(시각 인코딩·토큰)** ↔ **D6-b(행동 UX)** … 「어떻게 보이는가」와 「무엇이 일어나는가」는 별개다.
    로딩/비어있음/읽기실패의 구별, 되돌릴 수 없는 조작의 계약, **존재하지 않는 곳을 가리키지 않는가**.
  - **D6-c(애니메이션·모션)** 은 D6 에 한 줄로 두지 말고 별도로 본다.
- **에이전트 1기 = 1관점 × 1코드군.** 코드군은 컨텍스트가 들어가는 크기로 자른다(거대 앱은 3~4조각).
- **모델을 섞어라.** 도구 비교에서 발견의 93.4%가 정확히 한 도구에서만 검출됐다. 같은 모델 반복은 커버리지를 늘리지 않는다.
- 동시성 결함은 **서버-클라 쌍을 함께 봐야** 보인다. 한쪽만 준 관점은 그 부류를 구조적으로 못 찾는다.

### 3. 발견사항 계약 (모든 항목이 이 슬롯을 채운다)

```
### [P?/차원] `경로:라인`
**한 줄: 무엇이 어떻게 깨지는가**

- 근거:     코드 인용 + 그 인용이 왜 결론을 함의하는지
- 재현조건: 누가/언제/몇 명이/무엇을 하면 발생하는가(트리거 창)
- 영향:     데이터 손실? 자기치유? 침묵성? 권한 경계?
- 수정안:   구체적 방향
- 검증법:   수정됐는지 판정하는 결정적 방법(명령·쿼리·프리뷰 절차)
- 반증:     죽이려고 시도한 것과, 왜 살아남았는지
- 확신도:   확정 | 미검증 | 반증됨
- 분류:     신규 확정 | 기지(재확인) | 판단済   ← §1. **대상을 줄이는 라벨이 아니라 보고용 라벨**
```

**`검증법`이 없으면 그 항목은 완성되지 않은 것이다.** 이 필드가 없어서 다음 라운드가 코드를 다시 읽어야 했던 전례가 있다.

**`확신도`가 다른 항목을 같은 목록에 섞지 마라.** `확정`과 `미검증`은 절을 나눠 보고한다.

### 4. 승격 전에 반증한다

P1 이상은 **반증 전담 검사자**를 붙인다. 계약은 "검토해줘"가 아니라 **"이 지적을 죽여라. 죽이지 못했을 때만 확정으로 승격한다"**이다.

- 반증자에게 **원 지적문을 보여주지 않는다**(앵커링 방지). 파일·라인·증상만 주고 스스로 판정하게 한다.
- 가능하면 **실행/재현 게이트**를 통과시킨다(스크립트·프리뷰·쿼리). 재현 게이트 없는 다중 리뷰는 오탐을 통과시킨다.
- P2는 샘플링, P3는 기본 `미검증`으로 표시하고 배치 처리한다.

## 실행 방식 — 손으로 띄우기 vs **Workflow(ultracode)**

**기본은 손으로 Agent 를 띄우는 것**이다(관점 1개 = 에이전트 1기). 그걸로 충분한 경우가 많다.

**Workflow 가 값을 하는 조건** — 2026-07-30b 라운드의 실측 근거:

- 그 라운드는 손으로 **관점 8기 + 블라인드 반증 2기 + 배포전 이중검토 2기 = 12기**를 띄웠다. 결과는 좋았지만
  **메인 컨텍스트가 보고 12개를 전부 읽느라 매우 길어졌다.** 이게 실제 비용이었다.
- 그리고 반증·이중검토를 **사람이 기억해서** 붙였다. **빠뜨려도 아무도 모른다.**

→ Workflow 의 이점은 「에이전트를 더 많이」가 아니라 다음 둘이다:
  ① **에이전트 출력이 메인 컨텍스트에 안 쌓인다** ② **반증 게이트가 스크립트에 고정돼 빠뜨릴 수 없다**

### ⚠확장할 때 반드시 지킬 것

> **그 라운드의 최대 성과는 팬아웃이 아니라 2차 opus 리뷰와 블라인드 반증자가 냈다.**
> P1 두 건 중 하나(딥링크가 「공허하게 참」)는 **팬아웃이 GREEN 으로 통과시킨 것을 2차 리뷰가 실측으로 뒤집은 것**이다.

찾는 쪽만 넓히고 죽이는 쪽을 얇게 만들면 **더 빨리 더 많은 미검증 지적**이 나올 뿐이다.
스크립트에서 반증 단계의 비율을 줄이지 마라.

### 스크립트 골격 (이 스킬의 불변식을 코드로 고정)

```js
export const meta = {
  name: 'multi-dim-audit',
  description: '관점별 감사 → 발견마다 블라인드 반증 → 확정만 승격',
  phases: [{ title: 'Find' }, { title: 'Refute' }, { title: 'Synthesize' }]
}

/* ⚠pipeline 을 쓴다(배리어 없음). 한 관점이 끝나는 즉시 그 발견의 반증이 시작된다.
   parallel 로 전 관점을 기다리면 느린 관점 하나가 전체를 잡는다. */
const findings = await pipeline(DIMENSIONS,
  d => agent(d.prompt, { label: `find:${d.key}`, phase: 'Find', schema: FINDINGS, model: d.model }),
  (res, d) => parallel((res?.findings ?? [])
    .filter(f => f.severity === 'P0' || f.severity === 'P1')      // P1 이상만 반증 전담
    .map(f => () => agent(
      /* ⚠**원 지적문을 넣지 마라.** 파일·라인·증상만 주고 스스로 판정하게 한다(앵커링 방지).
         여기서 f.summary 를 그대로 붙이면 반증이 아니라 확인이 된다 — 스크립트에서 가장 틀리기 쉬운 곳. */
      blindRefutePrompt(f.file, f.line, f.symptom),
      { label: `refute:${f.file}`, phase: 'Refute', schema: VERDICT, model: 'opus' })
      .then(v => ({ ...f, verdict: v })))))

const confirmed = findings.flat().filter(Boolean).filter(f => f.verdict && !f.verdict.refuted)
log(`확정 ${confirmed.length} / 전체 ${findings.flat().length}`)   // ⚠분모를 함께 남긴다
```

- **모델을 섞어라**(`opts.model`). 도구 비교에서 발견의 93.4%가 정확히 한 도구에서만 검출됐다.
- **schema 를 써라.** 발견사항 계약(§3)의 슬롯을 JSON Schema 로 강제하면 `검증법` 누락이 구조적으로 막힌다.
- **`log()` 로 분모를 남겨라**(관점 수·발견 수·반증 통과율). 「0건」이 「안 쟀음」으로 보이지 않게.
- 수정까지 시킬 거면 `isolation: 'worktree'` — 다만 감사는 읽기 전용이라 보통 불필요하다(비싸다).

### ⚠쓸지 말지는 2단 게이트로 (상세는 「인자」절)

1. **허가**: 스킬 인자에 `ultracode`/`workflow` 가 있거나, 사용자가 자기 말로 요청했을 때만.
   프롬프트에 `ultracode` 키워드가 있는 경우도 포함. **없으면 안 쓴다.**
2. **효율**: 허가가 있어도 **관점 수·대상 규모를 세어 보고** 값이 없으면 쓰지 않는다.
   ⚠**인자는 허가이지 명령이 아니다.** 1앱·1차원·작은 diff 라면 손으로 하는 편이 빠르고,
   단계마다 판단이 끼는 탐색적 감사는 애초에 스크립트로 굳히면 안 된다.

두 게이트 중 어디서 걸렸든 **그 이유를 한 줄로 말하고** 손으로 진행한다. 조용히 방식만 바꾸지 않는다.

## 심각도 = 점수가 아니라 결정트리

사내·로그인 게이트 앱에서 CVSS는 정보량이 0이다(AV/PR/UI 축이 상수). 점수 대신 4문항으로 판정한다.

| 질문 | 효과 |
|---|---|
| Q1 복구 불가 데이터 손실 / 인가 우회로 파괴적 작업 | → **P0** |
| Q2 자기치유되는가(다음 틱·폴링·재수집으로 회복) | → 강등 |
| Q3 **침묵인가**(사용자가 모른 채 틀린 값으로 업무 판단) | → 승격 |
| Q4 권한 경계를 넘는가(비관리자가 관리 기능·타인 데이터) | → 승격 |

**P0** 배포 차단·즉시 / **P1** 이번 라운드 내 / **P2** 큐 적재 / **P3** 배치(오탐 위험 구간)

## 코드를 읽기 전에 돌리는 결정적 스크린

기계가 판정할 수 있는 것에 에이전트 컨텍스트를 쓰지 마라. 전수 grep으로 먼저 좁힌다 — 목록은 `dimensions.md`의 「자동 스크린」.

## Common mistakes

| 실수 | 결과 |
|---|---|
| 어쩌다 부른 검사자에게 커버리지를 맡김 | 보고서가 그 검사자 전문 분야로 쏠리고 나머지 차원은 통째로 누락 |
| `검증법` 생략 | 다음 라운드가 같은 코드를 다시 읽음 |
| 확정과 미검증을 한 목록에 섞음 | 이미 고쳐진 것·오탐이 수정 큐에 들어감 |
| 협조적 2차 리뷰를 반증으로 착각 | 합의만 쌓이고 오탐이 통과 |
| 생성물(`preview.html`·목데이터·스냅샷)을 감사 대상에 포함 | 대상 라인수가 몇 배로 부풀고 무의미한 지적이 쏟아짐 |
| 개선안으로 "ARIA 추가"를 남발 | ARIA를 쓴 페이지가 안 쓴 페이지보다 오류가 더 많다(59.1 vs 42) |
| 없는 인프라를 매번 지적(테스트 커버리지 등) | 노이즈. `검증법` 필드로 흡수하라 |
| **원장을 「보지 않을 것」의 목록으로 씀** | 원장이 틀린 만큼 그대로 사각지대. 점검은 전수, 줄이는 건 **보고**뿐(§1) |
| **재지 못한 범위를 원장에 안 적음** | 다음 라운드가 「0건」과 「안 쟀음」을 구별 못 해 커버리지를 오판 |
| **「그 코드가 있다」로 「그 코드가 효력이 있다」를 확인했다고 믿음** | 소스 문자열 검사가 **도달 불가능한 죽은 코드**를 GREEN 으로 통과시킨다(실측 2건) |
| **입력에 넣은 값을 재고 출력에 나온 결과를 안 잼** | 「피커는 X·그래프는 Y」를 통과시킨다. **행동은 출력으로 판정**하라 |
| 신규 테스트·e2e 를 **뮤테이션 검사 없이** 채택 | 아무것도 안 재는 검사가 늘어난다. 「옛 코드에서 실패하는가」를 반드시 확인 |
| 하네스가 **전제(지연·실패)를 실제로 일으켰는지 확인 안 함** | 훅이 안 걸린 채 「OK」가 줄줄이 나온다(실측: `APP.getMeta` 교체가 무효였다) |

## Real-world impact

이 방법으로 감사했을 때 **감사가 자기 자신의 최근 산출물을 잡았다**: 배포 직후의 공용 포커스링이 `:where()`(명시도 0) 설계 탓에 앱의 레거시 `outline:none` 한 줄에 무력화되어, 그 앱에서는 한 군데도 렌더링되지 않고 있었다. 협조적 이중검토는 같은 코드를 "안전하다"고 승인했었다.

## 2. 설계 — 정의서를 그대로 옮긴 것만

### 2-1. 범위(scope)를 인자로 받는 코어 하나 — M1

```ts
export interface StreakScope {
  /** 기본 "regular"(§1-1 · 사용자 결정 ⑴) */
  competition?: string;
  /** 이 날짜까지. 기본 "9999-12-31" */
  through?: string;
  /** 훑을 시즌의 하한. **시즌 모드면 그 시즌** · 통산 모드면 보유 하한 */
  fromSeason: number;
  /** 훑을 시즌의 상한 = **보고 있는 시즌**(§1-5 「통산의 끝은 언제나 보고 있는 시즌」) */
  toSeason: number;
}
```

- **시즌 모드** = `fromSeason === toSeason`. **통산 모드** = `fromSeason < toSeason`.
- ⚠**두 모드가 같은 코드를 탄다** — 갈라 두면 규칙이 두 벌이 되고 반드시 값이 갈린다(M1).
- 기존 `battingStreaks(db, season, competition, through)` 는 **시그니처를 그대로 두고**
  코어에 `{fromSeason: season, toSeason: season}` 로 넘기는 얇은 껍데기가 된다.
  ⚠**SQL 의 `g.season = ?` 를 `g.season BETWEEN ? AND ?` 로 바꾼다** — 양쪽이 같은 값이면 같은 집합이다.
  **계산 결과가 안 바뀌는 것을 시험으로 확인한다**(§5-1 T-B0).

### 2-2. 투수 — 사건과 마루

- 사건 = `pitching_line` 한 행(정규 · `played`). `PRIMARY KEY (game_id, player_id)` 라 **등판 = 경기**.
- `hit` = `runs === 0`. **건너뜀 없음**(등판 안 한 경기는 열에 안 들어온다).
- 마루 = 극대 구간. `current` = 열 끝에 붙은 마루(끝이 실점이면 **`null`**).
- ⚠**`current` 를 `0` 으로 쓰지 않는다** — 「지금 이어지는 마루가 없다」와 「등판이 0이다」는 다른 사실이다(M11).
  등판 0 인 선수는 **지도에 안 들어온다.** 호출자가 명시적으로 쓸 `emptyPitchingStreaks()` 를 둔다(`emptyStreaks` 선례).

### 2-3. 규칙 R 의 구현 — 경계 등판만 `pa_event` 를 본다

```
마루 안 (전 등판이 무실점)   → Σ pitching_line.outs        **100% 정본**
시작 경계 (마루 직전의 실점 등판) → 마지막 실점 하프이닝 **뒤**의 아웃
끝   경계 (마루 직후의 실점 등판) → 첫 실점 하프이닝 **앞**의 아웃
```

⚠**무실점 등판에 `pa_event` 를 쓰지 않는다**(정의서 §3-4). 무실점 등판 35,171 중 **1,691(4.8%)** 에서
`pa_event` 가 「실점이 있다」고 말한다(계승주자) — 그대로 쓰면 **공식적으로 무실점인 등판 21개 중 1개**에서
마루가 거짓으로 끊긴다.

**하프이닝별 아웃**(정의서 §3-4 의 구현 지시 그대로):
타석 `i` 가 만든 아웃 = `outs_before(i+1) − outs_before(i)`, 마지막 타석은 `3 − outs_before(last)`.
`pitcher_id` 가 일치하는 타석의 아웃만 그 투수에게 더한다.
⚠**`LEAD` 는 하프이닝 전체(다른 투수 타석 포함) 위에서 계산한다** — 투수로 먼저 거르면 아웃이 어긋난다.

**확정 판정**(정의서 §8 · 둘 중 하나):
1. 그 등판의 하프이닝이 **1개** → 기여는 **무조건 0**(실점이 붙은 이상 그 하프이닝에 붙었다).
2. `Σ pa_event.runs_scored = pitching_line.runs` **그리고** `Σ 하프이닝별 아웃 = pitching_line.outs`.

⚠**둘 다 아니면 미확정**이고 기여를 **0 으로 두되 `exact = false`** 로 표시한다(M7 — 근사로 흘리지 않는다).
⚠**「대략 맞으니 통과」로 완화하지 마라** — 그 완화가 정의서 §5 의 이름 판정을 뒤집는다.

**값 3종**(정의서 §3-3 마지막 줄이 요구하는 것):

```ts
export interface ScorelessInnings {
  lowerOuts: number;   // 미확정 경계의 기여를 0 으로 둔 값. **반드시 참**
  upperOuts: number;   // 하한 + 미확정 경계 등판의 **전체 아웃**. **반드시 참**
  exact: boolean;      // 양 끝 다 확정. false 면 화면은 「N回以上」
}
```

### 2-4. 「以上」의 사유는 둘이고 섞지 않는다 (정의서 §1-6)

| 필드 | 뜻 | 화면이 붙일 각주 |
|---|---|---|
| `exact === false` | **그 등판의 실점 시점을 못 짚는다** | 「最大 N回」 |
| `atRangeStart === true` | **그 앞을 우리가 안 봤다** | 통산 모드면 「(하한−1)年以前は未参照」 |

⚠**`atRangeStart` 의 뜻이 모드마다 다르다.** 시즌 모드에서는 「시즌 시작」이라 **「以上」이 아니다**
(화면이 이미 「今季」라고 말한다 · 山﨑 케이스가 그 증거다). 통산 모드에서만 「以上」이 된다.
→ **계산 계층은 사실(`atRangeStart` + `fromSeason`)만 낸다. 문구는 화면이 고른다.**
⚠**「2017」을 코드에 박지 않는다** — `fromSeason − 1` 에서 유도한다(사용자 결정 ⑵).

⚠**끝쪽에는 「以上」을 붙이지 않는다**(§1-4). 안 끊긴 것은 데이터가 없어서가 아니라 아직 안 끊겨서다 →
`open: boolean` 으로 낸다. **`open` 은 「継続中」이 아니다**(§1-5 는 세 상태이고 그 판정은 화면 몫).

### 2-5. 분모 3종 (M2 · 정의서 §1-6)

| # | 무엇 | 어디에 |
|---|---|---|
| ⑴ 훑은 사건 수 | 등판 수 / 타석이 있던 경기 수 | `appearances` · `games` |
| ⑵ 마루의 기간 | `from`〜`to` | 마루마다 |
| ⑶ 집계 범위 | `fromSeason`〜`toSeason` + `competition` | 결과 객체 |

⚠**⑶ 을 결과에 넣는 이유**: 화면이 「2018〜2026年 レギュラーシーズン」이라고 **말할 근거**를 계산이 갖고 있어야 한다.
정의서 §5 의 이름 판정 조건 3번이 그것이다.

### 2-6. 순위 (정의서 §1-7)

- 동률은 **같은 순위 · 다음 순위 건너뜀**(`docs/metrics/README.md` §5 상속 · `rankBy` 와 같은 규약).
- **2차 정렬**: 1) 길이 → 2) 이닝이면 아웃 수 → 3) `to` 늦은 것 먼저 → 4) **`playerId` 오름차순**.
  ⚠**4번이 없으면 정적 생성이라 빌드마다 diff 가 흔들린다.**
- ⚠**`exact === false` 인 이닝 기록은 순위 `null`. 목록에서 빼지 않는다.**
- ⚠**표시 하한(§1-7 의 5등판·10등판 등)은 여기서 안 정한다** — 정의서 §6-9 가 「화면 설계와 같이」로 남겼다.

## 3. ⚠고치지 않는 것

## 4. ⚠`連続試合無安打` 의 통산은 만들지 않는다 — 사용자 결정 대기

정의서 §4-4 가 세 근거로 **권고**했고 §6-7 이 **「사용자 결정 필요」**로 남겼다:
⑴ 공표 범주가 없다 ⑵ 예외 규칙의 부호가 반대다 ⑶ 토글의 뜻이 흐려진다.

→ **통산 타자 결과 타입에 `hitless` 를 두지 않는다.** `null` 로 두면 「기록이 없다」로 읽힌다 —
**타입에 자리가 없는 것**이 「우리가 아직 안 정했다」를 정직하게 말한다.
⚠**결정이 반대로 나면 필드 하나를 더하는 일이고, 코어는 이미 세고 있다**(같은 스캐너를 부르면 된다).

## 5. 작업 — **실패하는 시험 → 구현 → 통과 확인**

⚠**각 시험은 채택 전에 뮤테이션한다**(작업규칙 9) — 「고치기 전 코드에서 떨어지는가」.

### 5-1. 타자 — 범위 코어로 리팩터 (결과 불변)

| 시험 | 무엇을 잡는가 |
|---|---|
| **T-B0** ⚠실DB · 완결 8시즌 전 시즌에 대해 `battingStreaks(db, s)` 의 결과가 **리팩터 전후로 같다** | 「결과를 안 바꾼다」는 약속. ⚠비교는 리팩터 전 코드로 만든 **스냅샷 파일이 아니라**, 같은 커밋 안에서 `season BETWEEN` 코어와 옛 `season =` SQL 을 **둘 다 돌려 맞댄다** |
| **T-B1** 통산 모드가 시즌 경계를 넘어 잇는다(2025 마지막 안타 → 2026 첫 안타 = 2) | ①(SQL 의 `g.season = ?`) |
| **T-B2** 통산 모드의 분모 `games` 가 **전 범위**의 「타석이 있던 경기」다 | ⑤(분모가 마루보다 작아지는 화면) |
| **T-B3** 통산 마루가 **`toSeason` 에서 잘린다**(2022 화면이 2023 을 말하지 않는다) | ⑦ |
| **T-B4** `seasons` 가 **사건이 있던 시즌만** 담아 건너뛴 시즌이 드러난다(2019 → 2022) | ⑥ |
| **T-B5** `atRangeStart` 가 범위 첫 사건에서 시작한 마루에만 참 | §1-4 |
| **T-B6** ⚠**시즌 모드에서 결과가 기존과 완전히 같다**(합성 DB · 기존 15본 그대로 통과) | 회귀 |

⚠**T-B0 의 분모를 보고한다** — 「몇 선수-시즌을 맞댔는가」. 「0건 통과」와 구별한다.

### 5-2. 투수 — PSA · PSI (합성 DB)

**⑴ 「그 시즌이 아직 진행 중인가」(정의서 §1-5 의 조건 ⑶).**
정의서는 **「팀 소화 경기 < `regularSeasonGames(season)`」**을 제안했다. **그걸 안 썼다.**

- **M1** — 선수 페이지에는 「이 시즌이 끝났는가」의 한 벌이 이미 있다
  (`seasonPast = d.seasonOver || seasonSurelyOver(d.season, freshness.heldTo)`). 두 벌을 두면
  **같은 화면의 타자 블록과 투수 블록이 다른 시제로 말할 수 있다.**
- **명제가 다르다** — 「팀이 143경기를 다 치렀다」와 「시즌이 끝났다」는 같은 말이 아니다.
  우천 미실시로 142에서 끝나는 팀이 있고(2021 미실시 32건), 2020 은 120경기다
  (`regularSeasonGames` 가 시즌별 표인 이유가 그것이다).
- **방향이 안전하다** — `seasonPast` 는 `true` 만 증명이고 `false` 는 「모른다」다(M11).

**⑵ 「그때 소속 구단」.** ⚠**답이 스키마에 이미 있었다** — `pitching_line.side` 가 홈/원정을 말하므로
그 경기의 구단 코드가 **추측이 아니라 사실**로 나온다(「받고 있는데 안 읽던 것」의 네 번째 모양).

- 이적 판정은 **마지막 등판의 구단 대 그 페이지의 구단**으로 한다. 다르면 **경기 수를 안 내고
  경과 일수**를 낸다(M11 — 「그때 소속 구단의 경기 수」가 「그가 던질 수 있었던 경기 수」를
  뜻하지 않게 되기 때문).
- ⚠**A→B→A 는 못 잡는다.** 알고 남긴 한계다(그 경우 경기 수가 과다해진다).
- ⚠**그 갈림(이적 쪽)은 실DB 시험이 없다** — 화면 쪽만 픽스처로 고정했다(§10-7).

**⑶ 그리고 `N` 을 상태의 판정 조건이 아니라 분모로 썼다.**
사용자 결정 ⑹ 이 「상수를 만들지 마라」이므로 「며칠 이상 공백이면 継続中이 아니다」를 만들 수 없다.
대신 **세 상태와 무관하게 늘** 「以後 <구단> N試合で登板なし」를 낸다 — 島本(27등판)형 오독을
**상수 없이** 막는다. 정의서 §1-5 는 그 문장을 상태 ②에만 붙였는데, **상태 ①에도 붙여야
「최신 경기일에 안 던진 사람」이 「지금 던지고 있는 사람」으로 안 읽힌다**(타자 쪽에서 실측 21명이
그 상태였던 그 결함이다).

### 10-3. 표시 하한(§6-9)

| 화면 | 정한 값 | 근거 |
|---|---|---|
| **선수 페이지** | **없다. 0도 낸다** | M11·M12 가 그것을 **요구한다** — `0登板` 과 「데이터 없음」이 다른 화면이어야 하므로 0을 그려야 한다 |
| **홈·구단 「続いている記録」** | **連続無失点登板 5등판**(`HOME_PITCHING_STREAK_MIN`) | 실측(2026 시즌 범위 · 진행 중 마루 133명): **≥3 62명 · ≥5 37명 · ≥8 12명 · ≥10 7명 · ≥15 2명**. 표는 10행이라 3이면 하한 근처 잡음으로 차고 8이면 거의 안 거른다. 5는 **37명에서 상위 10명**을 고른다 |
| **이닝 마루** | **정하지 않았다** | 목록에 안 실었기 때문이다(아래) — 실을 때 정한다 |
| **歴代 목록** | **안 만들었다** | 이번 범위 밖 |

⚠**타자의 `HOME_STREAK_MIN`(5)과 수가 같은 것은 우연이고 근거가 다르다.** 별도 상수로 둔다 —
정의서 §1-7 의 「안타와 출루에 같은 값을 쓰지 마라」와 같은 정신이다.

### 10-4. 홈 화면에 투수를 넣을지 — **넣었다. 連続無失点登板만.**

- **넣은 이유**: 그 구획은 「続いている記録」이라고만 말하면서 실은 **打者の記録만** 실었다 —
  `blocks.ts` 의 「打者のみ」와 **같은 모양의 결함**이고, 그 상태로는 2025년 NPB 최대의
  연속 기록(石井大智 50試合)이 이 화면에 나올 수 없었다.
- **이닝은 안 넣었다**(정의서 §1-7): `23回以上` 은 `23回` 와 **비교가 성립하지 않아** 순위를 못 붙인다.
  이 표는 길이로 줄 세우는 표이므로 **항상 확정인 등판 축**만 쓴다.
- ⚠**타자의 「최신 경기일에 출장」 조건을 그대로 걸지 않았다.** 구원투수는 매일 안 던진다 —
  실측(2026 · 최신 정규 2026-08-16): **5등판 이상 37명 중 최신 경기일 등판은 9명**,
  **8등판 이상 12명 중 1명**. 걸면 **상위 기록이 거의 전부 사라진다**(16등판 1위도 3일 전 등판이다).
- ⚠**그래서 이 표에는 「以上」이 한 번도 안 나온다.** 등판 축은 경계 사유(`exact`)의 영향을 안 받고,
  범위 사유(`atRangeStart`)는 **시즌 범위에서는 「以上」이 아니기 때문**이다 — 즉 「順位를 못 붙이는 값」이
  섞이지 않는다(정의서 §1-7 이 걱정한 그 상태를 **구성으로** 피했다).
- ⚠⚠**넣자마자 반대 방향의 같은 결함이 났다 — 자리를 나눠야 했다.**
  길이로만 자르니 **2026 홈 화면이 10행 중 7행이 투수**가 됐다. 실측(하한 5): 후보 수가
  **2026 타자 23 · 투수 37** · **2025 타자 6 · 투수 37** · **2022 타자 4 · 투수 32** ·
  **2018 타자 7 · 투수 19** 다 — 진행 중 마루가 있는 투수는 늘 수십 명인데, 타자는
  「최신 경기일에 출장」까지 요구하므로 한 자릿수인 시즌이 흔하다. **끝난 시즌이면 거의 전부가
  투수가 된다.** → `shareStreakRows` 가 **자리를 절반씩** 주고, 한쪽이 모자라면 다른 쪽이 채운다.
  ⚠**순서는 안 바꾼다** — 나누는 것은 자리이지 순위가 아니다.
  ⚠**이 결함을 실측으로만 봤다** — 화면을 실제로 구워 보기 전에는 시험도 타입도 안 잡았다.
- ⚠**각주를 고쳐야 했다.** 옛 문장(「その日より後に試合があれば、記録はもう途切れているか、
  本人が出ていないかのどちらかです」)은 **투수에게 거짓**이다 — 등판하지 않으면 안 끊긴다.
  「출장하지 않았다」와 「기록이 끊겼다」가 타자에서는 배타적이지만 투수에서는 아니다.
  ⚠**종류가 다르면 길이 비교가 성립하지 않는다**는 것도 같이 적었다.

### 10-5. 타자 3종 — 통산 탭을 붙였다(§4-3 의 ①~⑦)

- 토글은 **시즌 넘김 마루가 실재하는 선수에게만**(사용자 결정 ⑶).
- ⚠**탭이 생기면 머리에서 분모를 뺀다**(§4-3 ②) — 머리는 하나인데 패널은 둘이라, 그대로 두면
  **화면이 두 개의 분모를 동시에 주장한다**(M2). `countBlock` 이 이미 쓰는 규칙이다.
- ⚠**통산 패널은 「${season}年のなかだけで数えています」라고 말하지 않는다**(§4-3 ③) —
  대신 보유 범위를 말한다. **뒷문장(「通算」은 아래 通算成績 · 출처 NPB)은 살렸다.**
- **`連続試合無安打` 에는 통산을 안 붙였다**(확정). ⚠**화면이 왜 없는지 말한다** —
  안 말하면 「그 선수에게 그 기록이 없다」로 읽힌다.
- ⚠**「토글이 없다」의 사유가 둘이고 말이 다르다**(M11): 보유 하한 시즌의 화면에서는
  「시즌을 넘는 기록이 없다」가 **우리가 주장할 수 없는 말**이다(그 앞을 안 봤다) —
  그때는 「${season}年より前は当サイトが持っていない」고 적는다. **연도는 박지 않고 유도한다**(⑵).

### 10-6. 성능 — 통산을 시즌마다 부르는 것은 피할 수 없다

⚠**§7 의 「한 번만 부르고 잘라 쓰라」를 그대로는 못 지킨다.** **통산의 끝은 언제나 보고 있는 시즌**이고
(CLAUDE.md §2-2), **결과를 잘라 쓰면 조용히 다른 수가 된다** — 2023년에 끊긴 마루는 2022년 시야에서
`open` 이 되고 **경계 등판이 사라져 이닝의 상한이 달라진다.**
→ **`loadSite` 안에서 한 번씩만** 부른다(선수마다 부르는 O(n²)는 피했다).

| 호출 | 실측 |
|---|---|
| `pitchingStreaks` 통산(2018〜S) 9회 합계 | **16.4초**(2018:266ms → 2026:3,904ms) |
| `pitchingStreaks` 시즌 모드 9회 | 약 1.2초 |
| `careerBattingStreaks` 통산 1회(2018〜2026) | 1,595ms(계획서 §7 실측) |
| 참고 · 변경 전 전체 집계 | **348.7초**(2026-09-07 로컬 9시즌 빌드) |

⚠**보유 하한이 곧 그 시즌이면 통산을 안 훑는다** — 같은 범위라 답이 같고, 그 시즌에는
시즌 넘김 마루가 **원리적으로 없다.**

## 11. 이중 검토 6건의 반영 (2026-09-07 · 같은 날 · 별도 작업)

⚠**전부 「확인된 것」이다** — 여섯 건 모두 **재현하고 나서** 고쳤다.

### 11-1. P1 이적 투수의 기록이 이전 구단 페이지에 떴다 — **M1 위반**

`query.ts` 의 `teamCodeOf` 가 `agg.batting` → `agg.pitching` 순으로 찾아
**타격 구단을 무조건 먼저** 본다. 타자 행에는 맞지만 **투수 행에는 틀리다.**

**실측**(로컬 DB 9시즌 · 하한 5의 투수 행 **272건 중 1건**):
2023 山本拓(`03105136`) — 타격 `d` · **5연속 무실점을 만든 투구 구단 `f`** · `d` 로 실렸다.

⚠**같은 파일 안에 이미 옳은 답이 있었다** — 선수 페이지는 `pitching_line.side` 로
「그때 소속」을 얻고 있었다. **두 경로가 다른 답을 내고 있었다.**
→ **한 벌(`pitchingTeamOn`)로 합쳤다.** 선수 페이지의 준비된 문장을 모듈 수준으로 올리고
`Db` 별 `WeakMap` 캐시를 붙였다(`CAREER_STMTS` 선례).
⚠**못 찾으면 다른 값으로 안 때운다**(M11) — 행을 뺀다.
⚠**타자 행의 구단 배정은 안 건드렸다** — `teamCodeOf` 는 그대로다.

### 11-2. P1 상한 문구가 스스로와 모순됐다

`atRangeStart`(그 앞을 안 봤다)와 `exact=false`(실점 시점을 못 짚는다)가 **같은 마루에 겹치면**
화면이 「**6.2回以上**」 + 「**最大8.2回**」 + 각주 「実際にはもっと長い可能性があります」를 함께 냈다 —
**동시에 참일 수 없다.**

**배포물에서 확인했다**: `dist/2025/players/91495153.html` 의 通算 패널.
실측 분모 — 통산 패널 **460개**(9시즌 · 그 시즌 등판 투수 중 시즌 넘김 마루 보유자) ·
마루 슬롯 **1,134개 중 4슬롯**(고유 마루 1개 · 선수 1명).
⚠**게이트 없이 세면 67슬롯 / 12마루다** — `crossesSeasons` 로 통산 패널이 서는 경우만이 화면이다.
**분모를 밝히지 않으면 두 수 중 어느 쪽도 뜻이 없다.**

→ **숨기지 않고 한정했다**: `保有範囲内では最大8.2回`. 그리고 각주의
「最大までのどこかで必ず成り立ちます」를 **그 겹침이 있을 때만** 「当サイトが持っている範囲のなかでの上限」으로 바꿨다.
⚠**겹치지 않는 마루에서는 단정형 그대로다** — 시험이 양쪽을 다 고정한다.

### 11-3. P1 홈·구단의 표가 분모 3종을 안 냈다 — **M2 위반**

정의서 §1-6 이 **5종 전부에** ⑴훑은 사건 수 ⑵마루 기간 ⑶집계 범위를 요구하는데,
`HomeStreak` 은 `games` 와 `lastGameDate` 만 갖고 있었고 `STREAK_TABLE_NOTE` 에 ③이 없었다.

- `HomeStreak` 에 **`scanned` · `scannedUnit` · `from` · `to`** 를 더했다 —
  ⚠**타입으로 강제한다.** 이제 분모 없는 행은 만들 수 없다.
- `scannedUnit` 이 **타자 `試合` · 투수 `登板`** 이다. 같은 말로 적으면 다른 것을 센 것처럼 읽힌다.
- ③은 각주가 낸다(표가 좁다): `${season}年のレギュラーシーズンのみ` +
  「日本シリーズ…は入れていません」. ⚠**연도를 안 박는다** — 보고 있는 시즌에서 유도한다.
- 계산 계층에 **`Streak.currentFrom` · `currentTo`** 를 더했다.
  ⚠**`bestFrom`/`bestTo` 와 다른 구간이다** — 「지금」과 「최장」은 다른 마루다.
  ⚠**`currentTo` 는 `lastGameDate` 와도 다르다**(9.23(b) 로 건너뛴 경기가 마지막이면 갈린다).
  실측: 홈 표에 실릴 조건의 타자 행 **58건 중 어긋남 0건** — ⚠**「0건」은 「안 일어난다」가 아니다.**
  구조적으로 일어날 수 있어서 **두 필드로 나눠 뒀다**(M11).
- ⚠**`streaks-published.test.ts` 의 대조 구현에도 같은 필드를 더했다** —
  안 더하면 `deepEqual` 이 떨어진다. **두 번째 구현이 계속 독립적이도록 각자 계산하게 뒀다.**

### 11-4. P2 새 라벨이 키보드 툴팁에 안 닿았다

홈·구단의 표만 평문 `termLabel()` 이라 **키보드·터치로 설명을 열 방법이 없었다**
(선수 페이지는 `term()` 버튼이다). 루트 §7.

→ **행과 견출을 한 벌로 모았다**(`STREAK_TABLE_HEAD` · `streakCells` · `streakSpanText` in `home-page.ts`).
⚠**결함이 두 파일에 똑같이 있었던 이유가 「같은 표를 두 번 적었다」였다** — 그래서 고치는 김에 합쳤다.

### 11-5. P2 `shareStreakRows` 가 홀수 상한에서 한 행을 더 냈다

`half = ceil(limit/2)` 를 **양쪽에** 주므로 `limit=5` 에서 3+3 = **6행**이고,
남는 자리 배분이 `spare > 0` 만 봐서 **음수(−1)를 안 되돌렸다.**
⚠**호출 상수가 둘 다 짝수(10)라 화면에서는 발현하지 않았다** — 계약 결함이다.
→ `floor` 로 바꾸고 `Math.max(0, …)` 로 감쌌다. **짝수에서는 한 행도 안 바뀐다.**

### 11-6. P3 계획서의 뮤테이션 수 → §9 참조

**세지 않고 다시 돌렸다.** 9건 전부 다시 심어 다시 잡혔고, 그 과정에서
**계승주자 방어의 1차 방어선이 조건식이 아니라 SQL 이라는 것**이 드러났다(§9).

## 2. 무엇을 만드는가

`.github/workflows/heartbeat.yml` **한 파일.** 다른 것은 **아무것도 안 바꾼다.**

| | |
|---|---|
| 하는 일 | 「최근 24시간 안에 수집이 **한 번이라도 끝까지** 돌았는가」 |
| 아니면 | **exit 1** → GitHub 이 워크플로 실패 메일을 보낸다 |
| 권한 | **`contents: read` + `actions: read`**. ⚠**체크아웃을 한다** — 첫 판이 「안 한다」고 적고 `contents` 를 빼놓아 **체크아웃이 막힐 뻔했다**(이중 검토 F2) |
| 토큰 | 잡 기본 `GITHUB_TOKEN`. **새 토큰 0개** |
| 외부 요청 | **npb.jp 0건**(수집을 하지 않는다) |
| `daily.yml` | **손대지 않는다** |

⚠**복구(자동 재기동)를 하지 않는다.** 3판은 여기에 복구 dispatch 를 넣었고, 콜드 리뷰가
**「그러면 탐지가 수집을 유발해 중복 문제가 되살아난다」**(P1-1)로 잡았다 —
게다가 조회가 `status=completed` 라 **진행 중인 정상 실행이 안 보여** 그 위에 하나 더 얹는다.
→ **알림만 한다. 복구는 사람이 한다**(메일을 보고 `daily.yml` 을 수동 실행).

## 3. 판정 규칙

```
① GET /repos/{repo}/actions/workflows/daily.yml/runs?branch=main&status=completed&per_page=20
② 각 실행에 대해 GET /repos/{repo}/actions/runs/{id}/jobs
③ name == "collect" 이고 conclusion == "success" 이며
   completed_at 이 지금부터 24시간 이내인 것이 하나라도 있으면 → exit 0
④ 없으면 → exit 1
⑤ API 가 답을 못 주면 → exit 1   (모르면 알린다 · 안전한 방향은 「거짓 경보」다)
```

⚠**실행 결론(`conclusion`)을 쓰지 마라.** `decide` 만 성공하고 `collect` 가 `skipped` 여도
실행은 `success` 다 — **우리 이력에 실물이 있다**(2026-09-08 11:35 · `collect: skipped` · `conclusion: success`).

⚠**`created` 가 아니라 `completed_at` 으로 잰다**(콜드 리뷰 P2-4). 묻는 것은 「끝까지 돌았는가」이고
`collect` 는 `timeout-minutes: 45` 다 — 생성 시각으로 재면 **23시간 50분 전에 끝난 성공을
24시간 10분 전에 생성됐다는 이유로 놓쳐** 거짓 경보가 난다.
`completed_at` 은 실행 객체가 아니라 **잡 객체**에 있고, 어차피 잡을 열므로 비용이 0이다.

⚠**`per_page=20` 으로 충분하다** — 하루 실행이 3~6건이다. 20건을 넘겨 24시간이 안 덮이면
**그 자체가 이상**이므로 그때는 **알린다**(모르면 알린다).

## 4. 언제 도는가 — **되돌아보는 창과 검사 주기는 다르다**

```yaml
on:
  schedule: [{ cron: "0 1,7,13,19 * * *" }]   # 6시간마다
  workflow_dispatch:
```

⚠**3판은 「24시간 안에 알린다」고 적었고 거짓이었다**(콜드 리뷰 P1-2).
되돌아보는 창(24h)과 **검사 주기**가 곱해진다 — 하루 한 번이면 **최악 약 48시간**이다
(리뷰어 반례: 마지막 성공 23:45 → 다음날 검사 통과 → **그다음 날에야 경보** = 32시간 14분).

**6시간 주기로 하면**: 마지막 성공 후 **30시간**(24h 창 + 6h 주기)에 알린다.
⚠**그 30시간은 「최악」이 아니라 「하한」이다**(이중 검토 F7). 크론이 정시에 뜬다는 가정 위에 서고,
**같은 문서 부록 A-1 이 이 저장소 스케줄 지연을 81~385분으로 실측**했다 —
지연을 얹으면 **약 36시간**, 한 회 탈락하면 **약 42시간**이다. **둘을 같은 수로 쓰지 마라.**
⚠**그 이하로는 못 줄인다** — 창이 24시간이기 때문이다. **주기를 줄여도 24시간이 바닥이다.**

⚠**하트비트 자신도 `schedule` 이라 늦거나 탈락할 수 있다**(§1 의 그 성질). 그러면 알림이 더 늦는다.
**받아들인다** — 이건 주 경로가 아니라 그물이고, **늦은 그물도 없는 그물보다 낫다.**
⚠**6시간 주기라 한 번 탈락해도 다음이 6시간 뒤다** — 하루 한 번짜리보다 이 점에서도 낫다.

## 부록 A. ⚠외부 크론(지연 개선)을 **지금은 안 하기로 했다** — 실측과 사유

### A-1. 지연은 전부 「실행 생성」 단계다 (실측 · 실행 22건)

| 구간 | 스케줄(n=12) | 수동(n=10) |
|---|---|---|
| 크론 예정 → **실행 생성** | **81 ~ 385분**(중앙 **184.5**) | — |
| 실행 생성 → 첫 잡 시작 | **2 ~ 8초**(예외 1건 254초) | **3 ~ 7초** |

**러너는 즉시 붙는다.** 우리 자원 문제가 아니다. GitHub 문서가 사양으로 적는다:
「고부하 시 지연될 수 있다」 · **「부하가 충분히 높으면 큐에 든 잡이 버려질 수 있다」**.

슬롯별(각 **n=2** · UTC · ⚠**상수로 쓰지 마라**):
06:30→345 · 05:00→274 · 14:30→210 · 16:00→158 · 23:30→104 · 22:00→96(분).
⚠**GitHub 의 조언(「정시를 피해 다른 분에」)은 우리 데이터로 성립하지 않는다** —
최악이 `:30`, 최선이 `:00` 이다. **분이 아니라 시각대**가 설명한다.

### A-2. 그런데 실해가 아직 0이다

- **데이터 손실 0건.** 予告先発 취득 창이 **약 24시간**(페이지가 하루치만 게시 · **13시 무렵** 전환)이라
  최대 385분 지연으로도 슬롯이 전부 창 안에 들어온다.
- 확인된 실해는 **거짓 경보로 배포 1회 차단**뿐이고, 그건 **2026-09-09 에 다른 수정**
  (공표표 기준일을 읽게 한 것)으로 닫혔다.
- ⚠**「탈락」은 실재하는 위험이고 아직 안 났을 뿐이다.** 관측 창에서 12/12 가 전부 떴다.

### A-3. 외부 크론 안이 왜 접혔는가

Cloudflare Worker 의 Cron Trigger 가 `workflow_dispatch` 를 부르면 지연이 사라진다
(**수동 실행은 3~7초에 시작한다**). 그런데 콜드 리뷰 3라운드가 수렴하지 않았다:

| 판 | 발견 | 무너진 것 |
|---|---|---|
| 1판 | **17건** | 백스톱이 자기 억제된다는 주장이 **거짓**(내 문서의 지연 수치로 반증됨) |
| 2판 | **14건** | 「신선도 띠가 그물」이 **거짓**(§1) · 역순 중복 · 롤백 범위 |
| 3판 | **8건** | 복구 dispatch 가 있으니 **중복 문제가 안 사라짐** · 「24시간 안에 알린다」가 **거짓**(최악 48h) |

⚠**세 판 모두 「내가 그물이라고 적은 것이 그물이 아니었다」가 P1 이었다.**

리뷰어의 판정: **정지 탐지만이 목표라면 전체 구성은 과하다** —
`heartbeat.yml` 하나로 되고 **외부 PAT 가 필요 없다**. 부품을 셋(Worker · PAT · `daily.yml` 개조) 없앨 수 있다.

### A-4. 다시 열 조건

1. **탐지가 붙은 뒤** 「실제로 며칠에 한 번 못 도는가」를 세어 본다 — **지금은 그 수를 모른 채 논하고 있었다.**
2. 그 수가 의미 있게 크거나 **탈락이 실제로 관측되면**, 그때 부록의 3판 설계를 꺼내
   **P1 둘**(복구 dispatch 의 중복 · 탐지 지연)부터 닫는다.
3. 값싼 완화가 하나 있다: **슬롯을 22:00·23:30 UTC 대역으로 옮기면 274·345분 → 96·104분**이다
   (`daily.yml` 한 곳 · 새 부품 0개). ⚠**슬롯당 n=2 위에 서는 값이라 언제든 뒤집힐 수 있다.**

### A-5. 그때 반드시 읽을 것 (콜드 리뷰가 잡은 함정)

- `controller.cron` 을 쓰면 시각→슬롯 추론이 필요 없다. **결합 표현식(`0 5,16,22 * * *`)을 쓰면 그 이점이 사라진다.**
- `workflow_dispatch` 는 `github.event.schedule` 이 **비어 있다** → `decide` 의 재시도 억제가 통째로 죽어
  **수집이 하루 3회 → 6회**가 된다. 소비 지점이 `daily.yml` **140 · 159 · 162 · 170행**이다.
- `Actions: write` 는 `Contents: write` 의 **부분집합이 아니다** — 워크플로 **비활성화**와 **실행 삭제**가 된다.
  고르는 이유는 「더 좁아서」가 아니라 **「워크플로 정의를 못 바꿔서」**다.
  저장소 시크릿 목록 조회는 **`Secrets: read`** 다.
- `concurrency` 는 **대기 실행을 하나만 두고 새 대기가 기존 대기를 취소**한다 — 「직렬화만」이 아니다.
- 실측 분모에 **예정 회차**를 넣어야 **탈락**이 보인다. 실행 목록만 세면 탈락은 안 보인다.

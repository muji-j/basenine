## 2. 무엇을 고르지 않았는가

### ✖ 날짜 페이지(`days/<date>.html`)에 합친다

절감은 더 크다(−7,397 → 총 8,047장 = 40.2% · 약 6.9시즌). **그런데 전제가 안 선다.**

실측: 경기 날짜 **1,531개 중 105개에 날짜 페이지가 없다**(그 날짜의 경기 **151장**).
빠지는 이유가 **두 가지**다 —

1. **포스트시즌**(시즌당 12~16일). `data.days` 자체가 정규시즌 경계로 만들어진다
2. **최신 경기일**. `pastDays()` 가 일부러 뺀다 — 그 날은 `today.html` 이 맡는다

⚠**그대로 옮겼으면 그 151장이 조용히 404 가 됐다.**
1번을 메우려면 날짜 페이지가 대회를 섞어야 하고, 그건 **§2-1 의 대회 경계**를 건드린다.
「섞어서 집계하지 마라」가 목록에까지 미치는지는 별도 판단이 필요하고, **이 변경의 값에 비해 크다.**

### ✖ 월별로 묶는다(`games/<YYYY-MM>.html`)

파일은 **약 81장**까지 줄지만 한 장이 **약 2.9 MiB**(150경기)가 된다. 못 쓴다.

### ✖ 선수 페이지를 샤드로 묶는다

6,207장(40.2%)으로 두 번째로 크지만, **선수 페이지는 이 제품의 착지점**이다(§0-1 「3클릭 이내」).
URL 이 바뀌면 잃는 것이 파일 수보다 크다.

## 3. 고른 것 — `games/<date>.html` + 앵커

경기 하나에 파일 하나 대신, **경기일 하나에 파일 하나**를 낸다.
그 안에 그 날 경기가 `id="g-<slug>"` 섹션으로 들어간다.

```
전:  games/2026-0814-s-db-17.html
후:  games/2026-08-14.html#g-2026-0814-s-db-17
```

| | |
|---|---|
| 파일 | 7,502 → **1,531** (**−5,971**) |
| 배포물 | 15,444 → **9,473 = 47.4%** |
| 여유 | 2.61시즌 → **약 6.0시즌** |
| 날짜당 경기 | 중앙 **6** · 최대 **6** |

**왜 이쪽인가**: 파일을 **경기 자신에게서** 만들므로 포스트시즌도 최신일도 **자연히 덮인다.**
대회 경계를 건드리지 않고, 날짜 페이지는 지금의 가벼운 개요 그대로 남는다.

## 4. 링크와 파일이 갈리지 않게 하는 법

⚠**이 변경의 유일한 위험은 「링크가 가리키는 날짜」와 「파일이 그리는 날짜」가 갈리는 것**이다.
갈리면 나는 것은 오류가 아니라 **404** 이고, 그건 조용하다 —
`gameSlug()` 의 주석이 원래 경고하던 바로 그것이다.

```
gameDayPath(date)              -> "games/2026-08-14.html"
gameAnchor(gameId)             -> "g-2026-0814-s-db-17"
gamePath(gameDate, gameId)     -> "games/2026-08-14.html#g-2026-0814-s-db-17"
```

**날짜는 `gameDate` 를 넘긴다** — 실재하는 필드다.
⚠**한때 슬러그에서 유도했다가 되돌렸다**(§7). 유도는 npb.jp 의 ID 형식이 영원하다고 가정하고,
형식이 다르면 **그리는 중에 던져서** 그 화면이 통째로 안 나온다.

⚠**그래서 「갈릴 수 있다」가 남는다.** 막는 것은 **링크 검사**다 —
빌드가 만들어진 파일에 대해 **앵커까지 포함해** 전 링크를 확인하고, 어긋나면 멈춘다.
날짜를 잘못 넘기면 죽은 링크가 되고 **빌드가 거기서 선다**(실측: 전 시즌 **9,370장 · 깨진 것 0**).

⚠**앞선 준비 커밋에서 경로를 이미 한 벌로 모았다**(`gamePath`) — 그때 링크 5곳과
**파일을 쓰는 곳 1곳**이 각자 조립하고 있었고, 마지막 하나는 새로 만든 시험이 잡았다.
그 덕분에 이 변경은 **그 한 함수와 호출부의 날짜 인자**에서 일어난다.

## 5. 화면에서 바뀌는 것

- 경기 상세의 제목이 `<h1>` → `<h2>` 가 된다(한 문서에 경기가 여럿이므로). **위계는 유지한다.**
- 「この試合の記録について」 각주는 **한 장에 한 번**만 낸다(지금은 경기마다 한 번).
- **원본 링크(L3)는 경기마다 그대로** 둔다 — 가리키는 대상이 경기별로 다르다.
- 페이지 색은 승자 구단색 → **중립**(한 장에 경기가 여럿이라 하나를 고를 수 없다).

⚠**「経過を転載しない」 경계는 그대로다**(L2). 담는 내용이 늘지 않고 **묶는 단위만** 바뀐다.

## 7. ⚠설계 중에 한 번 되돌린 것

처음에는 **날짜를 슬러그에서 유도**했다(`gameDayOf`). 호출부를 하나도 안 고쳐도 되니까.
**되돌렸다** — 유도는 ⑴ npb.jp 의 ID 형식이 영원하다고 가정하고, ⑵ 형식이 다르면
**그리는 중에 던져서** 그 화면이 통째로 안 나온다.
실제로 그 판을 만들자 **픽스처의 `gameId: "g1"` 에서 시험 32본이 한꺼번에 무너졌다** —
데이터가 틀린 게 아니라 **형식 가정이 깨진 것**이다.

지금은 `gameDate` 를 넘긴다(실재하는 필드). ⚠**그래서 「링크와 파일이 갈릴 수 있다」가 남는데,
막는 것은 링크 검사다** — 빌드가 앵커까지 포함해 전 링크를 확인하고 어긋나면 멈춘다.

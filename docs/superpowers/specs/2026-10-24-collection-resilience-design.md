## 4. 설계

### D1. 실패 분류 — `UpstreamError` 한 타입, 만드는 곳 한 곳(fetcher)

`packages/archiver/src/upstream.ts`(신규 · import 0개): `UpstreamError{ kind, url, attempts[], status }`, `FetchLocalError`, `ScheduleAbsentError`, `EXIT_UPSTREAM_ONLY = 75` · `EXIT_UPSTREAM_CIRCUIT_OPEN = 69` · `EXIT_LOCAL_CIRCUIT_OPEN = 70`, `isUpstreamCause(err)`, `exitCodeFor(results, circuitOpen)`.
**호출자는 `UpstreamError` 를 만들지도 세지도 않는다** — `fetcher.getUnqueued` 가 터미널 비성공을 **던지고**(재시도 루프 밖에서) 회로 계수도 그 자리 한 곳이다.

| 상황 | fetcher 결과 | 회로(프로세스 안) | `errorKind` |
|---|---|---|---|
| 2xx · 304 | 응답 반환 | 연속 소진 리셋 | — |
| **404 · 410** | 응답 반환(사실 · 지금처럼) | 리셋 | — |
| **`RETRYABLE`**(408·425·429·500·502·503·504) / 알려진 네트워크 코드·타임아웃(아래 ⑶) / 2xx 헤더 뒤 본문 끊김 | 재시도(최대 3회) 후 소진 시 `UpstreamError` | 연속 +1 · 합계 +1 | upstream |
| 3xx 종결(타 출처 · 읽을 수 없는 `Location` · 홉 > 3) | `UpstreamError(http-<3xx>)` 즉시 | 연속 +1 · 합계 +1 | upstream |
| **그 밖의 모든 4xx·5xx**(400·405·401·403·451·501…, 404·410·재시도 집합 제외) | `UpstreamError(http-<status>)` 즉시(재시도 없음) | 연속 +1 · 합계 +1(**401·403·451 도 같다 — 즉시 열림 없음** · 3중 검토 반영) | upstream |
| 회로 열림 | `UpstreamError(circuit-open)` — 요청 0 | 불변 | upstream |
| **응답 없는 로컬 고장**(cause 없는 `TypeError`/`RangeError` · 헤더 검증 · `ERR_INVALID_URL` · `UND_ERR_INVALID_ARG` · 목록 밖 코드) | `FetchLocalError` 즉시(재시도 0) | **세지 않는다** | **local** |
| `readMeta`/쓰기 예외 · `discoverGames` 구조 예외 · 현재 달 `ScheduleAbsentError` | (fetcher 밖) | — | **local** |

- **상류인가(`isUpstreamCause` · 닫힌 목록 한 곳 — 3중 검토 반영)**: 응답 없는 예외는 원인 사슬(오류 → `cause` → `AggregateError` 의 첫 원소)에 아래 코드가 있거나 `DOMException` 이 `TimeoutError`·`AbortError`(정정 경로의 `AbortSignal.timeout`)일 때만 상류다. 그 밖은 로컬 오류 — **모르면 막는 쪽**(I4)이다: 상류로 잘못 보면 배포가 열리고, 로컬로 잘못 보면 한 실행이 막힐 뿐이다. ⚠`UND_ERR_*` 를 통째로 넣지 않는다(`UND_ERR_INVALID_ARG`·`UND_ERR_CLOSED`·`UND_ERR_DESTROYED` 등은 우리 쪽 고장) · 인증서 오류(`CERT_*`·`ERR_TLS_*`)도 넣지 않는다(가로채기일 수 있다).
  목록: `UND_ERR_CONNECT_TIMEOUT` · `UND_ERR_HEADERS_TIMEOUT` · `UND_ERR_BODY_TIMEOUT` · `UND_ERR_SOCKET` · `UND_ERR_HEADERS_OVERFLOW` · `UND_ERR_RES_CONTENT_LENGTH_MISMATCH` · `ECONNRESET` · `ECONNREFUSED` · `ECONNABORTED` · `ENOTFOUND` · `EAI_AGAIN` · `EAI_FAIL` · `ETIMEDOUT` · `EPIPE` · `EHOSTUNREACH` · `ENETUNREACH` · `EHOSTDOWN` · `ENETDOWN` · `EPROTO` · 앞머리 `ERR_SSL_*`.
- **`kind` 매핑(순수 함수 `classifyFetchCause` · 상류인 것만 · 위에서부터 처음 맞는 것)**: ⑴ HTTP 응답이 있었다 → `http-<status>` ⑵ 오류(또는 `cause`, `AggregateError` 면 `errors[0]`)의 `code` 가 아래 표에 있다 → 그 kind ⑶ 그 밖의 **상류(위 목록)** → `network`(`code`/`name` 은 그대로 기록). ~~⑶ 그 밖 → `network`~~ 는 3중 검토에서 바꿨다 — 그 규칙이 연락처의 CR/LF(헤더 검증 `TypeError`)를 4번 재시도한 뒤 75(배포)로 만들었다. 평소 경로는 `AbortSignal` 을 쓰지 않으므로 시간 초과는 undici 코드로 온다(D3).

| `code` | kind |
|---|---|
| `UND_ERR_CONNECT_TIMEOUT` | `connect-timeout` |
| `UND_ERR_HEADERS_TIMEOUT` | `headers-timeout` |
| `UND_ERR_BODY_TIMEOUT` | `body-timeout` |
| 위 목록의 그 밖(`ECONNRESET` · `ECONNREFUSED` · `UND_ERR_SOCKET` · `ERR_SSL_*` …) · `DOMException` 의 `TimeoutError`·`AbortError` | `network` |

- **연락처 검사(`buildUserAgent`)**: 제어 문자(C0 · DEL · C1 — CR·LF·TAB 포함)와 latin1 밖 문자(0xFF 초과)를 거부한다 — 받기 자식 셋은 fetcher 를 만들기 전에 부르므로 **요청 0 · 종료 2**. 거부 메시지는 연락처를 되찍지 않는다(위치만).
- 호출자 판정은 `instanceof UpstreamError` 하나다: `prepareUrl`·`players.ts`·`starters.ts` 의 바깥 `catch` 는 받기와 쓰기를 같이 덮으므로 `UpstreamError` 만 `upstream`, 나머지(`FetchLocalError` 포함)는 `local`. `PageResult`·`DayError` 에 `errorKind` 를 더한다. 호출자의 `res.body === null` 갈래(2xx/304 가 아닌 것은 도달 불가)는 방어용 `local`.
- `MonthlyScheduleCache.load` 는 404/410 에서 `ScheduleAbsentError` 를 던진다(회로는 fetcher 가 이미 성공으로 셌다).
- **종료 코드 `exitCodeFor(results, circuitOpen)` — 회로가 열렸는가로 가른다**(3중 검토 반영): 실패 0건 → 0 · 실패가 있고 **전부 `upstream`** → 회로 닫힘 **75** / 열림 **69** · 하나라도 `local`/미분류 → 닫힘 **1** / 열림 **70**. 던져서 끝나는 local(사이드카를 못 읽음 등)도 진입 함수가 잡아 회로 상태로 1/70 을 고른다. 부모가 이 코드로 뒤 받기를 정한다(D4). **75·69·70 계약은 `update.ts` 가 spawn 하는 받기 자식 세 개(`cli.ts` · `cli-players.ts` · `cli-starters.ts`) 뿐**이고 `update.ts` 자신은 0/75/1 만 낸다. `cli-stats.ts`(`continue-on-error` 단계) · `cli-draft.ts` · `cli-draft-wiki.ts`(사람이 연 1회 로컬) · `cli-games.ts`(정정 경로 — `FetchResult.exit`·`readFetchResult`·`stepExitCode` 가 `0|1` 계약이다)는 **0/1 그대로**이고 메시지(D2)·회로(D4)만 공통으로 받는다.
- **다음 달 일정**(`cli.ts` 끝의 best-effort 취득): `UpstreamError` 는 **upstream 실패로 세어 75 에 포함**한다(조용히 녹색이 되지 않게 · 3차-3). `ScheduleAbsentError`(404/410)는 꼬리표 「（오프시즌이면 정상）」만 붙이고 종료 코드 무영향. 그 밖의 예외는 지금처럼 경고만(무영향 · 현행 유지).

### D2. 원인 기록 — 소진 메시지를 결정적으로

`취득 실패 (재시도 N회 소진): <url> — 마지막 원인 <kind>[<code|status>] <detail> · 시도 1:<code|status> <ms>ms 2:<…> …`
- 앞 구절 `취득 실패 (재시도 N회 소진)` 는 글자까지 유지(검색 호환).
- `<code|status>` = HTTP 상태, 아니면 `err.code ?? cause.code ?? cause.errors?.[0]?.code ?? err.name`(`AggregateError` 는 첫 원소). `<detail>` = 마지막 원인의 `message` 앞 120자(undici `ConnectTimeoutError` 메시지가 `attempted address:… timeout: …ms` 를 싣는다 — 시험이 이 메시지에서 주소가 나오는지 고정). `<ms>` = 그 시도의 경과.
- **길이 규칙(결정적 · 단위는 JS `string.length`)**: `<url>` 은 120자를 넘으면 앞 119자 + `…`, `<detail>` 도 120자 상한. 앞부분(`…<detail>`)의 최악은 약 35 + 120 + 50 + 120 ≈ 330자라 **마지막 원인은 항상 397자 안에 든다.** 시도 항목은 앞에서부터 전부 붙이고, **조립한 전체가 400자를 넘으면 397자에서 자르고 `…` 를 붙인다**(시도 목록의 꼬리만 잘린다).
- `cause` 는 그대로 붙인다. 6개 호출자는 `err.message` 를 찍으므로 코드 변경 0.
- **로컬 오류의 메시지**(3중 검토 반영): `로컬 오류 (재시도 없음 · 상류 실패 아님): <url> — <code> <detail>` — `취득 실패 (` 로 시작하지 않는다(그 앞 구절은 상류 실패의 검색어다) · 400자 규칙은 같다 · `cause` 는 **붙이지 않는다**(헤더 검증 오류는 UA 를 품는다).
- **UA·연락처를 지운다**(3중 검토 ③ · 방어): 상류 원인의 `<detail>` 과 로컬 오류의 한 줄에서, 공백 정리·자르기 **전에** UA 를 `<User-Agent>` 로 · 연락처를 `<연락처>` 로 바꾼다(`redactSecrets`). undici 의 헤더 검증 오류는 헤더 값을 메시지에 싣는다.
- 빼는 것(§9): server 헤더 · phase 분류 · DNS 조회 · family · 성공 요청 연결 계측.

### D3. 시간 상한 — 홉마다 연결 30 · 헤더 30 · 본문 유휴 30초

`PoliteFetcher` 기본 `fetchImpl` 만 바꾼다(주입된 것은 그대로): `undici` 의 `fetch` + `Agent({ connect:{timeout:30_000}, headersTimeout:30_000, bodyTimeout:30_000, connections:1 })`. `@bb-app/archiver` 가 `undici@7.29.0` 을 정확히 같은 버전으로 직접 의존한다(락의 `package-lock.json:1598` 에 이미 있다 · 새 tarball 0 · `dev` 플래그만 바뀐다).
- **상한은 홉마다 undici 옵션뿐이다**(4차-1 — 이전 판의 「시도 전체 90초 단일 `AbortSignal`」은 폐기: 홉 사이 슬롯 대기를 신호 밖에 두면서 전체를 90초로 검사하는 것이 양립하지 않았다). 우리는 `AbortSignal` 을 쓰지 않으므로 시간 초과는 전부 undici 오류 코드(`UND_ERR_CONNECT_/HEADERS_/BODY_TIMEOUT`)로 오고 단계가 코드에 담긴다.
- **한 시도(재시도 루프의 한 바퀴)의 최악** = `H × (연결 30 + 헤더 30 + 본문 유휴 30) + H × 슬롯 3`, `H = 1 + MAX_REDIRECTS = 4` → `4×90 + 12 = 372초`(상계 — 리디렉션 홉은 본문을 읽지 않으므로 실제 상계는 이보다 작다). URL 하나(4시도 + 백오프 3+6+12+24 = 45)의 최악 = `4×372 + 45 = 1,533초`.

| B 연결 성공 뒤 무응답 | 30+30 = 60 | 4×60+45 = 285초 | 14.3분 | 16.9분 | 예 |

- **가설을 가르는 법과 그 한계** (D5 로그 `시도 n:<code> <ms>ms` 로 읽는다 · diagnostics 계측은 뺐다):

| 로그 | 읽는 법 |
|---|---|
| 모든 시도가 `UND_ERR_CONNECT_TIMEOUT` · 약 30,0xx ms · 성공 0 | **H1(SYN 폐기)** 쪽. 연결 30초 안에 응답이 없다 |
| 장애가 풀렸다(성공이 돌아옴) — 한도 상향 뒤 | **H2(수락 지연)와 정합할 뿐 입증은 아니다**(4차-7) — 「timeout 상향 후 회복했으나 계층 미확정」. 같은 시각의 우연한 회복·경로 복구와 구별하지 못한다. 성공한 연결의 시간은 소진 메시지가 없어 못 본다 — 프로세스의 첫 성공 `get` 의 헤더까지 ms 를 CLI 합계 줄에 한 번 찍는다(새 연결+TTFB 합 — 연결만 가르지 못한다). **accept 지연이라는 단정은 연결 단계 시간을 따로 재거나 통제된 동일 조건 비교가 있을 때만**(§9 의 diagnostics 계측) |
| `http-403`·`http-429`·`http-503` 등 | H3(HTTP 계층 거절) · 연결은 즉시 성공 |
| 즉시(<1초) `ECONNRESET`·`ENOTFOUND`·`EPROTO` | H4(RST·DNS·TLS) |

⚠**못 가르는 것**: H1 이 「러너 대역만 막힘」인지 「경로 장애」인지 · H2 에서 10~29초 구간의 분포. 더 가르려면 추가 요청이 필요하고 사용자 결정 ①이 막는다. 의도적 차단 정황(403/429/451 + 차단 본문, 또는 30초 소진이 정시 3회·24시간 연속 + 성공 0이고 사용자 PC 는 성공)이 보이면 **우회하지 않는다** — 프록시·UA 위장·다른 이그레스 금지, 사용자와 상의(L4: 확정은 사용자가 한다). 요청을 완전히 멈추는 스위치는 §9.

### D4. 회로 차단 — 상태 파일 없이, 프로세스 안 + 부모의 중단

1. **자식 안(프로세스 단위)**: `HostCircuit`(`circuit.ts` 신규 · 시계 주입). 연속 소진 **N**(정시·수동 3, 재시도 슬롯 1 — 워크플로가 env `BB_NPB_CIRCUIT_N` 으로 준다) **또는** 합계 소진 6 이면 열려 남은 `get()` 이 요청 0 으로 `circuit-open`. **404·410 을 뺀 모든 비성공은 연속 +1 · 합계 +1 로 센다**(4차-2) — ~~401·403·451 은 즉시 열림~~ 은 **없앴다**(3중 검토 2차 F1): 한 페이지만의 거절(자원 단위)이 형제 받기를 막았다. 의도적 차단이면 모든 페이지가 같은 응답이라 연속 3(재시도 슬롯 1)에서 곧 열린다. 로컬 오류(`FetchLocalError`)는 세지 않는다. 성공(404·410 포함)은 연속 카운터를 리셋. 자식은 끝까지 돌고 종료 코드는 `exitCodeFor(results, 회로 열림?)` — 0 / 75·69 / 1·70(D1).
2. **부모(`update.ts` → `collect-steps.ts`) — 닫힌 표**(3중 검토 반영 · 2차 F1 · 3차 ①):

| 그 밖(2 · 신호 · 종료 코드 없음 · spawn 실패) | 모름 | **멈춤**(요청에 대해 닫힌 쪽) | blocking |

   멈춘 뒤의 받기 자식은 띄우지 않고 합성 step 으로 남긴다 — 회로 열림(69·70)이면 종료 69(상류 · 로그 `상류 실패 — 이후 받기 건너뜀 <단계>`) · 모름이면 종료 1(blocking · `모르는 종료 — 이후 받기 건너뜀`). 로컬 자식(적재 · emit · freshness)은 **계속 돈다**. 뒤 받기를 정할 때는 **정규화 전의 종료**를 본다(신호로 죽은 자식을 1 = 「계속」으로 읽지 않는다).
   ⚠⚠**닫힌 채 실패한 자식(75·1) 뒤의 받기 자식은 `BB_NPB_CIRCUIT_N=1` 로 띄운다** — 표만으로는 자식마다 회로가 새로 서서 「닫힌 채 소진 5」를 자식마다 되풀이할 수 있다(전면 장애 · 날짜 2개면 예고 1 + 날짜 2 + 2 + 선수 3 = 소진 8). 3중 검토가 요구한 상한(아래 3)을 성립시키려고 더했다. `update.ts` 자신은 **0 / 75 / 1** 만 낸다(69 는 판정에서 75 와 같다 · 워크플로 계약 불변).
3. **상한 논증(혼합 실패 포함)**: 받기 자식을 차례로 c₁…cₖ, 처음 0 이 아닌 종료로 끝난 자식을 cⱼ 라 하자. cⱼ 앞의 자식은 0(실패 없음 → 소진 0). cⱼ 가 **열린 채**(69·70) 끝났으면 cⱼ 안의 소진 ≤ 6(연속 N 이나 합계 6 에서 열리고 그 뒤 요청 0) → 부모가 멈춘다. cⱼ 가 **닫힌 채**(75·1) 끝났으면 cⱼ 안 ≤ 5(합계 6 이면 열렸을 것이다) · 그 뒤 자식은 연속 한도 1 이라 처음 소진하는 자식이 ≤ 1 로 열려 69·70 → 멈춘다. 모르는 종료면 그 자리에서 멈춘다. 던져서 끝나는 local 도 진입 함수가 회로 상태로 1/70 을 고르므로 「열린 채 1」은 없다. → **실행 전체 소진(`UpstreamError` 로 끝난 `get()`) ≤ 6 · 걸쇠(30분)가 자식을 죽이면 그때 진행 중이던 `get()` 하나(≤ 4시도)가 더해질 수 있다.** 요청 수는 `get()` 하나당 소진 유형별로 다르다: 재시도 대상은 ≤ 4시도(× 홉), 비재시도 4xx·5xx·3xx 종결은 1시도 — 아래 시도 수는 **재시도 대상(관측형 A)** 기준이다. 시간은 D3 표.
4. **받기 순서**: 예고(予告先発)를 **맨 앞**으로 옮긴다 — 거르면 영영 못 받는 유일한 요청이고, 경기 단계에서 회로가 열리면 부모가 멈춰 받을 수 있던 예고를 건너뛴다. 정상일 때는 로그 순서만 바뀐다.
5. **날짜별 spawn 은 그대로 둔다**(`--dates` 묶음은 §9). 첫 날짜 자식에서 회로가 열리면(69·70) 부모가 나머지 날짜 자식을 안 띄우고, 닫힌 채 실패하면 나머지는 연속 한도 1 로 떠서 첫 소진에 멈추므로 같은 URL 의 반복은 사라진다.
6. **받기 자식 경계의 L1 간격**(3중 검토 3차 ②): 자식마다 `PoliteFetcher` 가 새로 서서 **각 자식의 첫 요청은 기다리지 않는다** — 예고 자식의 마지막 요청과 경기 자식의 첫 요청이 붙을 수 있었다. 부모가 **둘째 받기 자식부터** 띄우기 전에 `--delay`(기본 3000ms)만큼 동기로 잔다(`collect-steps.ts` 의 `blockingSleep` = `Atomics.wait` · 주입 가능 · 첫 받기 자식과 로컬 자식 앞에서는 안 잔다). `update.ts` 는 `--delay` 를 `l1.ts` 의 술어로 먼저 검사한다(틀리면 자식 0 · 종료 2). 요청 수는 안 는다.

**요청량(분모)**: 지금 `40044974431` **56시도**(14 URL) → **연속 장애 정시 ≤ 8시도**(예고 1 URL × 4 → 75 · 닫힘 → 첫 날짜 자식이 연속 한도 1 로 월간 일정 1 URL × 4 → 열림 → 69 → 멈춤) · 재시도 슬롯 ≤ **4시도**(예고에서 바로 열림). **자동 예약 6실행(정시 3 + 재시도 슬롯 3)만 센 하루** = 3×8 + 3×4 = **36시도**(이전 판의 상한 48 안). ⚠5판 구현(「75 면 이후 받기 중단」)은 정시 4시도였다 — 75 가 뒤 받기를 멈추지 않게 바꾼 대가가 정시 실행마다 +4시도다. **간헐 장애의 최악**은 실행마다 소진 6 = 24시도(정시) · 1 = 4시도(재시도 슬롯)라 하루 3×24 + 3×4 = 84시도로 5판과 같다. 수동 실행·「실패한 잡 다시 실행」은 실행마다 따로 더해진다(하루 전체 상한이 아니다 · 프로세스 간 공유 카운터가 없다 — §9 상태 파일). 받기 시간은 22분 5초 → 연결 단절형 연속 장애 ≈ 5.6분(165초 × 2 + 간격 3초).

### D5. 배포 정책 — `update.ts` 종료 0 / 75 / 1

`scripts/run-verdict.ts`(신규 · 순수 · 시계/I/O 없음) `classifyRun(steps, freshReasons)`. 모든 자식 실행은 `execStep(id, group, args)` 한 헬퍼로 모은다 — 기준 `update.ts` 는 `run()` 밖에서 직접 `spawnSync` 가 셋(`emit-stale-player-ids` · `emit-player-ids` · `freshness`)이라 구현이 `failures` 만 지우면 emit 실패가 판정에서 사라진다. `status===null`·signal·시간 제한은 1 로 정규화.

| 규칙 | 조건 | 결과 |
|---|---|---|
| R1 | `group ∈ {load, emit}` 이고 `exit ≠ 0` | blocking |
| R2 | `group = fetch` 이고 `exit ∉ {0, 75, 69}`(1 · 70 · 2 · 신호 → 1 · 모르는 종료로 건너뛴 합성 step) | blocking |
| R3 | `group = fetch` 이고 `exit ∈ {75, 69}`(회로 열림으로 건너뛴 합성 step 포함) | upstream |
| R4 | `group = freshness`: `exit = 0` → 파일 불필요(무시) · `exit ≠ 0` → 아래 「사유 파일 계약」으로 읽는다: 읽기 실패 → blocking · **`no-games` 포함 → blocking** · 그 밖: **사유마다 그 갈래(아래 표)의 받기 step 이 상류(R3)면 explained** · 하나라도 아니면 그 실행의 사유 전부 blocking(3중 검토 1차 P3-3 — ~~upstream 이 1건 이상이면 explained~~ 는 선수 페이지 하나의 소진이 경기 누락을 덮었다) | |
| R5 | blocking ≥ 1 → **1** · 아니면 upstream ∪ explained ≥ 1 → **75** · 아니면 **0** | |

**사유 파일 계약**(4차-3): `freshness.ts --reasons-out <path>`(`update.ts` 가 `data/freshness-reasons.json` 으로 부른다). 스키마 `{"schema":1,"exit":<0|1>,"reasons":["career-lag",…]}` — 키는 `@bb-app/domain` 의 `STALE_REASON_KEYS` allow-list. **쓰는 쪽**: 종료 **직전**에 `<path>.tmp-<pid>` 로 쓰고 `rename`(원자적) — 정상(`exit:0`)일 때도 빈 `reasons` 로 쓴다. 쓰기 실패는 stderr 한 줄 + 종료 코드 **2**(1 이 아님 → 읽는 쪽에서 blocking). **읽는 쪽(`update.ts`)**: spawn **전에** 파일을 지우고(이전 실행의 것을 읽지 않는다), 끝난 뒤 — `exit 0` 이면 파일을 안 본다 · `exit 1` 인데 파일 없음/JSON 깨짐/`schema≠1`/파일의 `exit≠1`/allow-list 밖 키/`reasons` 가 비어 있음 → **blocking(로컬 실패)** · 유효하면 중복을 제거하고 아래 사유 표로 분류 · `exit ∉ {0,1}`(예: 2 = 표 없음) → 파일과 무관하게 blocking.

**신선도 사유 → 「상류 장애로 설명되는가」 (표 하나로 닫는다 · `run-verdict.ts` 의 `REASON_AREA` · 그 갈래의 받기가 같은 실행에서 상류 실패일 때만)**

받기 step 의 갈래(`StepRecord.area`)는 `update.ts` 가 단다: 予告先発 아카이브 → `starters` · 경기 아카이브 <날짜> → `games` · 낡은 선수 프로필 재취득 · 신규 선수 프로필 → `players`. 갈래 없는 받기의 상류 실패는 아무 사유도 설명하지 않는다(모르면 막는다).

| 사유 | 갈래 | 설명되나 | 이유 |
|---|---|---|---|
| `starters-behind` · `starters-lag` | 予告先発 | 예 | 예고 취득이 실패했다 — 직접 결과 |
| `game-missed` | 경기 | 예 | 월간 일정/박스 취득 실패의 결과(증거는 장애 중엔 맹목이기도 하다) |
| `career-lag` | 선수 | 예 | 선수 페이지 취득 실패의 직접 결과. ⚠**조정자 지시(`career-lag` 등은 blocking)에서 벗어난다** — 이것을 blocking 으로 두면 경기가 이어지는 시즌 중 장애에서 4일 뒤부터 배포가 다시 막혀 사용자 결정 ②(받기 실패면 배포)를 깬다. 그 갈래에 상류 실패 **없이** 울면 blocking 이라 PR-1 이 고친 헛경보 유형은 여전히 막힌다 |
| `game-lag`(백스톱 45/200일) | 경기 | 예 | 장기 장애의 끝 단계 — 그래도 띠·붉은 실행·하트비트는 남는다 |
| `no-games` | — | **아니오** | DB 에 경기가 없으면 배포할 것이 없다 |

⚠회로가 열려 그 갈래의 받기가 **건너뛰어졌으면**(합성 step 69) 그것도 그 갈래의 상류 실패다 — 예고에서 회로가 열린 실행은 경기·선수 갈래의 사유도 설명된다. 모르는 종료로 건너뛰었으면(합성 step 1) 설명하지 않는다.

대가: 상류 실패와 수집 결함이 같은 실행에 겹치면 결함은 한 실행 늦게 드러난다 — 실행은 붉고 배포되는 것은 검증된 옛 데이터라 지연이지 오염이 아니다.
`update.ts` 마지막 줄은 `blocking N · 상류 M · 설명된 신선도 K` 로 가르고 종료 코드는 R5. **빌드의 `stale`(`packages/web/tools/build.ts:440-443`)**: `BB_UPSTREAM_OUTAGE=1` 이면 경고 한 줄만 · 종료 코드 불변. 그 밖의 `exitCode=1` 갈래는 건드리지 않는다. 값은 워크플로가 `rc == '75'` 일 때만 `1` 로 넘긴다.

### D6. 워크플로 — `daily.yml` (HEAD 의 단계 전부)

`수집·적재` 만 75 를 0 으로 통과시키고 출력 `rc` 를 남긴다. 나머지 단계의 `if:` 는 **고치지 않는다**(받기를 하는 두 단계 — 공표 성적표 갱신 · 정정 — 만 `rc != '75'` 를 더한다).

```yaml
- name: 수집·적재
  id: update
  timeout-minutes: 30
  env: { BB_ARCHIVER_CONTACT: …, BB_REFETCH_DATES: …,
         BB_NPB_CIRCUIT_N: ${{ needs.decide.outputs.slot == 'retry' && '1' || '3' }} }
  run: |
    set +e; node scripts/update.ts --max-writes 5000000; rc=$?; set -e
    echo "rc=${rc}" >> "$GITHUB_OUTPUT"
    case "$rc" in 0) ;; 75) echo "::warning::npb.jp 받기 실패만 있었다 — 이미 받은 데이터로 배포한다" ;; *) exit "$rc" ;; esac
```
`timeout-minutes: 30` = 걸쇠. 식: 선행 1.0(실측 최대 0.61) + 30 + 0.4 + 후속 11.43 = 42.8 ≤ 45 − 1.5 = 43.5. 이전 판의 33 은 44.8 이라 틀렸다. 걸쇠가 풀리면 `rc` 출력이 없어 blocking.

**단계 안의 최악 시간 — 따라잡기 날짜를 넣어 다시 쓴다**(3중 검토 1차 P2-2 · 2차 F2 · `scripts/collect-budget.ts`). ~~정상 최악(전원이 낡은 날 선수 재취득 400건 ≈ 24분)은 30 안이다~~ 는 **날짜를 안 셌다** — 장애가 풀린 뒤의 복구 실행은 대상 경기일이 최대 9일(따라잡기 `[어제 − 7, 어제]` + 오늘)이다.

`T(d, P) = 로컬 2.0 + [(예고 1 + d × 26 + P + 신규 선수 여유 40) × (간격 + 응답 여유 1.0초) + (d + 3 − 1) × 간격] ÷ 60` (분)

- `26` = 날짜 하나의 최대 요청(6경기 × 4장 + 그 달·다음 달 월간 일정 · 날짜 자식마다 따로 받는다) · `P` = 선수 재취득 수 · `d + 3` = 받기 자식 수(예고 · 날짜 d · 선수 둘) · 간격 = `--delay`(3초).
- 응답 여유 1.0초는 **보수값**이다: CI 실측은 선수 재취득 **3.06~3.16초/장**(17실행 · 2026-09-28~10-16 · 간격 3초)이지만 로컬 백필 실측은 3.96초/장이다 — 복구 실행은 장애 직후라 느린 쪽을 쓴다.
- **규칙**: `d ≤ 2`(정상 · 어제와 오늘)면 `P` = 설정값(400) 그대로 · `d > 2`(따라잡기 · 재수집)면 `T(d, P) ≤ 30 − 여유 3` 을 지키는 가장 큰 `P`(설정값을 넘지 않고 1 아래로 안 내려간다). 밀린 몫은 다음 실행이 잇는다(`emit-stale-player-ids` 가 밀린 수를 찍는다).

| d | 3 | 4 | 5 | 6 | 7 | 8 | 9 |
|---|---|---|---|---|---|---|---|
| P(간격 3초) | 252 | 225 | 198 | 172 | 145 | 118 | 91 |
| T(분) | 26.98 | 26.97 | 26.95 | 27.00 | 26.98 | 26.97 | 26.95 |

⚠**정상(d ≤ 2)은 브리프 결정대로 바꾸지 않았다** — 같은 보수값으로 재면 `T(2, 400)` = 35.07분 · `T(1, 400)` = 33.28분이라 걸쇠를 넘고, CI 실측 속도(3.1초/장 · 응답 여유 0.1)로 재면 27.67분 · 26.28분이다(식을 그대로 돌린 값). 즉 **전원이 낡은 정상 실행(복구 실행 다음 날 · 백필 직후)은 npb.jp 의 응답 속도에 기대어 30분 안에 든다** — 느린 날이면 걸쇠가 죽인다(blocking · 그때까지 받은 선수는 아카이브에 남아 다음 실행이 줄어든 목록으로 잇는다). §5 뒤집힐 조건 ⑸.

| 산출물 목록 만들기 · 보관 | `failure() \|\| cancelled()` | skip | skip(앞이 성공이면) | **실행** | 실행 |
| **A 요약**(신규) `failure() && rc=='75'` | | skip | 앞 단계 실패가 있을 때만 | skip(rc≠75) | skip |
| **B 의도적 실패**(신규) `success() && rc=='75'` | | skip | **앞 단계 전부 성공일 때 실행 → `exit 1`** | skip | skip |

- 굵은 「실행」 = **부분 수집분 보존 · 운영 기록 · 반영 확인**이라는 현재 `always()` 경로를 그대로 둔다(3차-2). rc=75 인 실행은 이 세 단계가 정상 실행과 똑같이 돈다.
- **A 가 B 앞**(2차-6): `failure()` 는 앞선 단계 중 실패가 있으면 참이다. B 를 먼저 두면 B 의 의도적 `exit 1` 이 A 를 참으로 만들어 「다른 실패와 병존」을 오인한다. A 를 먼저 두면 A 평가 시점에 B 는 아직 실행 전이다. 상호 배타 · 최종 메시지는 하나.
  `!cancelled()` 를 쓰지 않는다 — 상태 함수가 있으면 암묵 `success()` 가 붙지 않아 앞 단계 실패에도 참이다.
- 정정 단계는 `FetchResult.exit`·`readFetchResult`·`stepExitCode` 가 `0|1` 이라 75 계약에 참여시키지 않는다 — `rc != '75'` 이면 건너뛴다(요청 0 · 이력 불변: `history.next.json` 없음은 커밋 단계가 이미 `-f` 로 건너뛴다). 건너뛴 실행의 `외부 대조` 관문은 정정 보고가 없으므로 실패 시 「정정: 상류 장애로 건너뜀」을 찍는다(관문 판정은 한 글자도 안 바꾼다 — 불일치가 남으면 지금처럼 막는다). `rc==0` 에서 정정 단계 자신의 받기가 실패하면 지금처럼 1 = 막는다.
- **I3 의 세 예외(`continue-on-error: true`)**: ① 드래프트 원본 복원 — 연 1회 행사, 실패는 `::warning::`, 뒤 적재가 아카이브 유무를 본다 ② 드래프트 적재 — DB 에 어제 값이 남고 실패는 `::error::` 주석 ③ 공표 성적표 갱신 — 외부 대조의 재료일 뿐, 못 받으면 `외부 대조` 가 옛 스냅숏으로 돌고 대상 0명이면 exit 1. 새 단계(`수집·적재` 셸 · A · B)에는 `continue-on-error` 를 쓰지 않는다.
- **B (마지막)**: `echo "::error::npb.jp 받기 실패 — 이미 받은 데이터로 배포했다(띠가 낡음을 말한다)"; exit 1`. 재시도 슬롯(`decide`)은 붉은 실행 뒤에 그대로 돈다(`prev != success`) — 바라는 동작이다(예고는 거르면 영영 못 받는다). 장애 실행을 녹색으로 끝내면 하트비트·실패 메일·재시도가 전부 침묵한다(I5 위반)라 기각. 재시도 슬롯의 회로 한도는 1.

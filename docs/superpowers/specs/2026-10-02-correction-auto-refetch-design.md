# 공표 정정 자동 재수집 — 외부 대조가 찾을 불일치의 경기를 그 실행 안에서 다시 받는다 — 설계

- 날짜: 2026-10-02
- 상태: **3판**.
  - 콜드 리뷰 1차(「구현 불가」 · 9건)는 2판에서 반영했다.
  - 2차(「불가」 · P1 3 · P2 2 · P3 1)는 이 판에서 반영했다(§0). 다음은 3차 콜드 리뷰다.
- 고위험 영역: 수집 요청량(L1) · 배포 관문 · 운영 이력의 동시 쓰기 · 아카이브 판과 부분 기록(M4/M5) → 배포 전 `shiro-core:triple-review`(루트 §4)
- 사용자 결정(2026-10-02)
  - ① 지금은 수동 실행(`refetch_dates=2026-09-17`)으로 즉시 복구한다.
  - ② 자동 재수집으로도 안 풀리는 불일치가 남으면 **지금처럼 배포를 막고 분명히 알린다**(외부 대조 관문을 약하게 하지 않는다).
- **이 설계가 바꾸지 않는 것**
  - 외부 대조 관문(`외부 대조` 단계)의 판정과 종료코드
  - `crosscheck.ts` 를 `--emit` 없이 부를 때의 출력과 종료코드
  - 수동 `refetch_dates` 의 수집 경로(`scripts/update.ts`)
  - `PoliteFetcher` 의 기본값과 `archiveGame` 의 동작(평소 수집 경로)
  - 보관소 업로드의 조건(D14)

## 2. 목표와 비목표

- **목표 1**: 외부 대조가 진행 중 시즌에서 찾을 결함 후보를 **관문보다 먼저** 감지한다. 그 차이를 만들 수 있는 **경기**를 그 실행 안에서 다시 받고 다시 적재한다. 정정이면 그 실행에서 풀린다. 이번 사고라면 3경기 · 논리 페이지 12 · HTTP 전송 12(전부 200 일 때)다(D6 재현).
- **목표 2**: 풀리지 않으면 **지금처럼 배포를 막는다**(사용자 결정 ②). 그리고 「해 봤는데 남았다」와 「해 보지 않았다(사유)」를 **로그만으로** 가를 수 있게 한다.
- **목표 3**: 결함 후보가 없는 실행에서는 **요청이 하나도 늘지 않는다**(시험으로 고정 · D13).
- **목표 4**: 자동 경로는 **섞인 세트를 남기지 않는다**(R2-2). 그리고 **한 실행의 실제 HTTP 전송과 시간에 계산된 상한이 있다**(R2-1).
- **비목표**
  - 외부 대조 관문의 판정 기준을 바꾸는 것(문턱 · 허용 건수).
  - 완결 시즌의 자동 재수집. 그 불일치는 정정이 아니라 우리 파서·집계 회귀일 가능성이 크다. 관문이 그대로 막는다.
  - 지난 경기를 주기적으로 전부 다시 받는 것(L1 — 정정 지연을 재 본 적이 없다).
  - 우리에게 **행이 없는** 경기를 찾는 것(§7).
  - 자식 행만 바뀐 정정에 판 표지를 다는 것(§7 — M4 기존 한계).
  - 평소 수집 경로의 G3b(부분 기록)를 고치는 것(선례 설계가 G4 로 받기로 정했다 · §6).

## 4. 한 실행의 흐름

1. **(새) 잡 첫 단계** — 잡 시작 시각을 낸다(`steps.job-start.outputs.at`).
2. `수집·적재`(기존 · 그대로) — 수동 `refetch_dates` 가 있으면 여기서 그 날짜의 경기를 받는다.
3. `공표 성적표 갱신`(기존 · 그대로) — 정답지 30장.
4. **(새) `정정 감지 · 자동 재수집`** — 차례는 D9 의 표다. 요약하면 다음과 같다.
   1. 이력 읽기
   2. 사전 감지
   3. ① 사전 이력 갱신
   4. 계획
   5. 받기(`cli-games.ts` · 회로 차단 · 마감 · 예산 · 되돌리기)
   6. 다시 적재
   7. ③ 시도 기록
   8. 사후 감지
   9. ④ 사후 이력 갱신
   10. ⑤ 소진 판정
   11. 보고 · 다음 이력 쓰기
   12. 종료
5. `수집 후 재검증` → `보관소에 올림`(조건 불변 · D14) → `기록 갱신과 커밋`(이력 반영).
6. `파서 자기 검증` → `득점 대조` → **`외부 대조`(관문)** — 판정은 그대로이고, 실패하면 4의 보고를 다시 찍는다 → `화면 생성` … `배포`.

### D1. 새 단계의 자리와 배선 — `공표 성적표 갱신` 뒤 · `수집 후 재검증` 앞

**자리.** `daily.yml` 의 `공표 성적표 갱신`(466~484행) 바로 뒤, `수집 후 재검증`(486행) 바로 앞이다.
- 이 단계는 공표표를 다시 받지 않는다.
- **업로드 앞이어야 하는 이유(P2-8).** 정상 경로의 `보관소에 올림` 은 세대 tar(`store-YYYYMMDD.tar` = `data/archive`)와 `bb.sqlite.gz` 를 **함께** 올린다(525~527행 · 564행). 「DB 를 올리지 않는다. 아카이브만 올린다」는 `db-check` 실패 분기(528~531행)다.
  - 정정된 아카이브와 정정된 DB 가 **같은 세대**에 실려야 다음 실행이 둘 다 정정 뒤의 것으로 복원한다.
  - 뒤에 두면 다시 받은 페이지가 사라진다. 그래도 조용히 틀리지는 않는다 — D5 의 제외 규칙이 DB 의 `fetched_at` 을 보므로 그 경기는 다시 후보가 된다.
- 기존 `외부 대조`(관문 · 728~762행)는 이 단계 **뒤의 DB** 로 다시 잰다.
- **실패해도 업로드는 지금처럼 돈다** — 갈래별 근거는 D14.

**`if:` — 두지 않는다(= `success()`).**
- `continue-on-error` 가 아닌 앞 단계(체크아웃 … `복원 검증` · `수집·적재`)가 하나라도 실패한 실행에서는 돌지 않는다.
- 그 실행은 이미 빨갛고, 관문도 같은 이유로 돌지 않는다. 정정은 다음 실행이 다시 감지한다.
- `드래프트 원본 복원`·`드래프트 적재`·`공표 성적표 갱신` 은 `continue-on-error` 라 이 판정에 영향을 주지 않는다.

### D2. 감지 — `crosscheck.ts --emit` 의 상태 계약

**호출 형태.** `node packages/aggregate/tools/crosscheck.ts <db> <season> --archive <dir> --emit <path>`

| | `--emit` 없이(관문 · **불변**) | `--emit` 있음(감지 모드 · 새) |
|---|---|---|
| 사람용 출력 | 지금 그대로 | 지금과 같은 것을 찍는다 |
| 측정 성공 · 결함 0건 | 종료 0 | 종료 **0** · `status: "no_defects"` |
| 측정 성공 · 결함 N건 | 종료 1 | 종료 **0** · `status: "defects"` |
| 측정 실패(아래 닫힌 목록) | 종료 1(대부분) 또는 잡히지 않은 예외 | 종료 **2** · `status: "unmeasured"` |
| 예상 밖 예외(버그) | 0 이 아닌 종료 | 0·2 가 아닌 종료 · **JSON 을 약속하지 않는다** |

**측정 실패의 닫힌 목록(`reason`).**
- `asof_split` — 공표표 기준일이 장마다 다르다. 지금은 98~104행에서 종료 1 이다.
- `table_parse_error` — 공표표 해석이 던졌다(`StatsParseError`). 지금은 잡히지 않은 예외로 죽는다.
- `tables_missing` — 기대한 **24장**(12구단 × `idb1`·`idp1`) 중 못 읽은 장이 있다. 지금은 경고만 찍고 진행한다(221~222 · 273~276행). ⚠감지 모드는 관문보다 엄격하다.
- `compared_zero` — 대조한 선수가 0명이다. 지금은 392~399행에서 종료 1 이다.
- **둘 이상 걸리면 이 목록의 순서대로 첫 것 하나**만 `reason` 에 적는다. 예를 들어 공표표가 0장이면 `tables_missing` 이다. 나머지는 `reason_detail` 에 사람이 읽는 글로 덧붙인다.

**판정은 순수 함수 한 벌.** `crosscheck-classify.ts` 의 `crosscheckEmitStatus({ asOfDates, tablesRead, tablesExpected, parseError, comparedPlayers, defects })` 가 `{ status, reason }` 을 낸다. 종료코드는 `status` 에서 낸다.

### D3. 시즌 상태 — 공표표에 `現在` 가 있을 때만 자동

- 감지 시즌은 새 단계가 시계를 한 번 읽은 시각의 **JST 연도**다(`공표 성적표 갱신` 과 같은 규칙). 그 시즌 공표표가 없으면(1~3월) `tables_missing` 이다.
- **자동은 `as_of.source == "genzai"` 일 때만 한다.** 그 밖이면 받지 않고 사유를 찍는다.
  - `absent` — 「24장 어디에도 기준일(現在)이 없다 — 완결 시즌이거나 문구가 바뀌었다(못 가른다) · 자동 재수집 안 함 · 관문이 판정한다」
  - `partial` — 「일부 장에만 기준일이 있다 · 자동 재수집 안 함」
  - `override` — 「`--through` 로 사람이 정한 기준일이다 · 자동 재수집 안 함」
- `seasonIsOver()`(`packages/store/src/season-over.ts`)는 쓰지 않는다. 그 함수는 「우리 데이터로 시즌이 끝났나」에 답한다. 자동에 필요한 것은 ⑴ 기준일로 자른 스냅숏인가 ⑵ npb 가 아직 고치고 있나다 — 그 표지가 `現在` 다.
- ⚠npb 가 완결 시즌에서 `現在` 를 **언제 지우는지는 안 쟀다**.

### D5. 후보 경기와 제외 규칙 — ID 로만

**결함 키** = `시즌|팀|역할|player_id|항목`(예: `2026|t|pitching|91095136|暴投`). 대상이고 값 해석이 된 결함에만 만든다.

**후보 조회(키당 한 번 · ID 로만 · M10).** `crosscheckScope("x")` 는 crosscheck 의 두 SQL 과 **같은 조각**이다(M1).
```sql
SELECT g.game_id, g.game_date, g.fetched_at, <경기 값 식> AS value
FROM <batting_line|pitching_line> x JOIN game g ON g.game_id = x.game_id
WHERE <crosscheckScope("x")>            -- season · played · regular · game_date ≤ as_of · 그 팀 쪽
  AND x.player_id = ?
  AND (<o>p 이면 그 항목의 술어 · o<p 이면 1 = 1>)
ORDER BY g.game_date DESC, g.game_id
```
- 기존 색인을 쓴다(M-E). 팀 조건이 이적을 처리한다(M-D).
- `value` 는 보고의 「전 값」이다.

**제외 규칙.**
1. **E1 기준일 뒤**: 범위 조각이 이미 뺀다.
2. **E2 일화 시작 뒤에 본 사본**: `game.fetched_at ≥ 키의 first_seen_at` 이면 뺀다.
   - `game.fetched_at` 은 box 사이드카의 `checkedAt ?? fetchedAt`(「마지막으로 본 시각」 · `version-guard.ts` 4~6행)이다.
   - 네 장 세트가 기록되면 받은 시각으로 오른다. **받기 실패(G3a)·되돌린 기록 실패(G3b)면 오르지 않는다**(D7-5).
   - 비교는 `Date.parse` 로 한다. 못 읽으면 빼지 않는다(M11 — 모르면 받는 쪽).
   - 가정은 「npb 가 박스를 공표표보다 늦게 고치지 않는다」이다. 어긋나면 소진으로 사람에게 간다(§7).
3. **E3 이 실행의 수동 날짜**: 몇 분 전에 받았다. 날짜 상한을 셀 때도 쓴다.

- **남은 후보(키)** = 후보 − E2 − E3. **남은 날짜(키)** = 그 `game_date` 집합.

### D6. 고르기 — 관문 · 순서 · 상한

**전체 관문 — 위에서부터 처음 걸리는 것이 「해 보지 않았다」의 사유다.**

| 순 | 조건 | 사유 코드 |
|---|---|---|
| 1 | 감지기가 0·2 가 아닌 코드로 끝났거나 결과 파일이 없다 | `detector_error` |
| 2 | `status == "unmeasured"` | `unmeasured:<reason>` |
| 3 | `status == "no_defects"` | `no_defects` |
| 4 | `BB_RUN_SLOT` 이 `scheduled`·`manual` 이 아니다 | `retry_slot`(값이 `retry`) · `slot_unknown` |
| 5 | `as_of.source != "genzai"` | `as_of:<source>` |
| 6 | 결함 후보(`defects` 전체) > `AUTO_REFETCH_MAX_DEFECTS`(20) | `too_many_defects` |
| 7 | 대상 키가 0개다 | `no_eligible` |
| 8 | **시간 예산** — 아래 한 식 | `started_at_unknown` · `time_budget` |
| 9 | 날짜 자리가 없다: `MAX_REFETCH_DATES − 수동 날짜 수 ≤ 0` | `no_date_slots` |
| 10 | 대상 키가 전부 남은 날짜 0이다 | `all_exhausted` |

**8 의 식(R2-6 — 이 문서의 모든 「25분」은 이 식이다).**
```
elapsedMs = Date.parse(now) − Date.parse(BB_COLLECT_STARTED_AT)        // UTC 밀리초
started_at_unknown  ⇔  Number.isNaN(elapsedMs) || elapsedMs < 0 || elapsedMs > 6 × 3_600_000
time_budget         ⇔  elapsedMs >= AUTO_REFETCH_START_DEADLINE_MIN × 60_000   // = 1_500_000
```
- `now` 는 진입점이 한 번 읽은 시각이다(M6).
- 정확히 1,500,000ms 이면 `time_budget` 이고, 1,499,999ms 이면 진행이다.
- 경기마다의 마감(D7-4)은 `deadline = new Date(Date.parse(BB_COLLECT_STARTED_AT) + 1_500_000).toISOString()` 이고 비교는 `now >= deadline` 이다. **같은 시각 · 같은 등호**다.

**고르는 순서 — 전순서(R2-4).**
- **문자열 비교는 전부 UTF-16 코드 단위 비교**(`a < b` · JS 기본 문자열 비교)다. `localeCompare` 는 쓰지 않는다 — 로캘에 따라 갈린다. 키에 일본어(`暴投`)가 들어 있다.
- 감지 결과의 `defects` 배열 순서는 쓰지 않는다(계약이 아니다 · D2). 모든 입력을 아래 규칙으로 다시 정렬한 뒤 고른다.
```
키들 = 남은 날짜가 있는 대상 키를 (남은 날짜 수 오름차순, 키 문자열 코드 단위 오름차순)으로 세운다
고른 날짜 = [] · 고른 경기 = []
날짜 자리 = MAX_REFETCH_DATES − 수동 날짜 수
for 키 in 키들:
  for d in 그 키의 남은 날짜를 내림차순(최근부터):
    if d ∈ 고른 날짜: continue
    그날 경기 = ⋃(모든 대상 키의 d 날짜 남은 후보 경기)을 game_id 코드 단위 오름차순으로
    if |고른 날짜|+1 > 날짜 자리  or  |고른 경기 ∪ 그날 경기| > AUTO_REFETCH_MAX_GAMES(24): 전부 멈춘다
    고른 날짜 += d · 고른 경기 += 그날 경기(중복 제외 · 순서 유지)
```
- **받는 차례 = 고른 차례**다. 고른 날짜 순서대로, 날짜 안에서는 `game_id` 오름차순으로 `games.txt` 에 적는다. `cli-games.ts` 는 그 차례대로 받는다.
- **후보가 적은 키부터** 고른다. 한 키 안에서는 **최근 날짜부터** 고른다. 근거는 셋이다.
  1. 키가 새로 생겼다는 것은 그 사이 공표표가 바뀌었다는 뜻이다.
  2. 관측된 정정 1건이 약 열흘 뒤였다.
  3. 1판의 `fetched_at` 오름차순은 초기 구축 사본(623/842)을 먼저 집는다.
  - ⚠정정 지연 분포는 표본이 1건이다.
- 상한을 넘으면 그 자리에서 멈춘다. 건너뛰고 작은 날짜를 찾지 않는다.
- **이번 사고 재현(T4).** 키 1개 · o>p · 후보 3일 · 수동 0.
  - → 고른 날짜는 `2026-09-23, 2026-09-17, 2026-05-13` 이고, 경기는 3이다.
  - → 논리 페이지 12다. 전부 200 이면 HTTP 전송도 12다.

### D7. 재수집 전용 경로 — 논리 페이지와 HTTP 전송 · 회로 차단 · 마감 · 되돌리기

#### D7-1. 왜 `update.ts` 를 다시 부르지 않나(P1-2)

`BB_REFETCH_DATES=… node scripts/update.ts` 를 다시 부르면 다음이 전부 다시 돈다.
- 날짜마다 `cli.ts` 를 따로 띄운다(`update.ts` 201~209행). 그래서 날짜마다 월간 일정 1장, 다음 달 일정 1장(`cli.ts` 106~121행)을 받는다.
- 선수 재취득(상한 400) · 신규 선수 · 予告先発도 돈다.
- 수동 날짜와 겹치면 14일이 된다.

#### D7-2. 받기 도구 — `cli-games.ts`(얇은 CLI) + `refetch-games.ts`(핵심)

```
node packages/archiver/src/cli-games.ts --ids <work>/games.txt --out data/archive --delay 3000 \
  --deadline <ISO> --result <work>/fetch-result.json
```
- 연락처는 env `BB_ARCHIVER_CONTACT` 에서 읽는다(`cli.ts` 와 같은 규칙 · 비면 종료 2).
- **요청 0으로 종료 2** 하는 입력은 다음과 같다(L1 의 마지막 방어선).
  - ID 모양이 `^\d{4}/\d{4}/[a-z0-9]+(?:-[a-z0-9]+)+$` 가 아니다.
  - 줄 수가 `AUTO_REFETCH_MAX_GAMES`(24)를 넘는다.
  - `--deadline` 이 시각으로 안 읽힌다.
  - `--delay` 가 L1 하한 미만이다.
- ID → `GameRef` 는 `discover.ts` 의 새 `gameRefFromId` 다(`pageKey` 의 역함수 · 왕복 시험). **월간 일정은 받지 않는다** — 경기 ID 가 곧 URL 이다(`game.source_url` 실측).
- 상수는 잎 `@bb-app/store/refetch-limit` 에서 직접 가져온다(아카이버 → store 잎 · import 0개인 파일이라 다른 모듈을 끌어오지 않는다).
- 핵심은 `packages/archiver/src/refetch-games.ts` 의 `refetchGames(refs, deps, opts)` 다.
  - `deps = { fetcher, sink: RestorableSink, clock, meter }`
  - `opts = { deadlineMs, maxHttp }`
  - CLI 는 다음을 만들어 넘긴다.
    - `meter`
    - `meteredFetch(globalThis.fetch, meter, { timeoutMs: AUTO_REFETCH_REQUEST_TIMEOUT_MS })`
    - `new PoliteFetcher({ userAgent, minDelayMs: 3000, maxRetries: AUTO_REFETCH_MAX_RETRIES, clock: systemClock, fetchImpl })`
    - `new LocalSink(out)`
  - 시험은 핵심 함수를 가짜 fetch·sleep·clock·sink 로 부른다(T7).

#### D7-3. 논리 페이지와 HTTP 전송(R2-1)

- **논리 페이지(`page_fetches`)** = `prepareUrl` 호출 수다. 시작한 경기는 늘 4다 — `archiveGame` 은 받기 단계에서 네 장을 다 받는다(`archive.ts` 297~304행).
- **HTTP 전송(`http_attempts`)** = `fetchImpl` 호출 수다. M-R 의 코드 사실로 보면, 기본값 그대로일 때 페이지 하나가 **최대 4시도 × 4전송 = 16전송**이다.
  - ⚠2판의 「24경기 = 96요청」은 논리 페이지 수였다. 실제 전송은 최대 1,536(= 96 × 16)이었다 — **2판의 상한과 시간 계산은 틀렸다.**
- **자동 경로의 설정(전부 `refetch-limit.ts` 정본 · D12).**
  - **`maxRetries: AUTO_REFETCH_MAX_RETRIES`(1)** → 시도 ≤ 2 → 페이지당 전송 ≤ **8**.
    - 근거(L1): 상대가 5xx·시간 초과를 낼 때 같은 페이지를 네 번 치는 것은 아픈 상대를 더 친다. 이 경로는 급하지 않다 — 못 받은 경기는 `fetched_at` 이 그대로라 다음 정시 실행이 다시 고른다(E2).
    - **평소 수집(`update.ts`)의 기본값 3은 바꾸지 않는다.** 그쪽은 거르면 영영 못 받는 予告先発·당일 경기를 받는다.
  - **전송 시간 상한 `AUTO_REFETCH_REQUEST_TIMEOUT_MS`(5,000).** 지금 fetcher 에는 시간 상한이 없다(M-R). 그러면 한 전송의 상한이 런타임 기본값에 달리고, 이 저장소는 그 값을 잰 적이 없다.
    - 실측 전송 시간은 최대 0.191초다(M-Q · 145간격). 5초는 그것의 **26배**다.
    - 넘으면 예외 → 재시도 대상 → **고통 신호**(D7-4)다.
    - 5초보다 느린 응답은 그 자체로 상대가 아프다는 신호로 본다(§7).
  - **계측 — `meteredFetch(inner, meter, { timeoutMs, timeoutSignal? })`**(새 `packages/archiver/src/metered-fetch.ts`).
    - PoliteFetcher 에 넘기는 `fetchImpl` 을 감싼다.
    - 호출마다 `meter.http += 1` 한 뒤 `inner(url, { ...init, signal: timeoutSignal(timeoutMs) })` 를 부른다. 기본 `timeoutSignal` 은 `AbortSignal.timeout` 이고, 시험이 주입한다.
    - 응답 상태가 재시도 대상이면 `meter.distress = true` 다. 재시도 대상 집합은 `fetcher.ts` 의 `RETRYABLE` 을 **내보내 한 벌로** 쓴다(M1).
    - 예외(시간 초과 포함)도 `distress = true` 이고 그대로 다시 던진다.
    - 상태별 횟수(`meter.byStatus`)를 결과 JSON 에 남긴다.
  - ⚠**`PoliteFetcher` 는 고치지 않는다**(`RETRYABLE` 를 내보내는 한 줄만).
    - 첫 전송 · 리디렉트 홉 · 재시도가 **전부** `request()` → `fetchImpl` 을 지난다(262~266행). 그래서 감싼 쪽이 전송을 빠짐없이 센다.
    - 간격 하한 검사는 `fetchImpl` 주입과 무관하게 걸린다(`fetcher.ts` 113~131행 — 「시험이면 봐 준다」를 만들지 않았다).

#### D7-4. 경기 사이에서 멈춘다 — 회로 차단 · 마감 · HTTP 예산(R2-1)

`refetchGames` 는 **경기를 시작하기 전마다** 이 순서로 묻고, 처음 걸린 것으로 멈춘다. 멈추면 남은 경기는 전부 같은 사유로 `skipped` 다.

| 순 | 조건 | 사유 | 종료코드에 |
|---|---|---|---|
| 1 | **회로가 열렸다** — ⑴ 앞 경기가 `prepare_failed`·`commit_failed`·`snapshot_failed` 였다, 또는 ⑵ `meter.distress`(재시도 대상 응답이나 전송 예외가 **한 번이라도** — 그 페이지가 결국 성공했어도) | `circuit_open` | ⑴ 이면 그 경기 때문에 이미 1 · ⑵ 만이면 0 |
| 2 | `clock.now().getTime() >= deadlineMs` | `deadline` | 0 |
| 3 | `meter.http + 32 > AUTO_REFETCH_MAX_HTTP`(128) | `http_budget` | 0 |
| 4 | 사전 사본(D7-5)을 못 떴다(ENOENT 아닌 읽기 오류) | `snapshot_failed` → 회로가 열린다 | **1** |

- **회로 차단의 근거**: 받기 실패나 재시도는 상대가 아프다는 신호다(L1).
  - 열린 뒤 남은 경기는 `fetched_at` 이 그대로라 **다음 정시 실행이 다시 고른다**(E2). 재시도 슬롯은 받지 않는다(D6 의 4).
- **32** = 한 경기 최악 전송 = 4장 × (`AUTO_REFETCH_MAX_RETRIES` + 1) × (1 + `MAX_REDIRECTS`) = 4 × 2 × 4 다. 코드에서도 이 식으로 낸다(상수를 따로 적지 않는다).
  - 시작한 경기가 예산을 넘을 수 없게 **시작 전에** 막는다. 그래서 한 실행의 전송은 **절대 128 을 넘지 않는다.**
  - 정상(경기당 4전송)이면 24번째 경기 앞에서 92 + 32 = 124 ≤ 128 이라, 24경기가 다 돈다.
- ⚠**멈춤은 경기 사이에서만 한다.** 경기 하나 안에서는 기존 `archiveGame` 대로 네 장을 다 받는다. 그래서 한 경기의 최악(D7-8)이 계산에 들어간다.
- ⚠멈춘 경기를 `held` 라 부르지 않는다. 아카이버에서 `held` 는 「받았고 바뀌었지만 같은 경기의 다른 페이지가 실패해 기록하지 않은 **페이지**」의 이름이다(`archive.ts` 17~21행). 경기 단위는 `skipped` 다.

#### D7-5. 한 경기 안 — G3a 와 G3b, 그리고 되돌리기(R2-2)

**2판 정정.** 「하나라도 실패하면 아무것도 안 쓴다」는 **받기 단계에만** 맞다. 선례 설계(`2026-09-25-archive-load-version-guard-design.md` G3·G4)와 코드가 두 갈래를 가른다.
- **G3a — 받기 단계 실패**(`prepareUrl` 네 장 중 하나라도 `failed` · `archive.ts` 306~328행).
  - **아무것도 안 쓴다** — 본문 · 사이드카 · 안 바뀐 페이지의 「봤다」까지.
  - → box 사이드카의 본 시각이 그대로다 → 다시 적재해도 `game.fetched_at` 이 그대로다 → **그 경기는 다음 정시 실행에서 다시 후보다**(E2).
- **G3b — 기록 단계 실패**(`commitPrepared` 가 index → playbyplay → box → roster 차례로 기록하다 하나가 실패 · 330~342행).
  - **거기서 멈추고, 앞에서 기록한 페이지는 남는다.**
  - 기록 하나는 본문 → 사이드카 두 번의 원자적 쓰기다(`sink.ts` 123~134행 · 151~155행). 그래서 세트가 섞이거나(앞 페이지만 새 `set`), 한 페이지의 본문과 사이드카가 어긋날 수 있다.
  - 평소 경로에서는 적재기가 G4(본문 대조 → 세트 대조 · `load-archive.ts` 429~439행)로 잡아 그 경기를 실패로 센다.

**자동 경로는 섞인 세트를 남기지 않는다** — 경기마다 다음을 한다.
1. **받기 전에 뜬다.** 네 장의 **저장 바이트**를 메모리에 뜬다 — 본문 파일(`<key>.html.gz`)과 사이드카 파일(`<key>.meta.json`)의 바이트 그대로이고, 없으면 「없음」이다.
   - 새 인터페이스 `RestorableSink extends Sink { snapshot(key); restore(key, snap) }` 를 `sink.ts` 에 두고 `LocalSink`·`MemorySink` 가 구현한다. 기존 `Sink` 사용처는 바뀌지 않는다.
2. `archiveGame(ref, deps)` 를 그대로 부른다(바꾸지 않는다).
3. **결과에 `failed` 가 없으면** `recorded`(`rollback: null`)다.
4. **결과에 `failed` 가 있으면** 네 장을 다시 떠서 사전과 **바이트로** 맞댄다. 이 프로세스가 남긴 임시 파일(`<path>.<pid>.tmp`)이 있는지도 같이 본다.
   - 모두 같고 임시 파일도 없다 → **G3a**(`prepare_failed` · `rollback: null` · 되돌릴 것이 없다).
     - ⚠기록 단계의 첫 쓰기가 최종 경로와 임시 파일을 하나도 건드리기 전에 실패한 경우(예: 디렉터리 만들기 실패)도 여기로 온다. 이름은 `prepare_failed` 지만 **상태는 G3a 와 같다** — 아무것도 바뀌지 않았다. 이 이름은 「상태」를 말하지 「실패한 단계」를 말하지 않는다.
   - 하나라도 다르거나 임시 파일이 남았다 → **G3b**(`commit_failed`) → `restore` 한다.
     - 있던 파일은 원래 바이트를 「같은 디렉터리의 임시 파일 + rename」으로 다시 쓴다.
     - 없던 파일은 지운다(ENOENT 는 성공).
     - 이 프로세스가 남긴 임시 파일(`<path>.<pid>.tmp` · `sink.ts` 152행)도 지운다.
   - → 다시 떠서 사전과 같으면 `rollback: "ok"`, 아니면 `"failed"` 다.
   - 갈래를 결과 문자열이 아니라 바이트 비교로 가르는 이유: `PageResult` 에는 실패가 받기에서 났는지 기록에서 났는지 칸이 없다(`archive.ts` 23~38행). **바이트가 그대로라는 사실이 곧 「아무것도 안 썼다」의 판정**이다.

**되돌리기도 실패하면(이중 고장).**
- `cli-games` 는 종료 1, 단계도 종료 1 이다.
- 보고 첫 줄은 `정정 자동 재수집 — 해 봤으나 실패 — 섞인 세트 남음: <경기ID> — 런북 §7-E` 다.
- 그 상태는 다음 실행에서 이렇게 드러난다(D14 ③).
  1. 같은 실행의 다시 적재가 그 경기를 G4 로 건너뛴다(쓰지 않는다 → DB 는 그 경기의 옛 행).
  2. 업로드는 조건대로 돌아 섞인 세트가 세대에 실린다.
  3. **다음 실행의 `수집·적재`** 가 복원한 아카이브를 적재하다 G4(세트 또는 본문 불일치)로 그 경기를 실패로 센다(`load-archive.ts` 1033~1037행의 종료 1).
  4. → `수집·적재` 종료 1 → **새 단계는 `success()` 라 돌지 않는다** → 관문도 돌지 않는다 → 배포가 막힌다.
  5. 적재 로그가 `복구: 수동 실행 입력 refetch_dates=…` 를 찍는다(`load-archive.ts` 955~973행). **사람이 런북 §7-E 대로** 그 날짜를 수동으로 다시 받는다. 다시 받으면 네 장이 한 세트로 다시 쓰인다.
- **프로세스가 기록 도중 죽으면**(단계 시간 제한 · 자식 시간 제한 · 러너 사망) 되돌리기를 못 한다. 그러면 **같은 G4 경로**다.

#### D7-7. 요청 종류 전수와 상한표

**요청 종류(한 실행 · 기존 단계와 나란히).**

| 요청 종류 | 수동 `refetch_dates`(기존 · `수집·적재` · 기본 `maxRetries` 3) | 자동(새 단계 · `maxRetries` 1) |
|---|---|---|
| 경기 4장 | 그날 전 경기 × 4(날짜당 최대 24 · M-A) | 고른 경기 × 4(최대 24경기 = 96) |
| 그 달 · 다음 달 월간 일정 | 날짜마다 1 + 1 | **0** |
| 선수 재취득 · 신규 선수 | 기존대로 — 재취득은 상한 400, 신규는 아직 안 받은 수만큼 | **0** |
| 予告先発 · 공표 성적표 | 1 · 30(기존) | **0** |

**자동 경로의 한 실행 상한 — 논리 페이지와 HTTP 전송.**

| 경로 | 논리 페이지(`page_fetches`) | HTTP 전송(`http_attempts`) | 무엇이 묶나 |
|---|---|---|---|
| 정상(200 · 홉 없음) | 4 × 경기 ≤ **96** | = 논리 페이지 ≤ **96** | 경기 상한 24 |
| 같은 출처 리디렉트만(정상 응답) | ≤ 96 | 페이지당 ≤ 4 → **128 에서 멈춤** | HTTP 예산 |
| 고통 신호(재시도 대상 응답 · 예외 · 시간 초과)나 받기 실패 | 그 경기까지 | **그 경기 ≤ 32** + 앞 경기들 · 합 ≤ 128 | **회로 차단** — 그 경기 뒤로는 시작하지 않는다 |
| **절대 상한** | **96** | **128** | 경기 상한 · 시작 전 예산 검사 |

- **수동과 함께(날짜 상한 7을 나눠 쓴다 · 수동 `k` 일).**
  - 논리 페이지는 수동 `26k`(6경기 × 4 + 일정 2) + 자동 ≤ `4 × min(24, 6(7 − k))` 다. 최대는 **182**(`k = 7` · 2판 표와 같다)로, 기존 수동 최악과 같다.
  - HTTP 전송은 수동 쪽이 기본 `maxRetries` 3 이라 논리 페이지당 ≤ 16 이다(기존 경로 · 이 설계가 바꾸지 않는다). 자동 쪽은 ≤ 128 을 더한다.
- 하루 자동은 정시 3회 × 128 = **HTTP 384 · 논리 페이지 288** 이다. 재시도 슬롯은 0이다.
- npb.jp 는 검증자를 주지 않아(`archive.ts` 124~127행) 위 수는 전부 200 전체 본문이다.
- **불일치가 없는 실행 · 재시도 슬롯 · D6 의 사유로 건너뛴 실행은 `cli-games.ts` 를 띄우지 않으므로 요청이 0 늘어난다**(T9).

#### D7-8. `collect` 잡 45분 — 다시 계산(R2-1)

**한 경기 최악(그 경기만 고통을 겪는 경우 — 회로 차단 때문에 그런 경기는 실행당 하나다).**

| 단위 | 식 | 값 |
|---|---|---|
| 전송 하나 | 대기 ≤ 3초(`minDelayMs` · 268~272행) + 전송 ≤ 5초(시간 상한) | ≤ **8초** |
| 시도 하나 | 첫 전송 + 리디렉트 3홉 = 4전송 | ≤ 32초 |
| 페이지 하나 | 2시도 × 32초 + 백오프 3 + 6초(마지막 시도 뒤에도 잔다) | ≤ **73초** · 8전송 |
| **경기 하나** | 4장 × 73초 | ≤ **292초 = 4.87분** · **32전송** |

- 2차 리뷰가 제안한 식 「4장 × (2시도 × (1+3홉) × 간격 + 백오프)」 = 132초(2.2분)는 **전송 자체의 시간을 0으로 둔 값**이다. 여기서는 전송마다 시간 상한 5초를 더했다.
- 시간 상한이 없으면 이 식에 상한이 없다(M-R) — 그래서 D7-3 에서 시간 상한을 둔다.

**잡 최악.**

| 구간 | 값 | 근거 |
|---|---|---|
| 잡 시작 → 마지막 경기 시작 | **< 25.00분** | 경기마다 `now >= deadline` 이면 시작하지 않는다(D7-4) |
| 그 경기 최악 | 4.87분 | 위 표 |
| 다시 적재 | 1.71분 | M-L 최장(102.8초 · 분모 2) |
| 사후 감지 · 보고 · 이력 쓰기 | 0.05분 | M-M(0.43초) + 파일 쓰기 |
| 이 단계 뒤 → 잡 끝 | 11.43분 | M-J 최장(분모 3 · 깊은 시험 포함) |
| **합** | **43.06분 ≤ 45 · 여유 1.94분** | |

- 마지막 경기가 마감 직전에 시작해 최악으로 끝나는 경우가 이 합이다. 그보다 앞의 경기들은 마감 안에서 끝나므로 더해지지 않는다.
- 계획 시점에 이미 25분이 지났으면 받지도 다시 적재하지도 않는다(D6 의 8). 그때 이 단계는 감지·보고 몇 초뿐이다.
- **25분과 24경기를 다시 확인했다.**
  - **25분은 그대로다**: 위 합이 45 안이다. 선수 재취득이 상한 400까지 찬 날의 외삽(9.40 − 5.27 + 400 × 3.13초 ≈ 25.0분)에서도 아슬아슬하게 문이 열린다.
  - **24경기도 그대로다.** 다만 근거가 바뀌었다. 2판은 시간에서 거꾸로 냈지만, 이제 시간은 마감이 지킨다.
    - 24는 **L1 의 논리 페이지 상한**이다(실행당 96 · 하루 288).
    - 전형적인 정정(키 1~3개 × 7일 ≤ 21경기)을 한 실행에 담는 크기다(D12).
- **평소**(이번 사고 3경기 · 전부 200): 12전송 × 3.13초 + 102.8초 + 약 2초 ≈ **2.4분**. 정상 24경기: 96 × 3.13초 ≈ 5.0분 + 1.8분 ≈ 6.8분.

#### D7-9. 단계 시간 제한 · 자식 시간 제한 — 모형 밖의 고장을 담는 걸쇠

- 위 계산은 **망 쪽**(재시도 · 홉 · 시간 초과)을 상한으로 묶고, **국소 쪽**(적재 · 감지 · 파일 쓰기)은 실측 최장으로 둔다.
- 국소 쪽이 실측보다 크게 느려지거나 멈추는 것은 **모형 밖**이다. 그것은 아래 걸쇠가 담는다.
- **자식 시간 제한**(진입점의 `spawnSync` `timeout` · 넘으면 그 자식의 실패로 센다). 그 뒤에도 보고·다음 이력은 쓴다.
  - `git fetch` 60초 — 넘으면 작업 트리 사본으로 물러선다(D8).
  - `crosscheck.ts` 각 120초(실측 0.43초).
  - `cli-games.ts` = `max(0, deadline − now) + 292초 + 60초`.
  - `load-archive.ts` 600초(실측 최장 102.8초).
- **단계 시간 제한 30분.** 정상 동작에서 가장 긴 단계는 ≈ 27.0분이다(D1).
- 국소 쪽이 멈춰 잡 시간 제한(45분)에 걸리면 GitHub 이 잡을 취소한다. 이 경우는 **다른 단계(`수집·적재` 등)가 멈출 때와 같은 노출**이고 이 설계 밖이다.
  - 그때 남은 `always()` 단계는 취소 처리 중에 돈다고 보지만, GitHub 의 동작이고 이 저장소에서 잰 적은 없다.

#### D7-10. 다시 적재

- 기존 `node packages/store/tools/load-archive.ts data/archive data/bb.sqlite --max-writes 5000000` 을 그대로 부른다. ⚠`--max-writes` 를 빠뜨리면 기본 100,000행에서 멈춘다(지금 한 번 적재가 889,666행이다).
- **기록된 경기(`recorded`)가 1개 이상일 때만** 한다. `prepare_failed`·되돌린 `commit_failed` 는 아카이브가 사전과 같다.

### D8. 시도 이력 — 상태 전이 · 저장 위치 · 복원·재실행·동시 실행

**무엇을 보존하나.** 핵심은 결함 키마다의 **일화 시작 시각**(`first_seen_at`) 하나다. 판정은 DB 의 `game.fetched_at` 과 맞대어 한다(E2).
- 그래서 (키, 경기)는 일화마다 한 번이고, 같은 날짜는 같은 키에 대해 한 번이다.
- **`attempts` 는 기록이지 판정 근거가 아니다.** 판정을 목록에 맡기면 세대 복원 때 틀린다. DB 의 `fetched_at` 은 아카이브와 함께 되돌아가므로 스스로 맞춰진다.

**저장 위치 — `ops/correction-refetch.json`(git · 공개 저장소).**
- 워크플로가 매 실행 원격 `main` 에 커밋하는 `ops/` 의 넷째 파일이다(지금 3파일 · 684행).
- **공개 저장소**(`muji-j/basenine`)다. 그래서 **수치(우리 값 · 공표 값)를 넣지 않는다.** 수치는 실행 로그의 보고에만 나온다.

**형식(스키마 1 · 결정론적 바이트 · R2-4).**
- `keys` 객체의 키는 **코드 단위 오름차순**으로 넣는다(JSON 직렬화 순서 = 삽입 순서).
- `attempts` 는 `date` 내림차순, 같은 날짜면 `at` 오름차순이다.
- 2칸 들여쓰기에 끝 줄바꿈이다.
```json
{
  "schema": 1,
  "keys": {
    "2026|t|pitching|91095136|暴投": {
      "direction": "ours_more",
      "first_seen_at": "2026-09-28T20:40:57Z",
      "first_seen_run": "36480899578",
      "last_seen_at": "2026-09-28T20:51:02Z",
      "attempts": [
        { "date": "2026-09-23", "at": "2026-09-28T20:51:03Z", "run": "36480899578" },
        { "date": "2026-09-17", "at": "2026-09-28T20:51:03Z", "run": "36480899578" },
        { "date": "2026-05-13", "at": "2026-09-28T20:51:03Z", "run": "36480899578" }
      ],
      "exhausted_at": "2026-09-28T20:51:03Z"
    }
  }
}
```
(모양 예시다. 「세 날짜를 다 받았는데도 결함이 남았다」고 가정했다. 실제 사고였다면 9/17 을 받는 순간 풀려 ④ 에서 이 키가 지워진다.)

**갱신 규칙 `updateHistory(history, detect, collectStartedAt, now)`(순수 · `scripts/correction-plan.ts`).**

| 감지 결과 | 키가 결함 목록에 있다(대상 · 해석됨) | 목록에 없다 | 다른 시즌의 키 |
|---|---|---|---|
| `unmeasured` · 감지기 오류 | 바꾸지 않는다 | 바꾸지 않는다 | 바꾸지 않는다 |
| 측정 성공 · `genzai` · 결함 ≤ 20 | 없으면 **새 일화**(`first_seen_at` = 잡 시작). 있으면 `last_seen_at` 갱신. 방향이 다르면 새 일화로 갈아 끼운다 | **지운다**(풀렸다) | 지운다 |
| 측정 성공 · 그 밖 | 있으면 `last_seen_at` 갱신 · 새로 만들지 않는다 | 지운다 | 지운다 |

- 새 일화의 시작을 잡 시작으로 잡는 이유: 이 실행이 몇 분 전에 받은 사본은 같은 실행 안의 최신이다. 그래서 E2 로 뺀다.
- 잡 시작을 모르면(D6 의 8 의 `started_at_unknown`) 새 일화의 시작을 `now` 로 잡는다. 후보가 넓어지는 쪽이라 안전하고, 그 실행은 받지 않는다.

**상태 전이 — 한 실행 안에서의 순서를 고정한다(R2-5).**

| 순 | 전이 | 하지 않는 경우 |
|---|---|---|
| ① | 사전 감지 결과로 `updateHistory(pre)` | 사전이 `unmeasured`·오류면 이력은 그대로다(이후 ③~⑤ 도 없다) |
| ② | 계획 · 받기(D6 · D7) | D6 의 사유로 건너뛰면 받지 않는다 |
| ③ | **①의 결과 이력의 키에**, 그 키의 남은 후보 가운데 **`recorded` 된 경기가 있는 날짜**를 `attempts` 로 붙인다(`at` = 진입점의 `now` · `run`). 다시 적재의 성패와 무관하다 — 아카이브에는 새 사본이 있다 | 받은 경기가 없으면 없다 |
| ④ | 사후 감지 결과로 `updateHistory(post)` — 목록에 없는 키는 **지운다**(풀림), 남은 키는 `last_seen_at` 을 갱신하고, post 에서 처음 보인 키는 위 표대로 만든다 | **사후가 `unmeasured`·오류면 ④ 를 하지 않는다**(③ 까지의 이력을 쓴다). `recorded` 경기가 0이면 사후 감지를 따로 돌리지 않고 사전 결과를 사후로 쓴다(DB 가 그대로다) |
| ⑤ | **④ 뒤에 남은 키에 대해서만** 소진을 판정한다. 남은 날짜(다시 적재 뒤의 DB 기준)가 0이면 `exhausted_at` 을 처음 한 번 찍고 `소진 — 런북 §7-I · <키> · 후보 N일을 다 다시 받았는데 남았다` 를 찍는다 | ④ 를 안 했으면 하지 않는다. 자동이 허용되지 않은 실행(D6 의 1~9 중 하나에 걸림)이면 하지 않는다 |

- **해결된 키의 시도 기록은 남기지 않는다** — ④ 가 키째 지운다.
  - 이력은 「지금 진행 중인 일화」의 판정 상태(E2 · 소진)다. 풀린 일화는 더 판정할 것이 없다.
  - 남겨 두면 공개 저장소의 파일이 끝없이 자란다.
  - 풀린 일화의 시도는 그 실행의 보고(로그)에 남는다. 영속하는 정정 기록은 별도 결정이다(§7 범위 밖).
- **다시 적재가 실패하면 사후 감지를 하지 않는다**(D9 의 6). 그래서 ④·⑤ 도 없다 — DB 가 이번에 받은 사본을 아직 모르는 채로 「풀렸다」나 「소진」을 찍지 않는다. ③ 의 시도 기록은 남는다. 다음 실행의 `수집·적재` 가 아카이브 전체를 적재하면 DB 가 맞춰진다(D14 ④).

**읽기·쓰기 — 「원격 최신에서 읽고, 읽은 판 위에서만 쓴다」.**
1. **읽기**: `git fetch --quiet origin "$GITHUB_REF_NAME"`(60초) 뒤 `git show "origin/$GITHUB_REF_NAME:ops/correction-refetch.json"` 으로 읽는다. 「없음」과 「실패」는 `git cat-file -e` 로 가른다.
   - **체크아웃 사본을 읽지 않는다** — 줄을 섰던 실행의 `github.sha` 는 낡았다(659~661행).
   - fetch 가 실패하면 작업 트리 사본으로 물러서고 `::warning::` 을 찍는다.
2. **쓰기**: 읽은 바이트의 sha256(없었으면 `absent`)을 `history.base` 에 **먼저** 쓴다. 바뀐 경우에만 `history.next.json` 을 `.tmp`+`rename` 으로 쓴다.
3. **반영**: `기록 갱신과 커밋` 이 `reset` 뒤 원격 파일의 sha256 이 `history.base` 와 같을 때만 복사한다(D1). 다르면 덮어쓰지 않고 경고한다.

**복원 · 재실행 · 동시 실행.**
- **복원**: 세대가 되돌아가면 다시 받았던 경기의 box 사이드카와 DB 의 `fetched_at` 이 함께 돌아간다 → E2 에서 다시 후보가 되어 한 번 더 받는다. 보고는 「되돌려짐(복원) — 다시 후보」로 표시한다.
- **재실행**: `collect` 가 처음부터 돌아 `job-start` 가 새로 찍힌다. `decide` 출력(`slot`)은 원래 실행의 것을 다시 쓴다. 이력은 원격 최신에서 읽는다.
- **동시 실행**: `concurrency: daily-collection · cancel-in-progress: false`(115~119행)라 직렬이다.
  - 이 파일에 쓰는 것은 이 워크플로와 사람(§7-I 의 키 지우기)뿐이다. 사람이 실행 도중 커밋하면 대조가 그 실행의 반영을 버린다.
  - 잃는 것은 최대 한 실행치이고, 이미 받은 경기를 많아야 한 번 더 받는다.
- **커밋이 실패하면**(3회 푸시 경합 · 696행)도 같다. 그 단계가 빨개진다.

### D10. 관문과 알림 — 풀리지 않으면 지금처럼 막는다(사용자 결정 ②)

- `외부 대조` 단계는 **판정을 바꾸지 않는다.** 실패할 때만 이 실행의 `report.txt` 를 다시 찍는다(D1).

- **런북 `docs/operations/deploy.md` §7-I 신설**(구현 단계에서 쓴다)
  1. 증상
  2. 이번 사고와 복구 실행
  3. 자동 재수집이 하는 일과 보고 첫 줄 읽는 법
  4. 「해 보지 않았다」 사유 코드별 할 일(D6 의 10개)
  5. **「해 봤으나 실패」 갈래별 할 일**(D14 표)
     - 섞인 세트는 §7-E 다.
     - 받기 실패와 회로·마감은 다음 정시 실행을 기다린다.
  6. **「소진」일 때**
     - ⑴ 보고의 키와 후보 날짜를 본다.
     - ⑵ npb.jp 의 지금 박스와 공표표를 사람이 맞댄다(npb 내부 불일치면 기다린다).
     - ⑶ 우리에게 행이 없는 경기가 의심되면 그 날짜를 수동 `refetch_dates` 로 준다.
     - ⑷ 일화를 다시 열려면 `ops/correction-refetch.json` 에서 그 키를 지우는 커밋을 한다.
  7. 수동 실행은 하루에 여러 번 누르지 않는다(L1).
- `refetch_dates` 입력 설명(101행)에 「남은 자리는 자동 재수집이 쓴다」를 한 구절 더한다.

### D11. 멱등 · 판(M4/M5)

- **멱등.**
  - 같은 경기를 두 번 받아도 본문이 같으면 「봤다」만 남는다. 판 가드는 같거나 새 판만 받는다.
  - 되돌리기는 사전 **바이트 그대로**를 되쓴다. 그래서 되돌린 경기는 받기 전과 같다.
  - 같은 실행에서 이 단계를 두 번 돌려도 두 번째는 E2 로 후보가 빈다.
- **판 표지(P2-9).** `game.revision` 은 경기 행의 상태·점수·안타·실책·구장·대회·팀 코드가 바뀔 때만 오른다(`load.ts` 243~265행). 자식 행만의 정정(이번 사고의 暴投)에서는 그대로다.
  - 이 설계가 기대는 것은 `game.fetched_at` 하나다.
  - 사이드카 `revision` 도 표지가 아니다. 9/17 재수집에서 20장이 **전부** 바뀌었다.
- **보관소(P2-8)**: 정상 경로는 아카이브와 DB 를 같은 업로드로 올린다(D1 · D14).

- 정정 하나의 발자국은 전형 4~7건, 극단 약 12건이다(안타↔실책 + 장타·타점 + 투수 둘의 자책).
- 체계적 원인의 실측 최소는 ≥ 79건이다(M-O). 20은 그 사이에서 고른 값이다.
- ⚠작은 체계적 원인(2024 `犠失` · 6건)은 이 상한으로 못 가른다. 그때는 소진으로 사람에게 간다. 낭비는 실행당 HTTP 128 로 묶인다.

### D14. 실패 갈래와 보관소 업로드 — 업로드 조건은 바꾸지 않는다(R2-3)

**업로드 조건(그대로).**
- `수집 후 재검증`(`guard`)은 `always()` 다(486~491행).
- `보관소에 올림` 은 `always() && guard 성공` 이다(502행).
- DB 는 `db-check` 통과 시 함께 올린다(525~531행).
- 기존 철학은 이렇다: **아카이브는 소급 불가라 실패해도 올린다 · DB 는 아카이브에서 다시 만드는 파생물이다**(523~524행).
- 이 정책을 정정 단계 실패에도 그대로 쓴다. 근거는 아래 코드 확인과 갈래표다.

**코드로 확인한 것(파일:행).**
- **적재는 경기 단위로 원자적이다.**
  - `writeGameGuarded` 는 `db.transaction` 이다(`packages/store/src/version-guard.ts` 45~52행). 그것은 `BEGIN … COMMIT`, 예외면 `ROLLBACK` 이다(`packages/store/src/db.ts` 67~77행).
  - 성립 경기의 콜백(`packages/store/tools/load-archive.ts` 657~834행) 안에 다음이 **전부** 들어 있다: 타격·투구 삭제(669~670) · `upsertGame`(672) · 타격·투구 행 · `replacePaEvents`(745) · `replaceRunnerEvents`(783) · `replaceQuarantine`(833).
  - 미성립 경기도 같다(503~528행).
  - → **반쯤 적재된 경기는 없다.**
- **실패한 경기는 건너뛰고 나머지를 쓴다.**
  - 쓰기 전 검사는 각각 그 경기를 `continue` 로 건너뛴다. 대상은 읽기(376~382) · 취득 시각(401~410) · 판 가드(423~427) · 본문 대조(430~434) · 세트 대조(435~439) · 파싱(444~450) · 대회 판정(464~478)이다.
  - 쓰기 예외는 그 경기만 되돌리고 다음 경기로 간다(835~839행 → `noteWriteFailure` 270~282행). 단, 되돌리기 자체가 실패해 트랜잭션이 열린 채면 **다시 던져 적재를 멈춘다**(276행).
  - 반복 뒤 전역 쓰기 두 곳 — 명단 빈칸 채우기(894~907)와 시즌 표시명(916~923) — 은 각각 한 트랜잭션이다. 둘 다 「빈 자리만 채우기」·upsert 라 다시 해도 같다.
  - 실패가 하나라도 있으면 종료 1 이다(1033~1037행).
- **매 실행 아카이브 전체를 다시 적재한다.**
  - `scripts/update.ts` 211~217행은 `load-archive.ts <archive> <db>` 를 **`--from`/`--to` 없이** 부른다.
  - 적재기는 `walk(archiveRoot, "box.html.gz")`(`load-archive.ts` 348행)로 전부 훑는다. 날짜 거르기는 그 인자가 있을 때만 한다(356~357행).
  - → **DB 의 부분 갱신은 다음 실행의 `수집·적재` 가 아카이브 기준으로 다시 맞춘다.** 다만 같은 원인으로 또 실패하는 경기는 적재되지 않으므로 옛 행에 머문다(그 실행은 종료 1 로 시끄럽다).
- **`guard` 와 `db-check` 는 세트 섞임을 보지 않는다.**
  - `archive-guard.ts` 103~128행은 파일 수 감소와 바이트 감소만 본다.
  - `db-check.ts` 29~48행은 `PRAGMA integrity_check` 만 한다.
  - → 섞인 세트를 막는 것은 **업로드가 아니라 G4(적재기)** 다. 그래서 자동 경로가 섞인 세트를 **만들지 않는 쪽**(D7-5 되돌리기)을 택했다.
- **위 확인은 2차 지적 R2-3 의 전제와 맞는다.** 정책을 고칠 사실은 나오지 않았다.

## 6. 기각한 안

- **`update.ts` 를 그대로 다시 부르기**(1판) — 일정 2장 · 선수 재취득 · 予告先発이 다시 돌고 수동과 겹치면 14일이다.
- **날짜 단위로 그날 전 경기 받기**(1판) — 최대 6배를 받는다. 날짜는 상한의 단위로만 남긴다.
- **관문을 느슨하게** — 사용자 결정 ②로 기각.
- **지난 N일을 매 실행 다시 받기** — N 의 근거가 없고 L1 에 반한다.
- **박스 한 장만 다시 받기** — 판 가드가 네 장 세트를 대조한다.
- **`fetched_at` 오름차순** — 초기 구축 사본을 먼저 집는다(M-G).
- **받은 날짜 목록을 판정 근거로** — 세대 복원 때 틀린다.
- **이력을 데이터 저장소에** — 판정이 DB 기준이라 같은 수명이 필요 없다. 사람의 키 지우기가 번거롭다. `data/archive` 안이면 `archive-guard` 가 「줄었다」로 멈춘다.
- **재시도 슬롯에서도 받기** — 하루 6회가 되어 L1 에서 멀어진다.
- **`seasonIsOver()`** — 묻는 것이 다르다.
- **결함 상한을 대상 키 수로** — 관문 로그의 수와 달라진다.
- **감지 모드를 별도 도구로** — 비교 로직이 두 벌이 된다(M1).
- **(3판) 2차 리뷰가 권한 「임시 DB·변경 파일 스테이징에서 정정하고 사후 대조까지 성공하면 승격」** — 조정자 결정으로 기각했다.
  - D14 의 코드 확인대로 적재는 경기 단위 원자이고 매 실행 전체를 다시 적재하므로, DB 쪽은 승격 없이도 다음 실행에서 맞춰진다.
  - 아카이브 쪽 위험은 섞인 세트 하나인데, 그것은 경기 단위 되돌리기(D7-5)로 만들지 않는다.
  - 스테이징은 아카이브(267 MiB)·DB(170 MB)를 매번 복사하고, 승격 실패라는 새 갈래를 만든다.
- **(3판) 업로드를 정정 단계 성공에 묶기** — 그날 받은 소급 불가 페이지까지 버린다(D14).
- **(3판) `archiveGame` 자체를 고쳐 G3b 를 되돌리게(모든 경로)** — 평소 수집 경로의 동작이 바뀐다. 선례 설계는 G3b 를 G4 로 받기로 정했다. 자동 경로만 되돌린다 — 사람이 보지 않는 시각에 업로드 바로 앞에서 돌기 때문이다.
- **(3판) `PoliteFetcher` 의 기본 `maxRetries` 를 1로** — 평소 수집이 予告先発처럼 거르면 영영 못 받는 것을 받는다. 자동 경로에만 준다.
- **(3판) 경기 안에서도 마감을 보고 끊기**(페이지 단위) — `archiveGame` 이 네 장을 한 단위로 받으므로 고쳐야 한다. 대신 한 경기의 최악을 계산에 넣었다(4.87분).
- **(3판) HTTP 예산을 전송 중에 거부하기**(감싼 `fetchImpl` 이 던지기) — PoliteFetcher 가 그 예외를 일시 오류로 보고 백오프(3+6초)를 돈다. 경기 시작 전 검사가 같은 상한을 낭비 없이 지킨다.

## 7. 뒤집힐 조건 · 남는 위험 · 범위 밖

**뒤집힐 조건**
- **정정 지연의 분포를 재면** 순서(최근부터)와 상한(24경기 · 7일)을 다시 본다(표본 1건).
- **이후 단계 실측(11.43분)·재적재(1.71분)·잡 제한(45분)·fetcher 상수가 바뀌면** 마감 25분을 다시 낸다(T13 이 대조한다).
- **전송 시간 실측이 5초에 가까워지면**(지금 최대 0.191초) 시간 상한과 D7-8 을 다시 본다.
- **관측 정정이 결함 20건을 넘거나, 체계적 원인이 20건 아래로 관측되면** `AUTO_REFETCH_MAX_DEFECTS` 를 다시 본다.
- **npb 가 완결 시즌에서 `現在` 를 지우는 시점이 관측되면** D3 를 고친다.

**남는 위험**(전부 「소진 또는 실패 → 관문이 막음 → 런북」으로 사람에게 간다 · 조용히 틀리지 않는다)
- npb 내부 불일치(공표표만 고침).
- 공표표가 박스보다 먼저 고쳐짐 — E2 가 놓친다. 키를 지우면 다시 찾는다.
- o<p 인데 우리에게 행이 없는 경기.
- 같은 키에 일화 안에서 두 번째 정정이 생김.
- 새 키에서는 이 실행에서 막 받은 경기도 뺀다.
- 다시 받은 경기에 다른 선수의 박스 선행 정정이 딸려 옴 — 공표표가 따라올 때까지 새 결함이다. 그동안 HTTP 는 실행당 128 로 묶인다.
- 이름 짝짓기가 바뀌어 키가 「풀렸다」로 지워짐.
- **(3판) 5초보다 느린 정상 응답도 실패로 센다** → 회로가 열린다. 느린 날에는 자동 재수집이 덜 돈다(의도 · L1).
- **(3판) 이중 고장(되돌리기 실패)과 기록 도중 프로세스 사망** → 섞인 세트 → 다음 실행의 `수집·적재` 실패 → §7-E(D14 ③·⑤).

- 공개 로그 노출 — 보고에는 이름·수치가 나온다(관문 로그와 같은 층). 이력 파일에는 수치가 없다.

**범위 밖(기존 한계)**
- 자식 행만의 정정은 `game.revision` 을 올리지 않는다. 정정 전 본문은 보관소 세대 3개에만 남는다. 영속하는 정정 기록은 별도 결정이다.
- 평소 수집 경로의 G3b(섞인 세트를 G4 로 받는 설계)와 기본 재시도 4회.

## 2. 목표와 비목표

- **목표 1**: 외부 대조가 진행 중 시즌에서 찾을 결함 후보를 **관문보다 먼저** 감지한다. 그 차이를 만들 수 있는 **경기**를 그 실행 안에서 다시 받고 다시 적재한다. 정정이면 그 실행에서 풀린다. 이번 사고라면 3경기 · 12요청이다(D6 재현).
- **목표 2**: 풀리지 않으면 **지금처럼 배포를 막는다**(사용자 결정 ②). 그리고 「해 봤는데 남았다」와 「해 보지 않았다(사유)」를 **로그만으로** 가를 수 있게 한다.
- **목표 3**: 결함 후보가 없는 실행에서는 **요청이 하나도 늘지 않는다**(시험으로 고정 · D13).
- 비목표:
  - 외부 대조 관문의 판정 기준을 바꾸는 것(문턱 · 허용 건수).
  - 완결 시즌의 자동 재수집. 완결 시즌의 불일치는 정정이 아니라 우리 파서·집계의 회귀일 가능성이 크다. 관문이 그대로 막는다.
  - 지난 경기를 주기적으로 전부 다시 받는 것(L1 — 정정 지연을 재 본 적이 없다).
  - 우리에게 **행이 없는** 경기를 찾는 것(§7 — o<p 의 한계).
  - 자식 행만 바뀐 정정에 판 표지를 다는 것(§7 — M4 의 기존 한계).

## 4. 한 실행의 흐름

1. **(새) 잡 첫 단계** — 잡 시작 시각을 낸다(`steps.job-start.outputs.at`).
2. `수집·적재`(기존 · 그대로) — 수동 `refetch_dates` 가 있으면 여기서 그 날짜의 경기를 받는다.
3. `공표 성적표 갱신`(기존 · 그대로) — 정답지 30장.
4. **(새) `정정 감지 · 자동 재수집`** — 차례는 아래와 같다.
   1. 이력 읽기(origin 최신)
   2. 사전 감지(`--emit`)
   3. 이력 갱신
   4. 계획
   5. 받기(`cli-games.ts`)
   6. 다시 적재
   7. 사후 감지(`--emit`)
   8. 보고 쓰기 · 다음 이력 쓰기
   9. 종료코드 내기
5. `수집 후 재검증` → `보관소에 올림`(아카이브 + DB) → `기록 갱신과 커밋`(이력 반영 · 기존 단계에 몇 줄을 더한다).
6. `파서 자기 검증` → `득점 대조` → **`외부 대조`(관문)** — 판정은 그대로이고, 실패하면 4의 보고를 다시 찍는다 → `화면 생성` … `배포`.

- **업로드 앞이어야 하는 이유(P2-8 정정).** 정상 경로의 `보관소에 올림` 은 세대 tar(`store-YYYYMMDD.tar` = `data/archive`)와 `bb.sqlite.gz` 를 **함께** 올린다(525~527행에서 `assets` 를 둘로 정하고 564행에서 올린다). 「DB 를 올리지 않는다. 아카이브만 올린다」는 `db-check` 가 실패한 **예외 분기**(528~531행)다. 1판은 그 예외를 일반 동작으로 적었다.
  - 업로드 앞에 두는 진짜 이유는 이것이다: 정정된 아카이브와 정정된 DB 가 **같은 세대**에 실려야 다음 실행이 둘 다 정정 뒤의 것으로 복원한다.
  - 뒤에 두면 다음 실행이 정정 전 사본을 복원하고, 다시 받은 페이지는 사라진다. 그래도 조용히 틀리지는 않는다 — D5 의 제외 규칙이 DB 의 `fetched_at` 을 보므로 그 경기는 다시 후보로 돌아온다. 요청만 다시 든다.
- 기존 `외부 대조`(관문 · 728~762행)는 이 단계 **뒤의 DB** 로 다시 잰다. 판정과 종료코드는 바꾸지 않는다.

**`if:` — 두지 않는다(= `success()`).**
- 앞 단계 가운데 `continue-on-error` 가 아닌 단계(체크아웃 … `복원 검증` · `수집·적재`)가 하나라도 실패한 실행에서는 **돌지 않는다.**
- 그 실행은 이미 그 실패로 빨갛다. 관문도 같은 이유(`success()`)로 돌지 않는다. 정정은 다음 실행이 다시 감지한다.
- `드래프트 원본 복원`·`드래프트 적재`·`공표 성적표 갱신` 은 `continue-on-error` 라서 이 판정에 영향을 주지 않는다. 공표표를 못 받았으면 아카이브의 옛 스냅숏으로 감지한다 — 관문과 같다.

### D2. 감지 — `crosscheck.ts --emit` 의 상태 계약

**호출 형태.** `node packages/aggregate/tools/crosscheck.ts <db> <season> --archive <dir> --emit <path>`

| | `--emit` 없이(관문 · **불변**) | `--emit` 있음(감지 모드 · 새) |
|---|---|---|
| 사람용 출력 | 지금 그대로 | **지금과 같은 것을 찍는다** |
| 측정 성공 · 결함 0건 | 종료 0 | 종료 **0** · `status: "no_defects"` |
| 측정 성공 · 결함 N건 | 종료 1 | 종료 **0** · `status: "defects"` |
| 측정 실패(아래 닫힌 목록) | 종료 1(대부분) 또는 잡히지 않은 예외 | 종료 **2** · `status: "unmeasured"` |
| 예상 밖 예외(버그) | 0 이 아닌 종료 | 0·2 가 아닌 종료 · **JSON 을 약속하지 않는다** |

**측정 실패의 닫힌 목록(`reason`).**
- `asof_split` — 공표표 기준일이 장마다 다르다. 지금은 `publishedThrough()` 가 98~104행에서 종료 1 로 끝낸다.
- `tables_missing` — 기대한 **24장**(12구단 × `idb1`·`idp1`) 가운데 못 읽은 장이 있다. 지금은 경고만 찍고 진행한다(221~222행 · 273~276행). ⚠감지 모드는 관문보다 엄격하다 — **자동 재수집의 근거로는 전 구단을 잰 결과만 쓴다.**
- `table_parse_error` — 공표표 해석이 던졌다(`StatsParseError`: 열 수 · 수로 못 읽는 칸 · 한 장 안의 기준일 둘). 지금은 잡히지 않은 예외로 죽는다.
- `compared_zero` — 대조한 선수가 0명이다. 지금은 392~399행에서 종료 1 이다.
- **둘 이상 걸리면 위에서부터 처음 것 하나**만 `reason` 에 적는다: `asof_split` → `table_parse_error` → `tables_missing` → `compared_zero`. 예를 들어 공표표가 0장이면 `tables_missing` 이다(대조도 0명이지만). 나머지는 `reason_detail` 에 사람이 읽는 글로 덧붙인다.

**판정은 순수 함수 한 벌.** `packages/aggregate/src/crosscheck-classify.ts` 에 `crosscheckEmitStatus({ asOfDates, tablesRead, tablesExpected, parseError, comparedPlayers, defects })` 를 둔다. 돌려주는 것은 `{ status, reason }` 이고, 종료코드는 `status` 에서 낸다. 시험이 직접 부른다(D13).

**결과 JSON(스키마 1).**
```json
{
  "schema": 1,
  "season": 2026,
  "competition": "regular",
  "status": "defects",
  "reason": null,
  "reason_detail": null,
  "as_of": { "date": "2026-10-01", "source": "genzai" },
  "tables": { "expected": 24, "read": 24, "with_genzai": 24 },
  "compared": { "players": 1022, "fields": 18275 },
  "unmatched": { "ours": 6, "published": 99 },
  "folded": 702,
  "defects": [
    { "team": "t", "kind": "pitching", "player_id": "91095136", "name": "髙橋",
      "field": "暴投", "ours": "3", "published": "2" }
  ]

```
- `as_of.source` 는 넷 중 하나다.
  - `genzai` — 읽은 24장 **전부**에 같은 `現在` 날짜가 있다.
  - `partial` — 일부에만 있다.
  - `absent` — 하나도 없다 · `date: null`.
  - `override` — `--through` 가 주어졌다.
  - ⚠도구 안에서는 `absent` 를 지금처럼 `9999-12-31`(자르지 않음)로 다룬다. JSON 에는 `null` 로 적는다(M11 — 「자르지 않음」은 날짜가 아니다).
- `defects` 는 정의 차이로 접히지 **않은** 것(`classifyDiff` 가 `null`)만 담는다. `ours`·`published` 는 **도구가 비교한 문자열 그대로**다. 수로 읽는 것은 계획기가 D4 의 표로 한다.
- **원자적으로 쓴다.** `<path>.tmp-<pid>` 에 쓰고 `rename` 한다(같은 디렉터리 · POSIX 에서 원자적). 부르는 쪽은 호출 **전에** `<path>` 를 지운다. 그래서 「파일이 있다」는 「이번 호출이 썼다」와 같은 말이다.
- `unmeasured` 에서도 JSON 을 쓴다(`defects: []`). 0·2 가 아닌 종료에서는 파일이 없을 수 있다. 부르는 쪽은 그것을 「감지기 오류 — 자동 안 함」으로 읽는다(D9).

**`player_id` 와 `team` 운반(P2-7 · 관찰 b).**
- `BAT_SQL` 에 `b.player_id AS player_id` 를, `PIT_SQL` 에 `pl.player_id AS player_id` 를 SELECT 한다. 지금은 `GROUP BY` 에만 있어서 JS 행에서 사라진다(172~209행).
- `CrosscheckDiff` 에 `playerId: string` 을 더한다(`crosscheck-classify.ts` 13~22행). `cmp()` 가 그것을 채운다. `team` 은 이미 있다(`team.code`).
- **공표 쪽과 짝짓는 것은 지금처럼 이름이다.** 공표표에 ID 가 없다(도구 머리말). 이 경계는 검증 도구의 몫이고 바꾸지 않는다.
- **그 뒤는 ID 로만 간다**(M10). 후보 경기 조회는 `player_id` 와 팀으로 하고, 이름으로 우리 행을 다시 찾지 않는다(D5).
- 사람용 출력은 바꾸지 않는다. ID 는 JSON 에만 나온다.
- 같은 SQL 범위 조각을 후보 조회와 나눠 쓴다(M1 · D5).

### D3. 시즌 상태 — 공표표에 `現在` 가 있을 때만 자동

- **어느 시즌을 감지하나**: 새 단계가 시계를 한 번 읽어(M6) 그 시각의 **JST 연도**를 쓴다. `공표 성적표 갱신` 이 받는 시즌(`TZ=Asia/Tokyo date +%Y`)과 같은 규칙이다. 그 시즌의 공표표가 아카이브에 없으면(1~3월) `tables_missing` 이 되어 자동은 하지 않는다.
- **자동은 `as_of.source == "genzai"` 일 때만 한다.** 그 밖이면 받지 않고 사유를 찍는다.
  - `absent` — 「24장 어디에도 기준일(現在)이 없다 — 완결 시즌이거나 문구가 바뀌었다(못 가른다) · 자동 재수집 안 함 · 관문이 판정한다」. 관문은 지금처럼 자르지 않고 가장 엄격하게 잰다(`crosscheck.ts` 109~117행).
  - `partial` — 「일부 장에만 기준일이 있다 — 갱신 중이거나 문구가 바뀌는 중 · 자동 재수집 안 함」.
  - `override` — 「`--through` 로 사람이 정한 기준일이다 · 자동 재수집 안 함」.
- **왜 `seasonIsOver()`(`packages/store/src/season-over.ts`)를 안 쓰나.** 그 함수가 답하는 것은 「우리 데이터로 보아 시즌이 끝났나」다(더 나중 시즌 경기가 있거나 일본시리즈 4승).
  - 자동 재수집에 필요한 것은 다르다. ⑴ 공표표가 **기준일로 자른 스냅숏**이어야 기준일 뒤의 경기를 후보에서 뺄 수 있다. ⑵ npb 가 그 시즌을 **아직 고치고 있어야** 한다.
  - `現在` 가 바로 그 표지다. 그것이 없을 때의 두 경우(완결 · 마크업 파손)는 **둘 다 자동을 하지 않는 쪽이 맞다.** 완결이면 이 설계가 겨냥한 사건이 아니고, 파손이면 기준일 읽기가 깨진 것이다.
- ⚠npb 가 완결 시즌 페이지에서 `現在` 를 **언제 지우는지는 안 쟀다**(`packages/parser/src/stats.ts` 머리말). 지우기 전이면 자동이 돌고, 지운 뒤면 돌지 않는다.

### D4. 항목 대응표 — 닫힌 표(crosscheck 의 비교 항목 35개 전부)

- **정본은 `packages/aggregate/src/crosscheck-fields.ts`**(새)다.
  - **import 가 0개인 잎**으로 둔다(데이터와 문자열 함수뿐이다). `package.json` 에 서브패스 `"./crosscheck-fields"` 를 연다.

- **표가 빠짐없는지 시험이 지킨다**(D13). `crosscheck.ts` 의 비교 라벨(`c("…"` · `cmp(…, "…", …)`)을 역할별로 뽑은 집합이 이 표와 **정확히 같아야** 한다.
- `x` 는 `batting_line b` 또는 `pitching_line pl`(아래에서 `x` 로 통일)이다. **「출장」은 범위 안에 그 선수의 행이 있는 경기**다.

### D5. 후보 경기와 제외 규칙 — ID 로만

**결함 키** = `시즌|팀|역할|player_id|항목`(예: `2026|t|pitching|91095136|暴投`). 키는 D4 에서 「대상」이고 값 해석이 된 결함에만 만든다.

**후보 조회(한 키당 한 번 · ID 로만 · M10).** `crosscheckScope("x")` 는 crosscheck 의 두 SQL 이 쓰는 **같은 조각**이다. 지금 `BAT_SQL`·`PIT_SQL` 의 `WHERE` 를 옮겨 와서 셋이 나눠 쓴다(M1 — 「후보 경기는 대조가 합계를 낸 바로 그 행들이다」).
```sql
SELECT g.game_id, g.game_date, g.fetched_at, <경기 값 식> AS value
FROM <batting_line|pitching_line> x JOIN game g ON g.game_id = x.game_id
WHERE <crosscheckScope("x")>            -- season · played · regular · game_date ≤ as_of · 그 팀 쪽
  AND x.player_id = ?
  AND (<o>p 이면 그 항목의 술어 · o<p 이면 1 = 1>)
ORDER BY g.game_date DESC, g.game_id
```
- 실행계획과 시간은 M-E 다(기존 색인 · ≤ 1.0ms). 키는 많아야 20개(D12)라 조회 합계는 수십 ms 다.
- **팀 조건이 이적을 처리한다.** 한 시즌에 두 팀의 행을 가진 선수는 그 팀 쪽 경기만 후보다(M-D).

**제외 규칙 — 후보에서 빼는 것.**
1. **E1 기준일 뒤**: `game_date > as_of.date` 는 범위 조각이 이미 뺀다.
2. **E2 일화 시작 뒤에 본 사본**: `game.fetched_at ≥ 키의 first_seen_at`.
   - `game.fetched_at` 은 적재기가 **box 사이드카의 `checkedAt ?? fetchedAt`** 을 넣는 칸이다. 뜻은 「그 경기 박스를 마지막으로 본 시각」이다(`packages/store/src/version-guard.ts` 4~6행).
   - 네 장 세트가 다 성공하면 바뀌었든 안 바뀌었든(`markSeen`) 그 시각이 받은 시각으로 오른다. **한 장이라도 실패하면 아무것도 안 쓰므로 오르지 않는다**(`archive.ts` 306~328행).
   - 그래서 일화가 시작된 뒤에 본 사본은 「결함이 보인 뒤의 판」이다. 우리 자동 재수집의 결과든 평소 수집(어제 경기 · 따라잡기 · 수동)의 결과든 같다.
   - 비교는 `Date.parse` 로 한다. `fetched_at` 을 시각으로 못 읽으면 **빼지 않는다**(M11 — 모르면 후보에 남겨 받는 쪽이다).
   - ⚠이 판정의 가정은 「npb 가 박스를 공표표보다 늦게 고치지 않는다」다. 어긋나면 소진으로 사람에게 간다(§7).
3. **E3 이 실행의 수동 날짜**: `BB_REFETCH_DATES` 의 날짜 경기는 `수집·적재` 가 몇 분 전에 받았다. 새 키라면 E2 가 이미 뺀다(일화 시작 = 잡 시작 · D8). 그래도 날짜 상한을 셀 때 같이 쓰므로 명시한다.

- **남은 후보(키)** = 후보 − E2 − E3.
- **남은 날짜(키)** = 남은 후보의 `game_date` 집합.
- **소진(키)**: 자동이 허용된 실행에서 남은 날짜가 비었다.

### D6. 고르기 — 순서와 상한

**전체 관문 — 위에서부터 처음 걸리는 것이 「해 보지 않았다」의 사유다.** 사유 코드는 닫힌 목록이다.

| 순 | 조건 | 사유 코드 | 받기 |
|---|---|---|---|
| 1 | 감지기가 0·2 가 아닌 코드로 끝났거나 결과 파일이 없다 | `detector_error` | 안 함 |
| 2 | `status == "unmeasured"` | `unmeasured:<reason>` | 안 함 |
| 3 | `status == "no_defects"` | `no_defects` | 안 함(할 일 없음) |
| 4 | `BB_RUN_SLOT` 이 `scheduled`·`manual` 이 아니다 | `retry_slot`(값이 `retry`) · `slot_unknown`(그 밖) | 안 함 |
| 5 | `as_of.source != "genzai"` | `as_of:<source>` | 안 함(D3) |
| 6 | 결함 후보(`defects` 전체 · 대상 아닌 것 포함) > `AUTO_REFETCH_MAX_DEFECTS`(20) | `too_many_defects` | 안 함 |
| 7 | 대상 키가 0개다(비율·試合·해석 불가뿐) | `no_eligible` | 안 함 |
| 8 | `BB_COLLECT_STARTED_AT` 을 모른다 · 잡 시작 뒤 `AUTO_REFETCH_START_DEADLINE_MIN`(25분)이 지났다 | `started_at_unknown` · `time_budget` | 안 함(다음 정시 실행이 한다) |
| 9 | 날짜 자리가 없다: `MAX_REFETCH_DATES − 수동 날짜 수 ≤ 0` | `no_date_slots` | 안 함 |
| 10 | 대상 키가 전부 소진이다 | `all_exhausted` | 안 함 |

**고르는 순서(결정론적).**
```
키들 = 남은 날짜가 있는 대상 키를 (남은 날짜 수 오름차순, 키 문자열 오름차순)으로 세운다
고른 날짜 = [] · 고른 경기 = ∅
날짜 자리 = MAX_REFETCH_DATES − 수동 날짜 수
for 키 in 키들:
  for d in 그 키의 남은 날짜를 내림차순(최근부터):
    if d ∈ 고른 날짜: continue
    그날 경기 = ⋃(모든 대상 키의 d 날짜 남은 후보 경기)
    if |고른 날짜|+1 > 날짜 자리  or  |고른 경기 ∪ 그날 경기| > AUTO_REFETCH_MAX_GAMES(24): 전부 멈춘다
    고른 날짜 += d · 고른 경기 ∪= 그날 경기
```
- **후보가 적은 키부터** 고른다. o>p 키는 후보가 적어서(이번 사고 3일 · M-C 의 暴投 최대 7) 한 실행에 다 돌 수 있다. 그래서 큰 키(o<p 의 타자 최대 142일 · M-B)에 줄을 서지 않는다.
- **한 키 안에서는 최근 날짜부터** 고른다. 근거는 셋이다.
  1. 관문이 매 실행 돌기 때문에, 키가 새로 생겼다는 것은 그 사이에 공표표가 바뀌었다는 뜻이다.
  2. 관측된 정정 1건이 경기 약 열흘 뒤였다(§1).
  3. 1판의 `fetched_at` 오름차순은 2026 정규 842경기 가운데 623경기가 초기 구축 때 받은 사본이라(M-G) 「오래 안 다시 받은 사본」이 아니라 **4~8월 경기**를 먼저 집는다.
  - ⚠정정 지연 분포는 표본이 1건이다 — 뒤집힐 조건(§7).
- **날짜를 고르면 그날 모든 대상 키의 남은 후보 경기를 함께 받는다.** 날짜 자리는 이미 썼고, 같은 날 다른 키의 경기는 요청만 늘 뿐 자리를 더 쓰지 않는다. 경기 상한으로 묶인다.
- **날짜 하나를 넣다가 상한을 넘으면 그 자리에서 멈춘다.** 건너뛰고 작은 날짜를 찾지 않는다. 우선순위를 지키고 결과를 결정론적으로 만들기 위해서다.
- **이번 사고 재현(D13 시험).** 키 1개 · o>p · 후보 3일(9/23 · 9/17 · 5/13 · M-F) · 수동 0 · 이력 없음.
  - → 고른 날짜는 2026-09-23 · 2026-09-17 · 2026-05-13 이고, 고른 경기는 3이다.
  - → 요청은 **12** 다(월간 일정 0).
  - 1판의 날짜 단위였다면 그 3일의 전 경기를 받아야 했다. 9/17 하루만 5경기였다(M-P).

### D7. 재수집 전용 경로와 요청 상한 — `update.ts` 를 다시 부르지 않는다

**왜 `update.ts` 를 다시 부르지 않나(P1-2).** `BB_REFETCH_DATES=… node scripts/update.ts` 를 다시 부르면 아래가 **모두 다시 돈다**(실측 코드 경로).
- 날짜마다 `cli.ts` 를 따로 띄운다(`update.ts` 201~209행). 그래서 월간 일정 캐시를 나누지 못하고 **날짜마다 월간 일정 1장**을 받는다.
- **다음 달 일정도 날짜마다 1장** 받는다(`cli.ts` 106~121행).
- 선수 재취득(상한 400 · `update.ts` 239~260행), 신규 선수(262~291행), 予告先発 1요청(316~321행)도 돈다.
- 수동 실행이면 같은 실행 안에서 수동 7일과 자동 7일이 따로 돌아 14일이 될 수 있다.

**대신 — `packages/archiver/src/cli-games.ts`(새).**
```
node packages/archiver/src/cli-games.ts --ids <파일> --out data/archive --contact <연락처> --delay 3000 --result <json>
```
- `--ids` 는 한 줄에 경기 ID(`<시즌>/<MMDD>/<슬러그>`) 하나다.
  - ID 모양은 `^\d{4}/\d{4}/[a-z0-9]+(?:-[a-z0-9]+)+$`(경기 링크 정규식 `GAME_HREF` 와 같은 슬러그 규칙)이다.
  - 모양이 틀리거나 줄 수가 `AUTO_REFETCH_MAX_GAMES`(24)를 넘으면 **요청 0으로 종료 2** 한다(L1 의 마지막 방어선).
- ID → `GameRef` 는 `packages/archiver/src/discover.ts` 의 새 함수 `gameRefFromId(id)` 로 바꾼다.
  - 그 결과는 `path = /scores/<id>/` · `season` · `date` · `slug` · `venue: null` 이다. `venue` 는 받기에 쓰이지 않는다 — `pageKey`·`pageUrl` 은 `season`·`date`·`slug`·`path` 만 본다.
  - `pageKey`(`npb/scores/<시즌>/<MMDD>/<슬러그>/<잎>`)의 **역함수**이므로 아카이버가 자기 경로 규칙의 한 벌로 갖는다(M1). 왕복 시험을 둔다.
  - **월간 일정은 받지 않는다.** 경기 ID 가 곧 URL 이다(`game.source_url` 실측: `https://npb.jp/scores/2026/0917/t-c-20/box.html`).
- 받기는 경기마다 기존 `archiveGame(ref, deps)` 다(네 장 세트 · 하나라도 실패하면 아무것도 안 쓴다 · `archive.ts` 295~343행).
  - `PoliteFetcher` 와 UA 와 간격은 `cli.ts` 와 같다(`parseDelayMs` · L1 최소 간격 미만이면 종료 2).
  - **한 연결로 차례대로** 받는다.
- 종료코드는 셋이다. 실패(`failed`·`held`)가 하나라도 있으면 1, 입력이 틀리면 2, 그 밖은 0. `process.exit()` 대신 `process.exitCode` 를 쓴다(fetch 뒤 강제 종료 금지 · `scripts/test/exit-code.test.ts` 규율).
- `--result` 는 경기마다 `{ id, pages: {stored, unchanged, absent, failed, held}, boxShaBefore, boxShaAfter }` 를 담는 JSON 이다(보고용).

**다시 적재.** 기존 `node packages/store/tools/load-archive.ts data/archive data/bb.sqlite --max-writes 5000000` 을 그대로 한 번 부른다. 적재 경로를 새로 만들지 않는다.
- ⚠`--max-writes 5000000` 은 **빠뜨리면 안 된다.** 적재기 기본값은 D1 한도 100,000행이라 도중에 멈추고 종료 1 이 된다. 지금 한 번 적재가 889,666행이다(`36965884701` 로그).
- 전체를 다시 훑는다(실측 87.5~102.8초 · M-L). 판 가드는 새로 본 box 를 「같거나 새 판」으로 받는다.

**요청 종류 전수(한 실행 · 기존 단계와 나란히).**

| 요청 종류 | 수동 `refetch_dates`(기존 · `수집·적재`) | 자동(새 단계) |
|---|---|---|
| 경기 4장 | 그날 전 경기 × 4 · 날짜당 최대 24(M-A) | **고른 경기 × 4 · 최대 24경기 = 96** |
| 그 달 월간 일정 | 날짜마다 1 | **0** |
| 다음 달 일정 | 날짜마다 1 | **0** |
| 선수 재취득 · 신규 선수 | 기존대로 — 재취득은 상한 400, 신규는 아직 안 받은 선수 수만큼(상한 없음) · 실행마다 | **0** |
| 予告先発 | 1(기존) | **0** |
| 공표 성적표 | 30(기존 단계 · 그대로) | **0**(다시 받지 않는다) |

**한 실행의 재수집 요청 상한 — 수동과 자동은 한 날짜 상한(7)을 나눠 쓴다.** 수동 날짜 수를 `k` 라 하면 아래와 같다.
- 수동 = `k × 26`(6경기 × 4 + 일정 2 · M-A·M-P).
- 자동 ≤ `4 × min(24, 6 × (7 − k))`.

| k | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|---|
| 수동 | 0 | 26 | 52 | 78 | 104 | 130 | 156 | 182 |
| 자동 최대 | 96 | 96 | 96 | 96 | 72 | 48 | 24 | 0 |
| **합** | **96** | **122** | **148** | **174** | **176** | **178** | **180** | **182** |

→ **자동을 더해도 한 실행의 재수집 요청은 기존 수동 최악(7일 × 26 = 182)을 넘지 않는다.**
- 하루로는 자동 ≤ 정시 3회 × 96 = **288**이다(재시도 슬롯은 0 · D8). 수동 실행은 실행마다 그 위에 더해진다.
- npb.jp 는 검증자(ETag·Last-Modified)를 주지 않아 조건부 요청이 통하지 않는다. 그래서 위 수는 **전부 200 전체 본문**이다(`archive.ts` 124~127행의 실측 · 사이드카 3,000 표본에 둘 다 0건).
- **불일치가 없는 실행에서는 `cli-games.ts` 를 띄우지 않으므로 요청이 0 늘어난다**(D13 시험). 재시도 슬롯 · 관문 단계의 1~10 사유로 건너뛴 실행도 같다.

**`collect` 잡 45분 제한(221행) — 실측으로 계산한다.**
- 새 단계 최악(자동 24경기)은 다음의 합이다. 결과는 **≈ 6.8분**이다.
  - 받기 96 × 3.13초 = 300.5초(5.0분 · M-K)
  - 재적재 102.8초(1.7분 · M-L)
  - 감지 2회 ≈ 1초(M-M)
  - `git fetch` ≤ 3초(M-N)
- 이 단계 자리 → 잡 끝의 실측 최장은 **11.43분**이다(M-J · 수동 깊은 실행 — 시험 5.9분 포함).
- **마감 `AUTO_REFETCH_START_DEADLINE_MIN` = 25분.** 잡 시작 뒤 25분이 지났으면 받지 않는다(사유 `time_budget`). 그래서 최악은 25 + 6.8 + 11.43 = **43.2분 ≤ 45** 이다(여유 1.8분).
- 25분인 이유: 선수 재취득이 상한 400까지 찬 날에도 자동이 돌 수 있어야 한다. 그날 이 자리까지의 시간은 9.40 − 5.27 + 400 × 3.13초 ≈ **25.0분**이다(M-I·M-K로 외삽 · 그런 날은 관측된 적이 없다). 그 시간에서 거꾸로 낸 수가 25 이고, 경기 상한 24는 거기서 다시 나온다(D12).
- 평소에는 이 자리까지 4.68~9.40분(M-I · 5실행)이라 마감에 닿지 않는다.
- **새 단계가 `timeout-minutes: 15` 에 걸려도** 최악은 25 + 15 + 약 0.6(always 단계: 재검증 · 업로드 · 기록 · 반영 확인) ≈ 40.6분이다. 뒤의 `success()` 단계는 건너뛰므로 45 안이다.
- ⚠**이 설계 밖의 기존 한계.** 선수 재취득 400 + 수동 7일 + 깊은 시험이 한 실행에 겹치면 이 설계 없이도 ≈ 45분이다. 그 합은 다음과 같다.
  - 평소 새 단계 자리까지 4.7분(M-I)에서 평소 하루치 수집 약 1.1분을 뺀다.
  - 수동 7일 182요청 × 3.02초 ≈ 9.2분을 더한다.
  - 선수 400 × 3.13초 ≈ 20.9분을 더한다.
  - 이후 단계 11.43분을 더한다.
  - 그 실행에서 새 단계는 마감(25분)과 날짜 자리(0) 때문에 받지 않는다. 그래서 더하는 것은 감지·보고 몇 초뿐이다.

### D8. 시도 이력 — (키, 경기)는 일화마다 한 번 · 소진 · 저장 위치 · 복원·재실행·동시 실행

**무엇을 보존하나.** 핵심은 결함 키마다의 **일화 시작 시각**(`first_seen_at`) 하나다. 판정은 DB 의 `game.fetched_at` 과 그것을 맞대어 한다(D5 의 E2).
- 같은 경기는 일화가 시작된 뒤에 한 번 받으면 다시는 후보가 되지 않는다. 그래서 **(키, 경기)는 일화마다 한 번**이고, 날짜로 말하면 **같은 날짜는 같은 키에 대해 한 번**이다.
- ⚠**받은 날짜 목록(`attempts`)은 기록이지 판정 근거가 아니다.** 판정을 목록에 맡기면 보관소 세대가 되돌아갔을 때 판정이 틀린다. 「받았다」고 적혀 있는데 아카이브에는 정정 전 판이 남아 그 날짜를 영영 안 받는다. DB 의 `fetched_at` 은 복원된 아카이브와 함께 되돌아가므로 판정이 스스로 맞춰진다(아래 「복원」).

**저장 위치 — `ops/correction-refetch.json`(git · 공개 저장소).**
- 워크플로가 매 실행 원격 `main` 에 커밋하는 디렉터리는 `ops/` 다. 지금 대상은 정확히 3파일(`collection-log.txt` · `collection-log.jsonl` · `archive-manifest.json` · 684행)이고, 이 파일이 넷째가 된다.
- **이 저장소는 공개다**(워크플로가 도는 곳은 `muji-j/basenine` · 실행 로그의 체크아웃 줄 실측). 그래서 **이력에는 수치(우리 값 · 공표 값)를 넣지 않는다.** 키(선수 ID · 팀 · 항목)와 날짜·시각·실행 번호만 둔다. 수치는 실행 로그의 보고에만 나온다(관문 로그가 이미 찍는 것과 같은 층 · §7).
- 데이터 저장소(비공개 릴리스)에 두는 안은 기각했다(§6).

**형식(스키마 1 · 키 정렬 · 2칸 들여쓰기 · 끝 줄바꿈 — 실행마다 같은 바이트).**
```json
{
  "schema": 1,
  "keys": {
    "2026|t|pitching|91095136|暴投": {
      "direction": "ours_more",
      "first_seen_at": "2026-09-28T20:40:57Z",
      "first_seen_run": "36480899578",
      "last_seen_at": "2026-09-28T20:51:02Z",
      "attempts": [
        { "date": "2026-09-23", "at": "2026-09-28T20:51:03Z", "run": "36480899578" },
        { "date": "2026-09-17", "at": "2026-09-28T20:51:03Z", "run": "36480899578" },
        { "date": "2026-05-13", "at": "2026-09-28T20:51:03Z", "run": "36480899578" }
      ],
      "exhausted_at": "2026-09-28T20:51:03Z"
    }
  }
}
```
(모양 예시다. 「이 기능이 9/28 에 있었고, 세 날짜를 다 받았는데도 결함이 **남았다**」고 가정했다. 실제 사고였다면 9/17 을 받는 순간 풀려서 사후 감지에서 이 키가 **지워진다**.)

**갱신 규칙(순수 함수 `updateHistory` · `scripts/correction-plan.ts`).** 감지 결과를 받을 때마다(사전 · 사후) 적용한다.

| 감지 결과 | 키가 결함 목록에 있다(대상 · 해석됨) | 키가 목록에 없다 | 다른 시즌의 키 |
|---|---|---|---|
| `unmeasured` · 감지기 오류 | **바꾸지 않는다** | 바꾸지 않는다 | 바꾸지 않는다 |
| 측정 성공 · `as_of=genzai` · 결함 ≤ 20 | 없으면 **새 일화**(`first_seen_at` = `BB_COLLECT_STARTED_AT`). 있으면 `last_seen_at` 갱신. **방향이 다르면 새 일화로 갈아 끼운다** | **지운다**(풀렸다) | 지운다(자동 대상이 아니다) |
| 측정 성공 · 그 밖(`as_of≠genzai` 또는 결함 > 20) | 있으면 `last_seen_at` 갱신. **새로 만들지 않는다** | 지운다 | 지운다 |

- **새 일화의 시작을 잡 시작으로 잡는 이유.** 이 실행이 몇 분 전에 받은 사본(어제 경기 · 수동 날짜)은 지금 공표표보다 먼저 받았지만 **같은 실행 안**이다. 박스와 공표표가 함께 고쳐진다면 그 사본은 이미 최신이다. 그래서 E2 로 뺀다. 이 판정이 틀리는 창(공표표를 받기 전 몇 분 사이에 박스만 바뀜)은 §7 에 있다.
- **`BB_COLLECT_STARTED_AT` 을 쓰는 조건.** ISO 시각으로 읽히고, `now` 이하이며, `now − 6시간` 이상이어야 한다(잡 제한이 45분이다). 그 밖이면 「모름」이다.
  - 모르면 새 일화의 시작을 **이 단계의 시계(`now`)** 로 잡는다. 늦게 잡는 쪽이라 이 실행에서 받은 사본이 후보에 남는다 — **후보를 넓히는 방향이라 안전하다.**
  - 그 실행은 받지 않는다(D6 의 8 · `started_at_unknown`).
- **재시도 슬롯에서도 감지 · 이력 갱신 · 보고는 한다.** 받기만 하지 않는다(D6 의 4). 그래서 재시도 슬롯에서 처음 보인 키도 일화가 그때 시작한다.
- **받은 뒤**에는 키마다, 그 키의 남은 후보 경기 가운데 **네 장 세트가 실패 없이 기록된 경기**(`cli-games` 결과)가 있는 날짜를 `attempts` 에 붙인다. `at` 은 이 단계가 시계를 읽은 시각이다(M6 · 한 번).
- **소진.** 자동이 허용된 실행(D6 의 1~9 통과)에서 다음 둘 중 하나면 `exhausted_at` 을 찍고(처음 한 번), 로그에 `소진 — 런북 §7-I · <키> · 후보 N일을 다 다시 받았는데 남았다` 를 찍는다. 그 키는 받지 않는다(남은 후보가 없으므로).
  - 계획 시점에 남은 날짜가 없다.
  - 받은 뒤 사후 감지에서 키가 남았는데 남은 날짜가 0이다.
  - 관문은 그대로 막는다.
- **수명.** 키는 「측정 성공 + 목록에 없음」에서 지운다(**결함이 풀리면 지운다**). 파일 자체는 남긴다(키 0개). 바뀐 것이 없으면 다음 판을 쓰지 않으므로 커밋할 것도 없다.

**읽기·쓰기 — 「원격 최신에서 읽고, 읽은 판 위에서만 쓴다」.**
1. **읽기(새 단계 시작).** `git fetch --quiet origin "$GITHUB_REF_NAME"` 을 한 뒤 `git show "origin/$GITHUB_REF_NAME:ops/correction-refetch.json"` 으로 읽는다(`git cat-file -e` 로 「없음」과 「실패」를 가른다).
   - **체크아웃 사본을 읽지 않는다.** 줄을 섰던 실행의 `github.sha` 는 줄 서기 시작한 시각의 `main` 이라 앞 실행이 커밋한 이력을 모른다(659~661행이 같은 낡음을 적어 둔다).
   - fetch 가 실패하면 작업 트리 사본으로 물러서고 `::warning::` 을 찍는다. 아래 쓰기 대조가 덮어쓰기를 막는다.
2. **쓰기(새 단계 끝).** 읽은 바이트의 sha256(없었으면 `absent`)을 `/tmp/correction-refetch/history.base` 에 **먼저** 쓴다. 그 다음 바뀐 경우에만 `history.next.json` 을 `.tmp`+`rename` 으로 쓴다.
3. **반영(`기록 갱신과 커밋` 의 `attempt()` · D1).** `git reset --hard origin/<ref>` **뒤에** 원격 파일의 sha256 이 `history.base` 와 같을 때만 복사한다.
   - `attempt()` 를 다시 돌아도(푸시 경합) 매번 원격 최신 위에서 같은 비교를 하므로 멱등이다.
   - 다르면 덮어쓰지 않고 경고한다. 이 경우는 그 사이 사람이 이 파일을 커밋한 경우뿐이다(아래 「동시 실행」).

**복원 · 재실행 · 동시 실행.**
- **복원(보관소 세대가 되돌아감).** 오늘 업로드가 지운 뒤 실패하면(`--clobber` · 541~545행) 다음 실행은 어제 세대를 복원한다. 그러면 다시 받았던 경기의 box 사이드카와 DB 의 `fetched_at` 이 **정정 전 시각으로 함께 돌아간다.**
  - → E2 에서 그 경기가 다시 후보가 되어 **한 번 더 받는다**(스스로 맞춰진다).
  - 이력의 `attempts` 에는 그 날짜가 남아 있다. 보고는 그것을 「되돌려짐(복원) — 다시 후보」로 표시한다(attempt 의 `at` 보다 그 경기들의 `fetched_at` 이 이르면).
- **재실행(「실패한 잡 다시 실행」).**
  - `collect` 가 처음부터 다시 돌아 `job-start` 가 새로 찍힌다.
  - `decide` 출력(`slot`)은 원래 실행의 것을 다시 쓴다 — 원래가 재시도 슬롯이면 다시 실행해도 받지 않는다.
  - 이력은 원격 최신에서 읽는다.
- **동시 실행.**
  - `concurrency: daily-collection · cancel-in-progress: false`(115~119행)라 실행은 직렬이다. 앞 실행의 `기록 갱신과 커밋` 이 끝난 뒤에야 다음 실행의 새 단계가 돈다. 그래서 원격 최신을 읽으면 앞 실행의 이력을 본다.
  - 이 파일에 쓰는 것은 이 워크플로와 사람(런북 §7-I 의 키 지우기)뿐이다. 사람이 실행 도중 커밋하면 위 대조가 그 실행의 반영을 버린다.
  - 그때 잃는 것은 최대 한 실행치의 이력이다. 다음 실행이 다시 만든다. 새 일화의 시작이 늦어지므로 이미 받은 경기를 많아야 한 번 더 받는다.
- **커밋이 실패하면**(3회 푸시 경합 · 696행)도 같다. 이력 한 실행치를 잃고 다음 실행이 다시 만든다. 그 단계가 빨개지므로 조용하지 않다.

### D9. 단계의 차례 · 종료코드 · 보고

**진입점 `scripts/correction-refetch.ts`(새).** 시계를 **한 번** 읽는다(M6). 그래서 `scripts/test/clock-injection.test.ts` 의 허용 목록에 `["scripts/correction-refetch.ts", 1]` 을 더한다.
- 자식 프로세스로 띄우는 것은 셋이다: `crosscheck.ts`(감지 두 번) · `cli-games.ts` · `load-archive.ts`. `update.ts` 와 같은 방식이다.
- 판단은 전부 순수 모듈에 둔다.
  - `scripts/correction-plan.ts`: `updateHistory` · `planRefetch` · `renderReport` · `stepExitCode`. 시계·I/O 가 없다.
  - DB 읽기는 `scripts/correction-candidates.ts` 에 둔다. `node:sqlite` 를 `readOnly: true` 로 연다. import 만으로는 아무것도 하지 않는다(`collected-through.ts` 선례).
- 수동 날짜는 `scripts/date-window.ts` 의 `parseRefetchDates`(한 벌)로 읽는다. 틀리면 종료 1 이다. 실제로는 `수집·적재` 가 같은 파서로 먼저 종료 2 를 내서 이 단계까지 오지 않는다.
- 진입점은 `main(deps)`(자식 실행 함수 · 시계 · 경로를 주입)를 내보내고, **파일로 실행될 때만** 그것을 부른다. **import 만으로는 아무것도 하지 않는다** — `update.ts` 는 import 하는 순간 수집을 시작해서 시험할 수 없었다(`date-window.ts` 머리말). T9 가 이 주입으로 띄운 명령을 센다.
- 자식이 끝난 뒤 종료는 `process.exitCode` 로 낸다(`exit-code.test.ts` 의 규율).

| 차례 | 하는 일 | 실패하면 |

### D10. 관문과 알림 — 풀리지 않으면 지금처럼 막는다(사용자 결정 ②)

- `외부 대조` 단계는 **판정을 바꾸지 않는다.** 실패할 때만 이 실행의 `report.txt` 를 다시 찍는다(D1). 그래서 그 단계의 로그만 보고도 셋 가운데 어느 것인지 알 수 있다.
  - 「해 봤는데 남았다」(남은 키 · 소진 여부)
  - 「해 보지 않았다(사유)」
  - 「보고 없음」
- 관문이 실패한 실행은 지금처럼 `화면 생성`·`시험`·`배포` 를 건너뛰고 빨갛다. 재시도 슬롯이 뜨지만 받지는 않는다(D6).
- **런북 `docs/operations/deploy.md` 에 §7-I 를 신설한다**(구현 단계에서 쓴다). 담을 것은 다음과 같다.
  1. 증상 — 같은 결함 후보가 여러 실행 남는다.
  2. 이번 사고 요약과 복구 실행(§1).
  3. 자동 재수집이 하는 일과 보고 첫 줄 읽는 법.
  4. **「해 보지 않았다」 사유 코드별 할 일** 표(D6 의 10개). 예: `too_many_defects` → 정정이 아니라 체계적 원인부터 본다(§7-D 같은 시각 문제 · 파서) / `time_budget`·`retry_slot` → 다음 정시 실행을 기다린다.
  5. **「소진」일 때.**
     - ⑴ 보고에 나온 키와 후보 날짜를 본다.
     - ⑵ npb.jp **지금의** 그 경기 박스와 공표표를 사람이 맞댄다. 박스는 고쳐지지 않았고 공표표만 고쳐졌으면 npb 내부 불일치다 → 기다리거나 사람이 판단한다.
     - ⑶ 우리에게 **행이 없는** 경기가 의심되면(o<p · 출장 자체가 더해진 정정) 그 팀의 의심 날짜를 수동 `refetch_dates` 로 준다. 그날 남은 자리는 자동이 쓴다.
     - ⑷ **일화를 다시 열려면** `ops/correction-refetch.json` 에서 그 키를 지우는 커밋을 한다. 다음 실행이 새 일화로 연다. 이미 받은 경기도 다시 후보가 된다 — 같은 날 여러 번 하지 않는다(L1).
  6. 수동 실행은 하루에 여러 번 누르지 않는다(L1 · §6).
- `refetch_dates` 입력 설명(101행)에 「남은 자리는 자동 재수집이 쓴다」를 한 구절 더한다. 숫자 7은 그대로 둔다(정본 주석 99~100행).

### D11. 멱등 · 판(M4/M5) — P2-9 · P2-8

- **멱등(M5).**
  - 같은 경기를 두 번 받아도 아카이버는 본문이 같으면 쓰지 않고 「봤다」만 남긴다(`markSeen`). 다르면 새 판을 쓴다.
  - 적재기의 판 가드는 같거나 새 판만 받는다(PR #18).
  - 같은 실행 안에서 이 단계를 두 번 돌려도 두 번째는 E2 로 후보가 비어 받지 않는다. 결과는 한 번과 같다.
- **판 표지(P2-9 정정 — 1판의 보장 문장을 삭제한다).** 1판은 「다시 받은 경기의 `game.fetched_at`·`revision` 이 새로워진다」고 적었다. **`revision` 쪽은 거짓이다.**
  - 아카이버는 같은 본문이면 `checkedAt` 만 갱신한다(`archive.ts` 135~154행).
  - DB 의 `upsertGame` 은 경기 행의 상태 · 점수 · 안타 · 실책 · 구장 · 대회 · 팀 코드가 바뀔 때만 `game.revision` 을 올린다(`packages/store/src/load.ts` 243~265행).
  - 이번 사고의 暴投 같은 **자식 행만의 정정**에서는 `game.revision` 이 그대로다. `batting_line`·`pitching_line` 에는 `revision` 칸이 없다.
  - **이 설계가 기대는 것은 `game.fetched_at` 하나**다(D5 의 E2). 다시 받기가 성공하면 그 값이 받은 시각으로 오른다. 그것으로 「언제 받은 판인가」에 답한다.
  - 사이드카의 `revision` 도 정정의 표지가 아니다. 9/17 재수집에서 5경기 20장이 **전부** 본문이 바뀌었다(`신규 20` · §1) — 정정과 무관한 4경기까지.
- **보관소(P2-8 정정).** D1 에 적었다. 정상 경로는 아카이브와 DB 를 같은 업로드로 함께 올린다.

**`AUTO_REFETCH_MAX_DEFECTS` = 20 의 근거.**
- **정정 하나의 발자국**을 항목 의존으로 세었다(크로스체크 항목 35개 기준).
  - 안타↔실책 정정이면 타자 쪽이 安打 · 打率 · 出塁率 · 長打率이다. 장타면 二塁打·三塁打, 타점이 붙으면 打点이 더해진다 → 최대 6.

  - 그래서 전형은 4~7, 극단은 약 12다. 暴投·盗塁·打点 하나만 바뀌는 정정은 1이다(이번 사고).

## 6. 기각한 안

- **`update.ts` 를 그대로 다시 부르기**(1판 D5) — 날짜마다 일정 2장, 선수 재취득 ≤ 400, 予告先発 1 이 다시 돌고, 수동 날짜와 겹치면 14일이 된다(P1-2 · D7).
- **날짜 단위로 그날 전 경기 받기**(1판) — 후보는 그 선수가 그 팀 쪽에서 뛴 경기뿐인데, 날짜로 받으면 최대 6배를 받는다(이번 사고: 3경기 대 그 3일의 전 경기 · 9/17 하루만 5경기). 날짜는 **상한의 단위**로만 남긴다 — 수동 입력과 같은 말로 세기 위해서다.
- **관문을 느슨하게**(소수 불일치는 경고만 하고 배포) — 사용자 결정 ②로 기각.
- **지난 N일 경기를 매 실행 다시 받기** — 정정 지연을 재 본 적이 없어 N 을 고를 근거가 없다(관측 1건: 약 열흘). 불일치가 없는 날에도 요청이 늘어 L1 에 반한다.
- **박스 한 장만 다시 받기** — 판 가드가 경기 4장의 세트를 대조한다(세트 불일치는 적재 실패). 4장을 함께 받는다.
- **`fetched_at` 오름차순으로 고르기**(1판 D3) — 2026 경기의 623/842 가 초기 구축 사본이라 그 순서는 4~8월 경기를 먼저 집는다(M-G). 같은 날짜를 다시 고르는 문제도 못 막았다(P1-3). 진행은 E2 가 맡고, 순서는 「작은 키부터 · 최근부터」로 바꿨다.
- **받은 날짜 목록을 판정 근거로 쓰기** — 보관소 세대가 되돌아가면 「받았다」는 적혀 있는데 아카이브에는 정정 전 판이 남는다. 그 날짜를 영영 안 받는다. 판정은 아카이브와 함께 움직이는 DB `fetched_at` 으로 하고, 목록은 기록으로만 둔다(D8).
- **이력을 데이터 저장소(비공개 릴리스 자산)에 두기** — 세대와 수명이 같고 수치를 넣어도 공개되지 않는다는 장점이 있다. 그러나 ⑴ 판정을 DB `fetched_at` 으로 하므로 세대와 어긋나도 스스로 맞춰진다 — 같은 수명이 필요 없다. ⑵ 사람이 키를 지우는 처치(§7-I)가 자산 내려받기·고치기·올리기가 된다. ⑶ `data/archive` 안에 두면 `archive-guard` 가 키를 지울 때 「줄었다」로 멈춘다. → git `ops/` 에 두고 수치를 빼서 공개 문제를 피한다.
- **재시도 슬롯에서도 받기** — 관문이 막는 동안 재시도 슬롯은 매번 뜬다(직전이 실패). 거기서도 받으면 자동 요청이 하루 6회 × 96 = 576 이 된다. L1 의 「하루 1회 배치가 기본」에서 더 멀어진다. 재시도 슬롯의 이유(予告先発 · 수집 실패 보완)와도 상관이 없다.
- **`seasonIsOver()` 로 시즌 상태 판정** — 묻는 것이 다르다(D3).
- **결함 상한을 「대상 키 수」로 세기** — 관문 로그의 「결함 후보 N건」과 다른 수가 되어 사람이 대조하기 어렵다. 비율 항목만 어긋나는 체계적 원인을 못 센다.
- **감지 모드를 별도 도구로 두기** — 비교 로직이 두 벌이 된다(M1). 같은 도구에 플래그를 두고, 플래그가 있을 때만 종료코드 계약이 달라진다.

## 7. 뒤집힐 조건 · 남는 위험 · 범위 밖

**뒤집힐 조건**
- **정정 지연의 분포를 재면** 순서(최근부터)와 상한(24경기 · 7일)을 다시 본다(지금 표본 1건).
- **이후 단계 실측(11.43분)이나 잡 제한(45분)이 바뀌면** 마감 25분과 경기 24를 다시 낸다(D12 · 시험이 45 를 대조한다).
- **관측 정정이 결함 20건을 넘거나, 체계적 원인이 20건 아래로 관측되면** `AUTO_REFETCH_MAX_DEFECTS` 를 다시 본다.
- **npb 가 완결 시즌에서 `現在` 를 지우는 시점이 관측되면** D3 의 전이 구간 서술을 고친다.

**남는 위험**(전부 「소진 → 관문이 막음 → 런북 §7-I」로 사람에게 간다 · 조용히 틀리지 않는다)
- **npb 내부 불일치** — 공표표는 고쳤는데 박스는 안 고쳤다. 다시 받아도 안 풀린다.
- **공표표가 박스보다 먼저 고쳐졌다** — 일화가 시작된 뒤 받은 사본이 정정 전 박스다. E2 가 그 경기를 빼서 놓친다. 키를 지우면(§7-I ⑷) 새 일화로 다시 찾는다.
- **o<p 인데 우리에게 행이 없는 경기**(정정이 출장 자체를 더함) — 후보 조회가 그 경기를 볼 수 없다.
- **같은 키에 일화 안에서 두 번째 정정**이 일화 시작 뒤에 받은 사본에 생기면 놓친다(같은 처치).
- **새 키에서는 이 실행에서 막 받은 경기도 뺀다**(일화 시작 = 잡 시작). 그 경기의 박스가 공표표를 받기 전 몇 분 사이에 바뀐 경우를 놓친다.
- **다시 받은 경기에 다른 선수의 박스 선행 정정이 딸려 오면** 그 선수는 공표표가 따라올 때까지 새 결함이다(관문이 막는다). 공표표가 따라오면 그 실행에서 풀린다. 그동안 자동이 그 키를 찾느라 쓰는 요청은 실행당 96 으로 묶인다.
- **이름 짝짓기가 바뀌면**(공표 표기 변경으로 미해결이 되면) 키가 목록에서 빠져 「풀렸다」로 지워진다. 다시 짝지어지면 새 일화가 되어 이미 받은 경기를 한 번 더 받을 수 있다.
- **공개 로그 노출** — 보고(실행 로그)에는 이름과 수치가 나온다. 관문이 지금도 공개 로그에 `우리 3 공표 2` 를 찍는 것과 같은 층이다. 이력 파일(git)에는 수치를 넣지 않는다(D8).

**범위 밖(기존 한계 — 이 설계가 고치지 않는다)**
- **자식 행만의 정정은 `game.revision` 을 올리지 않는다**(D11). 정정 전 박스 본문은 보관소 세대 3개(`KEEP=3`)에만 남는다. 「어제 본 숫자와 다른데?」에 오래 답하려면 영속하는 정정 기록이 필요하다 — 별도 결정이다.
- 선수 재취득 400 · 수동 7일 · 깊은 시험이 겹친 실행의 ≈ 45분(D7).

## 1. 목적

일본 프로야구(NPB)의 선수·구단 성적을, **npb.jp가 보여주지 않는 각도로** 볼 수 있게 하는 웹 서비스.

v1의 성공 조건은 「데이터가 많다」가 아니라 **「여기서만 볼 수 있는 숫자가 있다」**이다. 기본 성적만 예쁘게 보여주는 것은 이미 존재하는 사이트의 열화 복제이며, 그 자체로 법적 위치도 나빠진다(§7).

## 4. 아키텍처

### 4.1 왜 이 형태인가

무료 Cloudflare 트랙의 최대 함정은 **Workers Cron의 CPU 10ms 제한**이다. 수집을 Workers에서 돌리면 v1 수집조차 팬아웃 설계 없이는 성립하지 않는다(조사 보고서 §4).

→ **수집을 Workers 밖으로 뺀다.** 아카이버는 이미 순수 Node 스크립트이고 저장소가 인터페이스 뒤에 있으므로, 어디서 돌든 상관없다. Workers는 **읽기 전용 배포**만 담당한다.

이렇게 하면 Cron CPU 제한이 설계에서 사라지고, Workers는 자기가 잘하는 일(엣지 캐시된 읽기)만 한다.

### 4.2 구성

```
  ┌──────────────── 수집·가공 (GitHub Actions, 1일 1회) ────────────────┐
  │                                                                     │
  │  archiver ──원시 HTML──▶ R2 (raw archive)                           │
  │      │                        │                                     │
  │      │                        ▼                                     │
  │      │                    parser ──타석 레코드──▶ D1 (structured)    │
  │      │                                              │               │
  │      │                                              ▼               │
  │      └──────────────────────────────────────▶  aggregator           │
  │                                            (지표·순위·스플릿 사전계산)│
  └─────────────────────────────────────────────────────────────────────┘
                                                        │
                                                        ▼
  ┌──────────── 배포 (Cloudflare Workers, 읽기 전용) ─────────────┐
  │  Cloudflare Access (Google OIDC + 이메일 허용목록)             │
  │        │                                                      │
  │        ▼                                                      │
  │  Worker ── D1 조회 ──▶ SSR ──▶ 엣지 캐시                       │
  └───────────────────────────────────────────────────────────────┘
```

### 4.3 패키지 경계

| 패키지 | 책임 | 의존 |
|---|---|---|
| `archiver` | 원시 HTML 취득·보존. **파싱하지 않는다** | 없음 (구현 완료) |
| `parser` | 원시 HTML → 타석 레코드. 소스별 1벌(M7) | `archiver`(픽스처) |
| `metrics` | **지표 계산식 전용. 순수 함수. I/O 없음**(M1) | 없음 |
| `store` | D1 스키마·마이그레이션·쿼리 | — |
| `aggregator` | 원시 → 집계(순위·스플릿·상대전적) 재계산 | `metrics` `store` |
| `web` | Worker + SSR + UI | `store` `metrics` |

**`metrics`가 I/O를 갖지 않는 것이 이 설계의 핵심 제약이다.** 서버·배치·(장래) 클라가 같은 1벌을 쓰고, 스택을 갈아도 살아남으며, 공개 수치와 대조 테스트를 붙이기 쉽다.

### 4.4 데이터 흐름의 되돌릴 수 있음

```
원시 HTML(R2)  →  타석 레코드(D1)  →  집계(D1)
     ↑ 보존              ↑ 재생성 가능         ↑ 재생성 가능
```
**R2의 원시 HTML만 진짜 자산이다.** 아래 둘은 언제든 다시 만들 수 있다. 파서에 버그가 있었다면 원시에서 다시 돌리면 되고, 새 지표를 만들고 싶으면 집계만 다시 돌리면 된다. 이 방향성이 깨지는 설계(예: 원시를 버리고 집계만 저장)를 채택하지 않는다.

pa_event          타석 1건. game_id · 이닝 · 아웃 · 주자상태 · 투수 · 타자 · 결과 · 타순
                  status: 'final' | 'live'   ← v1은 'final'만 쓴다. v2에서 컬럼 추가 없이 확장

원칙:
- **이닝은 아웃 카운트(정수)로 저장.** `6.2`를 부동소수로 누적하지 않는다.
- **경기일(business date)과 타임스탬프를 별도 컬럼으로.** 경기는 자정을 넘긴다.
- **경기구분을 컬럼으로.** 정규/CS/오픈전을 섞어 집계하면 전부 틀린다.
- 미수집 / 0 / 없음을 구별한다(M11).

## 6. 지표

### 6.1 계산 규약
- 산식은 `docs/metrics/`가 정본이고 `metrics` 패키지가 유일한 구현이다(M1).
- 모든 비율은 **분모(표본 수)와 함께 반환**한다. 분모를 버리는 시그니처를 만들지 않는다(M2).
- 리그 순위는 **자격 기준(규정타석·규정투구회)과 동률 처리 규칙**을 명시하고 테스트로 고정한다(M3).
- 각 지표에 확신도를 붙인다: `공식 정의 인용` / `관례(출처 명시)` / `우리 정의`.

### 6.2 파생 재료
- **리그 상수와 파크팩터를 우리 아카이브에서 산출한다.** 1.02 공개 wOBA 계수는 1세트뿐이므로, wOBA 절대치가 아니라 **리그평균 대비 상대치(wRAA·wRC+)로 제시**한다.
- 파크팩터는 1년치 편차가 크므로 3~5년 합산이 필요하다 → **v1에서는 파크팩터 미적용**으로 시작하고, 그 사실을 지표 라벨에 쓴다. (2025~ 2시즌뿐이라 신뢰할 만한 PF를 만들 표본이 없다.)

### 6.3 간판 지표 — 상황가중 공격 기여도

**정의 방향** (최종 산식은 `sabermetrics-analyst`가 `docs/metrics/`에 확정)

- 기반: **우리 아카이브에서 산출한 NPB 자체 득점기대치 행렬**(24 base-out states)
- 내용: 각 타석이 득점기대치를 얼마나 바꿨는가(RE24 계열) + 주루 기여
- 단위: **평균 대비 득점(runs above average)**. 승리(wins)로 환산하지 않는다
- **수비를 포함하지 않는다** — 이 사실을 각주가 아니라 **지표 설명의 첫 줄**에 쓴다

**왜 이걸 간판으로 두는가**
1. 가진 입력으로 **정직하게 계산된다.** 무엇을 재고 무엇을 안 재는지 말할 수 있다.
2. npb.jp에 존재하지 않는 값이므로 **원본의 재배열이 아니라 우리 산출물**이다 — §7의 2·3층 위험을 실질적으로 낮춘다.
3. 상황 가중이 들어가 단순 타율보다 정보량이 많다.

**⚠제약**
- **WAR과 명확히 다른 이름을 쓴다.** 이름이 같은데 값이 다르면 그건 거짓말이다.
- 표본이 작은 구간(월별·스플릿)에서는 분모를 반드시 병기하고 임계 미만은 시각적으로 약하게 표시한다.
- 2025~ 2시즌만으로 만든 득점기대치 행렬임을 명시한다.

## 7. 데이터 권리 대응

`CLAUDE.md` §2-5의 4층 구분과 L1~L7을 그대로 따른다. v1에서 실제로 지키는 것:

| 규칙 | v1에서의 구현 |
|---|---|
| L1 예의 | 아카이버가 3초 간격·동시 1커넥션·연락처 UA를 코드로 강제 (구현 완료) |
| L2 데드카피 회피 | 원본 표 레이아웃을 재현하지 않는다. 화면은 **자체 계산값 위주**(§6.3이 그 실체) |
| L3 출처 | 전 화면에 출처 명기 + 원본 링크 |
| L4 창구 | 삭제·정정 요청 경로를 v1부터 |
| L5 범위 | 공개된 직업활동 성적만 |
| L6 경계 | **원시 아카이브는 R2에 내부 보관, 외부 노출은 파생값** |
| L7 조건부 요청 | 구현했으나 **npb.jp는 ETag/Last-Modified를 주지 않음**(실측). 실효는 본문 해시 비교 |

**S1(비공개)은 「공개」 축만 해소한다.** 수집 행위 자체의 규칙은 그대로 남는다.

## 8. 접근 제어

**Cloudflare Access(Zero Trust) + Google OIDC + 이메일 허용목록.**

- 인증 코드를 우리가 쓰지 않는다. 세션·토큰·콜백 검증을 직접 구현하면 그게 곧 취약점 면적이 된다.
- ⚠**무료 티어의 사용자 수 상한을 착수 전에 실측한다**(§11 미결 1). 상한을 넘으면 설계가 바뀐다.
- **인가는 엣지에서 매 요청 검증한다.** UI 숨김은 인가가 아니다.
- 로그인 성공 ≠ 이용 허가. 허용목록에서 빠지면 즉시 차단되는 경로를 확인한다.

## 9. 실패 처리와 관측

### 9.1 이 서비스가 죽는 방식
가장 흔한 죽음은 「장애」가 아니라 **「수집이 조용히 멈추고 어제 숫자를 계속 보여주는 것」**이다.

그런데 조사 결과 **무료 감시 수단 3종이 전부 시한부**로 판명됐다:
- Cloudflare 헬스체크 — Free 플랜에 **없음**
- GitHub Actions 스케줄 — **60일 무활동 시 자동 비활성화**
- healthchecks.io — **1년 무로그인 시 계정 삭제**(ping은 활동으로 안 침)

### 9.2 대응 — 감시를 제품 안에 둔다

**제품 화면이 신선도를 표시한다.** D1의 최신 경기일이 기대보다 오래됐으면 UI가 그 사실을 크게 말한다(M12의 「수집실패」 상태).

이 감시는 **만료되지 않는다.** 제품의 일부이고, 사용자가 볼 때마다 작동하며, 별도 계정도 무료 한도도 쓰지 않는다. 외부 감시가 조용히 사라져도 남는다.

보조 장치:
- GitHub Actions 워크플로가 매 실행마다 **수집 요약 1행을 `ops/collection-log.tsv`에 append 커밋**한다(전용 브랜치가 아니라 기본 브랜치, 봇 커밋). 리포 활동이 갱신되므로 60일 자동 비활성화에 걸리지 않는다 — 자기 문제를 자기가 푼다
- 수집 결과를 `stored / unchanged / absent / failed` **분모와 함께** 기록한다

### 9.3 4상태
로딩 / 데이터없음 / **수집실패** / 시즌외 — 각각 다른 화면(M12). 「데이터 없음」과 「수집이 멈춤」을 같은 화면으로 만들지 않는다.

## 10. 테스트 전략

| 대상 | 방법 |
|---|---|
| 파서 | **저장된 픽스처**로만. 외부 사이트를 때리지 않는다. **옛 픽스처를 남겨** 구조 변경 회귀를 잡는다 |
| 지표 | `docs/metrics/`의 검증 케이스(선수·시즌·기대값)를 그대로 테스트로. **자기 산식으로 자기 산식을 검증하지 않는다** |
| 멱등성 | 같은 날 2회 수집 → 쓰기 0 (아카이버는 실환경에서 확인 완료) |
| 파싱 실패 | 구조가 바뀐 픽스처 → **실패하는가**(빈 값을 반환하면 그게 버그) |
| 경계값 | 분모 0 · 이닝 1/3 · 더블헤더 · 자정 넘김 · 시즌 경계 |
| 인가 | 허용목록 밖 계정이 실제로 차단되는가 |
| 채택 기준 | 새 테스트는 **고치기 전 코드에서 실패하는지** 확인 후 채택(뮤테이션 검사) |

보고는 항상 분모와 함께, **FAIL과 ERROR를 분리**해서.

|---|---|---|---|
| 1 | **Cloudflare Access 무료 티어의 사용자 수 상한** | 실측 안 함. 상한이 낮으면 접근 제어 설계가 바뀐다 | 착수 전 |
| 2 | D1 무료 한도가 실제로 충분한가 | 조사 보고서가 「미실측」으로 명시 | 파서 착수 전 |
| 3 | 간판 지표의 최종 산식·이름 | `sabermetrics-analyst` 작업 | 지표 정의서 작성 시 |
| 4 | 제품명 | 사용자 보류 | UI 착수 시 |
| 5 | `playbyplay`가 2025년부터인 이유 (기능 시작 / 롤오프) | 구별할 근거가 없다. 롤오프라면 2025분이 언젠가 사라진다 | 백필로 선확보 중 |
| 6 | 경기 진행 중 npb.jp의 갱신 거동 | 조사에서 유일하게 관측 못 한 항목 | v2 검토 시 (평일 18:00~21:30 JST) |
| 7 | 공개 전환(S2) 시점의 변호사 확인 | S1에서는 불필요 | S2 판단 시 |

## 12. 단계

```
v1  확정 데이터 + 자체 간판 지표 + 지인 한정 비공개
v2  라이브 (규정·소스 제약을 재평가한 뒤)
v3  공개 전환 검토 → 수익화 검토 (각각 재평가 게이트)
```

v1 완료 판정: §3의 「넣는 것」이 전부 화면에 있고, 지표가 공개 수치와 대조 통과하며, 수집이 자동으로 돌고, 신선도 표시가 작동한다.

## 13. 증분 분해

**이 스펙 전체는 한 번의 실행 계획으로 다루기에 크다.** 아래 증분마다 별도의 `writing-plans` 계획을 만든다. 각 증분은 **그 자체로 검증 가능한 산출물**을 남긴다.

| # | 증분 | 산출물 | 완료 판정 | 선행 |
|---|---|---|---|---|
| **A** | 아카이버 | `packages/archiver` | ✅ **완료** (43/43 통과, 실환경 확인) | — |
| **B** | 파서 | `packages/parser` | 저장된 픽스처에서 타석 레코드가 나오고, 구조 변경 픽스처에서 **실패**한다 | A |
| **C** | 지표 엔진 | `packages/metrics` | `docs/metrics/` 검증 케이스(공개 수치 대조)를 통과한다. I/O 의존 0 | 없음(병행 가능) |
| **D** | 저장소 | `packages/store` + D1 스키마 | 백필한 아카이브가 전량 적재되고 행수·합계 대조가 일치한다 | B |
| **E** | 집계 | `packages/aggregator` | 순위·스플릿·상대전적이 원시에서 재계산되고, 재실행이 멱등이다 | C·D |
| **F** | 간판 지표 | `docs/metrics/` + `metrics` 확장 | 득점기대치 행렬이 우리 아카이브에서 산출되고, 지표에 이름·정의·제외 범위가 명시된다 | C·D |
| **G** | 배포 | `packages/web` + Cloudflare Access | 허용목록 밖 계정이 차단되고, 4상태가 구별되며, 신선도 표시가 작동한다 | E·F |
| **H** | 자동화 | GitHub Actions | 1일 1회 자동 수집·적재·집계가 돌고, 실패가 보인다 | D·E |

**B와 C는 서로 의존하지 않으므로 병행할 수 있다.** C(지표)는 스택·소스 어느 쪽에도 의존하지 않아 가장 안전한 선행 작업이다.

⚠**증분 D 전에 §11 미결 2(D1 무료 한도 실측)를 해소한다.** 한도가 부족하면 저장소 선택이 바뀌고, D 이후에 알면 E까지 재작업이다.
⚠**증분 G 전에 §11 미결 1(Access 무료 사용자 상한)을 해소한다.**

# 옛 판이 새 판을 덮지 못하게 — 경기 적재의 판 가드와 경기 페이지 세트 기록

- 날짜: 2026-09-25
- 출처: 다방면 감사 `docs/audits/2026-09-25-multi-dimensional.md` 의 **C5**(P1)·**C6**(P1) — 둘 다 외부 블라인드 반증을 견뎠다
- 결정(사용자 · 2026-09-25): 접근 A · 옛 판을 감지하면 **실패로 끝내 배포를 막는다** · 재수집 입력 포함
- 고위험 영역: 멱등성(M5) · 정정 순서(M4/M9) · 데이터 계약 → 배포 전 `shiro-core:triple-review`(루트 §4)

## 0. 한 줄 요약

적재기는 **아카이브가 DB 보다 옛 판인 경기를 통째로 건너뛰고 실패로 끝내고**, 아카이버는 **경기 페이지 4장을 다 받았을 때만 한꺼번에 기록**하며
그 세트를 사이드카에 표시해 적재기가 대조한다. 옛 판이 감지되면 사람이 **그 날짜만 다시 받는** 수동 실행 입력으로 푼다.

## 1. 문제 — 실측

### 1-1. C5 · 경기 행은 판을 비교하지 않는다

- `packages/store/src/load.ts:215-276` `upsertGame` 은 `ON CONFLICT DO UPDATE` 로 **판을 비교하지 않고** 덮는다.
  덮는 열: 팀 코드 둘 · `status` · `not_played_reason` · `competition` · `series` · `source_url` · `fetched_at` · R·H·E 여섯 · `venue`
  (`season`·`game_date`·`game_no` 는 키가 결정하므로 일부러 안 덮는다 · 208-212행).
  `revision` 은 그중 **`series`·`source_url`·`fetched_at` 을 뺀** 열이 달라질 때만 +1 이다(245-265행).
  같은 파일의 `upsertProbablePitcher`(176-203)는 `WHERE probable_pitcher.fetched_at IS NULL OR (excluded.fetched_at IS NOT NULL AND excluded.fetched_at > probable_pitcher.fetched_at)` 로
  **더 새 판만 이기게** 한다(기존 행의 시각이 NULL 이면 새 값이 이긴다 · 새 값이 NULL 이면 덮지 않는다).
- 경기에 그 가드가 없는 것은 **결정이었다** — `packages/store/tools/load-archive.ts:262-270`:
  ① 경기당 `box.html.gz` 가 하나라 한 실행 안의 경합이 없다 ② **옛 아카이브로 되돌아가는 경우는 `archive-guard` 가 앞에서 막는다**.
- ⚠**전제 ②가 부분적으로 거짓이다.** `scripts/archive-guard.ts` 는 **`.gz` 파일 수 감소**와 **바이트 감소(0.5% 또는 1MiB 중 큰 것 초과)**만 본다.
  파일 수가 같은 채 일부 경기의 페이지만 옛 판이 되면 **통과한다.** 그런 경로가 둘 있다:
  1. **CI 업로드 부분 실패** — `.github/workflows/daily.yml` 「보관소에 올림」은 세대 `store-YYYYMMDD.tar` 와 `bb.sqlite.gz` 를 `--clobber` 로 올린다.
     `--clobber` 는 **기존 자산을 지운 뒤** 올리므로(워크플로 주석이 `gh` 원문을 인용한다) 오늘 세대 업로드가 실패하면 오늘 세대가 사라지고,
     다음 실행은 **어제 세대 + 그보다 새 DB** 를 복원한다(복원 302-362행). 그 사이 **새 페이지가 하나라도 늘었으면** 커밋된 매니페스트의 파일 수 검사가 막지만,
     **정정만 있던 경우**(파일 수 같음 · 바이트 차이가 허용 안)는 통과한다.
  2. **수동 백필 덧붙임** — 복원은 `archive-*.tar` 를 최신 세대 **위에** 푼다(330-348행 · 「겹쳐 풀어도 같은 파일」). 로컬에서 만든 덧붙임에 이번 시즌의 **옛 페이지**가 들어 있으면 새 페이지를 덮는다. 파일 수는 그대로다.
- 그 뒤 적재기가 옛 box 로 `upsertGame` 과 자식 행(타격·투수·타석·주자)을 다시 쓰면 **점수·안타·상태가 과거로 돌아가고 `revision` 은 오른다.**
  수집 창(`MAX_CATCHUP_DAYS`) 밖의 경기는 다시 받지 않으므로 **영영 안 돌아온다.** 화면에는 오류가 없다(침묵).
- 반증자 재현: 메모리 DB 에 새 판(득점 5)을 넣고 옛 판(득점 4)을 넣으면 득점 4 · revision 2 가 된다(감사 C5 절).

### 1-2. C6 · 경기 페이지 4장이 따로 저장된다

- `packages/archiver/src/archive.ts:203-209` `archiveGame` 은 `GAME_PAGES`(`index`·`playbyplay`·`box`·`roster` · `discover.ts:111`)를
  **페이지마다 `archiveUrl` 로 받자마자 기록**하고, revision 도 페이지마다 따로 센다.
- 그래서 `playbyplay` 만 실패하고 `box` 가 바뀌면 **box 는 새 판 · playbyplay 는 옛 판**이 된다.
  적재기는 box(218행~)를 기준으로 playbyplay(397행)·roster(434행)를 **판 대조 없이** 따로 읽으므로 DB 에 그대로 섞인다
  (박스 유래 값과 타석 로그 유래 세이버가 서로 어긋난다).
- **실측(2026-09-25 · 로컬 아카이브 · 읽기 전용)** — 둘을 쟀다:
  ⑴ **box `fetchedAt` 과 다른 페이지의 본 시각(§3) 차이가 10분을 넘는 경기**: 7,805경기 중 index **0** · playbyplay **0** · roster **0**(차이 중앙 6.1초 · 3.0초 · −3.0초).
  ⑵ **본문(gunzip 후) sha256 과 사이드카 `sha256` 의 불일치**: 경기 페이지 **31,220장 중 0**(사이드카 없음 0 · 읽기 오류 0).
  ⚠⑴은 「10분 넘게 떨어진 경기가 없다」까지만 말한다 — **같은 `archiveGame` 실행에서 나온 세트라는 증명이 아니다.**
  그래서 D3 의 「`set` 없는 기존 기록은 통과」는 **실측으로 뒷받침된, 그러나 증명되지 않은 수용 위험**이다(§6).
  → 소급 복구 작업은 이 설계의 범위가 아니다. ⚠로컬 아카이브는 2026-08-16 까지다. 그 뒤의 CI 아카이브는 안 쟀다.

## 2. 목표와 비목표

**목표**
- G1 적재가 **DB 보다 옛 판인 box** 로 경기를 되돌리지 못한다 — 경기 행과 **자식 행 전부**.
- G2 옛 판을 만나면 **조용히 넘기지 않는다** — 경기 ID 를 출력하고 종료 코드 1(→ 배포가 막힌다 · 사용자 결정).
- G3 아카이버는 경기 페이지 세트를 **다 받았을 때만** 기록한다. 하나라도 실패하면 **이전 세트를 그대로 둔다.**
- G4 기록 도중 죽는 등으로 세트가 섞였으면 적재기가 **알아차리고 그 경기를 건너뛴다**(실패로 센다).
- G5 사람이 옛 판 경기를 **CI 에서 그 날짜만 다시 받아** 풀 수 있다.

**비목표**
- `archive-guard` 확장(파일별 판 비교) — 적재기 가드가 경기 단위로 정확하므로 중복이다.
- DB 를 세대 tar 에 묶기(기각안 C · §8).
- 선수·予告先発·공표표 페이지의 세트화 — 한 URL 이 한 단위라 섞일 짝이 없다.
- 이미 옛 판으로 되돌아간 경기의 탐지·복구 — 되돌아간 뒤에는 DB 도 옛 값이라 비교 대상이 없다. 실측으로는 C6 혼합 0건이고 C5 는 안 쟀다(§6).
- **DB 가 없는 실행**(첫 실행 · `bb.sqlite.gz` 유실) — 비교할 관측이 없으므로 가드는 전부 「진행」이다. 이때 아카이브가 옛 세대면
  **그 사이의 정정은 아카이브에서도 DB 에서도 사라진다.** 그건 DB 되돌림(C5)이 아니라 **아카이브 자산 손실**이고 이 가드의 대상이 아니다.
  「DB 가 없으면 아카이브에서 다시 만든다」는 워크플로의 기존 결정(`daily.yml:349-358`)을 바꾸지 않는다.
- **상류가 내용을 되돌린 경우**(나중에 받은 페이지가 예전 내용) — 가드는 **우리 관측 시각**으로 판을 정한다. 더 늦게 본 내용은 그것이 예전 내용과 같아도 **현재의 참**으로 받아들인다.
  상류의 판 식별자(revision·as-of)는 페이지에 없다(`archive.ts:112-115` — 검증자 `etag`·`lastModified` 0건 실측).

## 3. 용어

| 말 | 뜻 |
|---|---|
| **본 시각**(`seenAt`) | 사이드카의 `max(fetchedAt, checkedAt)`. 「그 내용이 상류와 같다고 마지막으로 확인한 때」. `checkedAt` 이 없으면 `fetchedAt` |
| **옛 판** | 아카이브 box 의 본 시각이 DB `game.fetched_at` 보다 **이른** 경우 |
| **세트** | 한 경기에서 한 번의 `archiveGame` 이 기록한 페이지들. 사이드카의 `set` 값이 같다 |
| **보류**(`held`) | 받았고 내용이 바뀌었지만, 같은 경기의 다른 페이지가 실패해서 **기록하지 않은** 페이지 |

## 4. 설계

### D1. 적재기의 경기 단위 판 가드 — `packages/store/tools/load-archive.ts`

위치: box 사이드카 시각을 읽는 자리(현재 271-279행) **바로 뒤** · 대회 판정·`inProgress`·`notPlayed` 분기 **앞**.

1. box 사이드카에서 `fetchedAt` 과 `checkedAt` 을 읽는다. 지금의 `fetchedAtOf` 는 `fetchedAt` 만 돌려주므로 **둘 다 돌려주는 함수**로 바꾼다
   (못 읽으면 지금처럼 그 경기를 건너뛰고 `failed` — M11).
   ⚠**시각은 fail-closed 로 검증한다**: `fetchedAt` 은 `Number.isFinite(Date.parse(v))` 여야 하고, `checkedAt` 은 없거나 그 조건을 만족해야 한다.
   어기면 그 경기를 **건너뛰고 `failed`** 로 센다(무효 시각을 「0」이나 「지금」으로 메우지 않는다).
2. ⚠**판정과 쓰기를 한 트랜잭션에 둔다.** 파싱(대회·라인스코어·PBP·명단)은 지금처럼 트랜잭션 **밖**에서 하고,
   경기를 쓰는 트랜잭션(실시 경기의 쓰기 트랜잭션 · 미성립 분기의 트랜잭션 — 둘 다)의 **첫 문장**에서
   `SELECT fetched_at FROM game WHERE game_id = ?` 로 다시 읽어 판정한다. 옛 판이면 **그 트랜잭션에서 아무것도 쓰지 않고** 빠져나온다.
   그래서 「검사한 뒤 다른 적재기가 더 새 판을 커밋」한 경우에도 옛 판이 이기지 못한다.
   ⚠적재기는 `BEGIN`(지연 잠금)이라 두 적재기가 동시에 쓰면 SQLite 가 한쪽을 `SQLITE_BUSY` 로 실패시킨다 — 그것은 지금 동작 그대로 **실패로 보인다**(조용히 틀리지 않는다).
   CI 는 `concurrency` 로 직렬이다. 이 설계는 동시 적재를 **허용하려는 것이 아니라 끼어들어도 옛 판이 이기지 못하게** 하는 것이다.
   DB 의 `fetched_at` 이 무효 시각이면(파싱 불가) 역시 **건너뛰고 `failed`**.
3. 판정:
   - 행이 없거나 `fetched_at` 이 NULL → **진행**(처음 들어오는 경기).
   - `seenAt < fetched_at` → **옛 판**. 그 경기에 대해 **아무것도 쓰지 않고**(경기 행·자식 행·미성립 분기의 DELETE 전부) `staleArchive` 목록에 경기 ID 를 넣고 `continue`.
   - `seenAt >= fetched_at` → **진행**. ⚠**같은 시각도 진행한다** — 팀 코드 별칭 재정규화(`load.ts:223-227`)는 같은 판을 다시 적재해 기존 행을 고치는 데 의존한다.
4. `game.fetched_at` 에 쓰는 값은 **지금처럼 box `fetchedAt`** 이다(뜻을 바꾸지 않는다 — 「그 내용을 언제 받았나」). 비교에만 본 시각을 쓴다.
   ⚠이 비대칭이 필요한 이유: 재수집에서 상류 내용이 아카이브와 같으면 `unchanged` 라 `fetchedAt` 은 옛값이고 `checkedAt` 만 오른다.
   `fetchedAt` 으로 비교하면 그 경기는 **영원히 옛 판**이 된다. 반대로 복원 사고로 되돌아간 페이지는 사이드카도 같이 되돌아가 `checkedAt` 도 옛값이라 여전히 잡힌다.
5. 비교는 **ISO 8601 문자열을 `Date.parse` 한 밀리초**로 한다(문자열 사전순 비교 금지 — 소수 자릿수가 다르면 틀린다).
6. 끝에서: `staleArchive` 가 비어 있지 않으면 건수와 **경기 ID 전부**(날짜별로 묶어서)를 출력하고 종료 코드 1 에 합친다(현재 747행 식에 `|| staleArchive.length > 0`).
   출력에 복구 명령(§D4 의 입력 예)을 한 줄 붙인다.
7. 요약 줄(현재 700행)에 `옛 판 건너뜀 N건` 을 더한다 — **0 이어도 출력한다**(「0건」과 「안 쟀음」을 가른다).

⚠`load.ts` 의 `upsertGame` SQL 에 `WHERE` 를 다는 방식은 **쓰지 않는다** — 자식 행은 같은 트랜잭션에서 통째로 갈아 넣으므로(`replacePaEvents` 등) 경기 행만 지키면 **자식만 옛 판**인 새 혼합이 생긴다.
262-270행의 결정 주석은 **전제 ②가 거짓이었다는 근거(§1-1)와 함께** 새 결정으로 바꿔 적는다.

### D2. 아카이버의 세트 기록 — `packages/archiver/src/archive.ts` · `sink.ts`

**`archiveUrl` 을 둘로 나눈다(규칙은 한 벌 · M1).**
- `prepareUrl(key, url, deps) → Prepared` — 받기와 판정까지. **기록하지 않는다.** 결과는 `unchanged`(304 또는 같은 sha) · `absent`(404/410) · `failed` · `changed`(새 본문과 새 `BlobMeta` 를 들고 있음).
- `commitPrepared(prepared, deps, extra) → Promise<PageResult>` — `changed` 면 `sink.write`, `unchanged` 면 `markSeen`, 나머지는 아무것도 안 한다.
  ⚠**던지지 않는다.** `sink` 가 던지면 잡아서 `{ outcome: "failed", error }` 를 돌려준다 — 지금 `archiveUrl` 이 저장 예외까지 `failed` 로 바꾸는 것(156-194행 한 `try`)과 같은 결과다.
- `archiveUrl` = `prepareUrl` → `commitPrepared`. **공표표·선수·予告先発 등 기존 호출자의 동작은 그대로다**(외부 요청 수·순서·결과 값 동일).

**`archiveGame` 은 이렇게 바뀐다.**
1. `GAME_PAGES` 순서대로 4장을 **모두** `prepareUrl` 한다. ⚠요청 수·순서·간격은 지금과 같다(L1). 중간에 실패해도 나머지를 계속 받는다(지금과 같다).
2. 하나라도 `failed` 면(⚠**`index` 포함** — 적재기는 `index` 를 안 읽지만 세트는 4장 전부다. 맞교환: `index` 만 실패해도 그날 box 갱신이 보류된다. 대신 규칙이 「전부 아니면 전무」 하나라 예외 목록이 없다):
   - `changed` 페이지는 **기록하지 않고** 결과를 `held` 로 돌려준다.
   - `unchanged` 페이지는 `markSeen` 을 하되 **`set` 값을 바꾸지 않는다**(아래 3의 `set` 을 붙이지 않는다) — 「봤다」는 사실은 참이다.
   ⚠**「있던 페이지가 404/410」도 실패로 센다.** `prepareUrl` 이 `absent` 를 돌려줬는데 그 키의 사이드카가 **이미 있으면**(`prev !== null`) `archiveGame` 은 그 페이지를
   `failed`(`error: "있던 페이지가 사라졌다"`)로 바꾼다 — 옛 사이드카가 옛 `set` 을 든 채 남아 D3 가 영원히 어긋나는 것을 막고, 상류가 페이지를 지운 이상 사태를 사람이 보게 한다.
   기존 본문·사이드카는 **지우지 않는다**(소급 불가 자산). 처음부터 없던 페이지의 404(`prev === null`)는 지금처럼 `absent` 이고 세트의 정상 구성원이다.
   ⚠이 규칙은 `archiveGame` 안에만 둔다 — 공표표 등 `archiveUrl` 단독 호출자의 `absent` 의미는 바꾸지 않는다.
3. 실패가 없으면 세트 id `set = clock.now().toISOString()` 을 **한 번** 만들고, `GAME_PAGES` 순서대로 `commitPrepared` 한다 — `changed` 는 `write`, `unchanged` 는 `markSeen` 이고 **둘 다 사이드카에 `set` 을 적는다.** `absent`(처음부터 없음)는 사이드카가 없으므로 적을 곳이 없다.
4. ⚠**기록 도중 실패**: `commitPrepared` 가 어떤 페이지에서 `failed` 를 돌려주면 **거기서 멈춘다.** 그 뒤 페이지의 `changed` 는 `held`, `unchanged` 는 `markSeen` 없이 `unchanged` 로 돌려준다.
   이미 기록한 앞 페이지는 **되돌리지 않는다**(되돌리기 자체가 또 실패할 수 있다) — 그 경기는 새 `set` 과 옛 `set` 이 섞인 상태가 되고 **D3 가 잡아 적재를 건너뛴다.**
   다음 실행(수집 창 안이면 자동 · 밖이면 D4 재수집)이 세트 전체를 다시 기록해 풀린다.
5. 각 파일 쓰기는 본문 `rename` 다음 사이드카 `rename` 이다(`sink.ts:118-123` · `141-149`). ⚠**둘 사이에서 죽으면 본문은 새 판 · 사이드카는 옛 판(옛 `sha256`·옛 `set`)이 된다** —
   `set` 비교만으로는 못 잡으므로 **D3 가 본문 sha 도 대조한다.**

**타입**
- `BlobMeta` 에 선택 필드 `set?: string` 을 더한다. ⚠없는 사이드카(기존 전부)를 **깨진 것으로 읽지 않는다.**
- `BlobExtra` 에 `set?: string` 을 더한다(`markSeen` 과 `write` 양쪽에서 쓰려고).
- `PageOutcome` 에 `"held"` 를 더한다. `summarize` 는 `held` 를 따로 센다. ⚠`held` 는 실패가 아니다 — 그 경기에 **이미 `failed` 가 있으므로** CLI 의 종료 코드는 지금 규칙(실패가 있으면 1)으로 이미 1 이다.
- `MemorySink`(시험용)도 같은 계약을 지킨다.

### D3. 적재기의 세트 대조 — `load-archive.ts`

**순서**: 파싱 단계(쓰기 트랜잭션 **전**)에서 ① 본문 무결성(아래) → ② `set` 대조 → 그다음 쓰기 트랜잭션 안에서 D1 판 가드. 셋 중 하나라도 걸리면 그 경기는 아무것도 쓰지 않는다.

box·playbyplay·roster·index 사이드카의 `set` 값을 모은다(사이드카가 없는 페이지 = 처음부터 없던 `absent` 는 제외).
- **아무 페이지에도 `set` 이 없다** → **기존 기록(D2 이전)으로 보고 통과**. 근거: §1-2 실측 혼합 0/7,805.
- **모두 같은 값** → 통과.
- **그 밖**(값이 둘 이상이거나, 어떤 페이지엔 있고 어떤 페이지엔 없음) → 그 경기를 **아무것도 쓰지 않고** 건너뛰고 `setMismatch` 목록에 넣는다. 종료 코드 1 에 합친다.
  ⚠이것이 잡는 것: D2 기록 도중 죽은 경우 · 누가 페이지 파일을 따로 바꿔 넣은 경우.
  ⚠기존 경기가 D2 이후 처음 다시 받히면 **세트 전체에 `set` 이 한꺼번에 붙으므로**(`unchanged` 도 `markSeen` 으로 적는다) 섞이지 않는다.

**본문 무결성**: 적재기가 실제로 읽는 페이지(box · playbyplay · roster)는 gunzip 한 본문의 sha256 을 계산해 **그 사이드카의 `sha256` 과 같아야 한다.**
다르면 그 경기를 **아무것도 쓰지 않고** 건너뛰고 `integrityMismatch` 목록에 넣는다(종료 코드 1). 이미 gunzip 하는 본문이라 추가 읽기는 없다.
`set` 대조보다 **먼저** 한다(본문이 사이드카와 안 맞으면 그 사이드카의 `set` 은 믿을 근거가 없다).
실측: 기존 아카이브 31,220장 전부 일치(§1-2 ⑵) — 이 검사가 첫 배포에서 기존 기록을 거짓으로 걸지 않는다.
⚠roster 는 「적재를 멈추지 않는 보충」(현재 429-432행)이지만 **무결성 불일치는 예외로** 경기를 건너뛴다 — 본문과 사이드카가 어긋났다는 것은 그 경기 디렉터리가 기록 도중 죽었다는 신호이기 때문이다.

### D4. 재수집 입력 — `.github/workflows/daily.yml` · `scripts/update.ts`

- `workflow_dispatch` 에 입력 `refetch_dates`(문자열 · 선택)를 더한다.
- 수집 단계는 그 값을 **환경변수 `BB_REFETCH_DATES` 로만** 넘긴다. ⚠`run:` 안에 `${{ inputs.refetch_dates }}` 를 직접 쓰지 않는다(스크립트 인젝션 · D1 security).
- `update.ts` 는 `BB_REFETCH_DATES` 가 비어 있지 않으면:
  - 형식을 검증한다 — 쉼표로 나눈 `YYYY-MM-DD` 가 **1~7개**, 각각 실재하는 날짜, 중복 없음. 틀리면 **종료 코드 2 로 즉시 멈춘다**(아무것도 받지 않는다).
  - 그 날짜들을 **수집 창 대신** 받는다(`--date` 와 같은 어법 — 「날짜를 명시하면 그날만」). 적재와 이후 단계는 그대로다.
  - 상한 7 은 L1 근거다: 하루 최대 6경기 × 4장 × 7일 = 168요청 ≈ 3초 간격 8.4분.
- ⚠수동 실행 전용이다. 크론 실행에서는 값이 비어 있어 **지금과 동작이 같다.**

## 6. 미측정 전제 — 틀리면 무엇이 바뀌나

- **CI 아카이브의 혼합·옛 판 실재 여부는 안 쟀다**(로컬 아카이브는 2026-08-16 까지). 배포 첫 실행에서 `옛 판 건너뜀`·`세트 불일치` 가 0 이 아니면 **이미 일어난 일**이다 — 런북대로 푼다.
  ⚠첫 실행이 빨개질 수 있다는 것을 배포 보고에 미리 적는다.
- `gh release upload` 가 자산 여러 개를 줄 때 **어느 순서로 지우고 올리는지**는 안 쟀다. §1-1 경로 1 은 「오늘 세대만 사라지고 DB 는 새것」이 가능하다는 것까지만 주장한다.
- 러너 시계 역행(§5 「시계가 뒤로 간 러너」)은 안 쟀다.
- **「관측 시각의 순서 = 내용 판의 순서」를 전제한다**(§2 비목표 마지막 줄). 우리 수집기의 시계가 판을 정한다.
- **`set` 없는 기존 기록이 섞이지 않았다**는 것은 증명이 아니라 실측 근거의 수용이다(§1-2 ⑴ — 10분 기준 · 네 페이지 전부 0건).

## 7. 시험 · 검증 — 완료 기준

⚠**새 시험은 고치기 전 코드에서 먼저 실패하는지 확인한 뒤** 채택한다(뮤테이션 검사 · 루트 §1).

**적재기(D1·D3)** — 임시 아카이브 디렉터리 + 메모리/임시 SQLite 로 `load-archive.ts` 를 실제로 돌리는 기존 시험 방식을 따른다.
1. 새 판(득점 5 · seenAt t2) 적재 뒤 옛 판(득점 4 · seenAt t1<t2) 적재 → 득점 5 · revision 불변 · **타격·타석 행도 새 판 그대로** · 종료 코드 1 · 출력에 경기 ID.
2. 같은 판을 두 번 적재 → 종료 코드 0 · revision 불변(멱등 · 기존 시험과 같아야 한다).
3. 별칭 재정규화: 같은 시각의 같은 판을 다시 적재했을 때 팀 코드가 갱신된다(`game-upsert.test.ts` 의 기존 기대가 계속 통과).
4. `fetchedAt` 은 옛값이지만 `checkedAt` 이 DB 보다 늦은 box → **진행**(본 시각 규칙).
5. 옛 판 **미성립** box 가 실시로 들어 있는 경기의 자식 행을 **지우지 않는다.**
6. 세트: 모든 사이드카에 `set` 없음 → 통과 · 모두 같음 → 통과 · box 만 다른 `set` → 건너뜀·종료 코드 1 · 일부만 `set` 있음 → 건너뜀.
7. 요약 줄에 `옛 판 건너뜀 0건` · `세트 불일치 0건` · `본문 불일치 0건` 이 **0 일 때도** 찍힌다.
7a. 트랜잭션 안 판정: 판정 함수가 쓰기 트랜잭션 안에서 DB 를 다시 읽는다는 것을, **파싱 뒤·트랜잭션 전에 더 새 `fetched_at` 을 심는** 훅(또는 판정·쓰기를 묶은 순수 함수에 DB 를 주입)으로 확인한다 — 결과: 옛 판이 안 쓰이고 `staleArchive` 에 들어간다.
7b. 무효 시각 표: box `fetchedAt` 무효 · `checkedAt` 무효 · DB `fetched_at` 무효 → 전부 건너뜀·`failed` · 소수 자릿수가 다른 두 ISO(`…:00.5Z` 대 `…:00.500Z`)와 같은 밀리초 → 「같은 시각」으로 진행.
7c. 본문 무결성: box 본문 한 바이트를 바꾼 픽스처 → 건너뜀·`integrityMismatch`·종료 코드 1 · DB 불변.

**아카이버(D2)** — 가짜 fetcher + `MemorySink`.
8. 가짜 fetcher 가 `index` 같은 본문 · `playbyplay` 예외 · `box` 바뀐 본문 · `roster` 같은 본문을 돌려줄 때 → 결과가 정확히 `[unchanged, failed, held, unchanged]` · sink 의 box 본문·revision 이 이전 그대로 · sink 에 새 box 쓰기 0회.
9. 전부 성공 → 바뀐 페이지는 새 revision, 안 바뀐 페이지는 `checkedAt` 갱신, **네 사이드카의 `set` 이 모두 같다.**
10. 실패가 있을 때 `unchanged` 페이지는 `checkedAt` 은 오르고 **`set` 은 이전 값 그대로.**
11. `archiveUrl` 을 쓰는 기존 호출자 시험(공표표·선수·予告先発)이 **변경 없이** 통과.
12. 요청 수·순서가 지금과 같다 — 가짜 fetcher 의 호출 기록을 기존 순서와 대조.
12a. 픽스처: `index` 같음 · `playbyplay` 바뀜 · `box` 바뀜 · `roster` 같음. 고장 주입 sink 가 `playbyplay` 의 `write` 에서 던짐 → 결과 `[unchanged(set 새것), failed, held, unchanged(markSeen 없음)]` · `archiveGame` 은 던지지 않음 · 첫 페이지 사이드카만 새 `set`.
12b. 고장 주입 sink: `writeMeta` 에서 던짐(본문은 이미 교체) → 결과 `failed` · 그 뒤 페이지 `held` · 이 상태의 아카이브를 적재기(7c 방식)가 `integrityMismatch` 로 건너뛴다.
12c. 있던 playbyplay 가 404 → 결과 그 페이지 `failed`(「있던 페이지가 사라졌다」) · 다른 바뀐 페이지 `held` · 기존 playbyplay 본문·사이드카 보존. 처음부터 없던 페이지의 404 는 `absent` 이고 세트가 기록된다.

**재수집 입력(D4)**
13. `BB_REFETCH_DATES` 검증: 빈 값 → 기존 창 · 정상 3일 → 그 3일 · 8일 → 종료 2 · `2026-02-30` → 종료 2 · `2026-08-01;rm -rf` → 종료 2 · 중복 → 종료 2. (날짜 계산은 `scripts/date-window.ts` 처럼 import 가능한 순수 함수로 두고 거기에 시험을 붙인다 — `update.ts` 는 import 하면 수집을 시작한다.)
14. `scripts/test/workflow-*.test.ts` 류 정적 시험: `daily.yml` 의 `run:` 블록 어디에도 `inputs.refetch_dates` 가 **직접** 나오지 않는다(환경변수로만).

- **C — DB 를 세대 tar 에 묶어 같은 시점으로 복원**: CI 경로는 막지만 **수동 백필 경로를 못 막는다.** 세대 크기와 운영 배선이 크게 바뀐다.
- **`upsertGame` 의 `WHERE` 만**: 자식 행이 옛 판으로 덮여 새 혼합을 만든다(D1 끝).
- **옛 판이면 경고만 하고 계속**: 아카이브 자산 손실(옛 판이 된 원인)을 아무도 모른다 — 사용자가 「실패로 끝내 배포를 막는다」를 골랐다.
- **`archive-guard` 에 파일별 판 비교**: 매니페스트가 공개 저장소에 커밋되는 파일이라 경기 수만큼의 목록을 싣기 어렵고, 적재기 가드가 경기 단위로 이미 정확하다.

# B안 —「年鑑組み」(Yearbook Setting)

> **한 줄**: 선을 줄이는 대신 **선에 위계를 준다**. 괘선 6단·활자 7단·자간을 HIG 트래킹표 안으로
> 되돌려, 표의 밀도를 **한 줄도 깎지 않고** 「투박함」을 지운다.

**가설**: 이 화면의 문제는 「선이 많다」가 아니라 **「선이 전부 같은 1px `#e0dfd8` 이라 위계가 없다」**다.
신문·연감·기록집은 선을 훨씬 많이 쓰고도 세련됐다 — 굵기·농도·용도가 각각 다르기 때문이다.

산출물: `docs/superpowers/specs/mockups-2026-09-07/b-almanac.html` (단일 파일 · 외부 의존 0 · 이미지 0)

## 0. 실측 (Chromium 1234 · DPR2 · Playwright)

⚠**아래는 전부 브라우저에서 잰 값이다. 읽어서 판단한 것이 아니다** — 이번 세션에서 표가 깨진 원인이
정확히 「읽어서 판단」이었다(§5 참조).

| | **1280** (desktop) | **390** (`pointer:coarse` 에뮬레이트) |
|---|---|---|
| 페이지 가로 넘침 | **없음** | **없음** |
| 가로 스크롤 영역 수 | **0** | **4 (전부 표)** ← 감사가 짚은 4개(내비·시즌띠·탭줄·표) 중 **표만 남음** |
| DOM 노드 | **1,077** | 1,077 (현재 홈 **1,094** — 밀도 유지) |
| 머리(柱) 높이 | 148px | **176px** |
| 표 본문 1행 높이 | 58px | 64px |
| 각주 | 13px / 행송 23px / **38字·行** | 동일 |
| `h2` 자간 | −0.204px = **−0.012em** | −0.192px = −0.012em |
| `h1` 자간 | −0.66px = **−0.022em** | −0.55px = −0.022em |
| 目次 행 높이 | 32px | **41px** |
| 내비 항목 높이 | 37px | 36px |
| 콘솔 오류 | **0** | **0** |

**대비(WCAG AA · 렌더된 실제 색으로 계산)**: 라이트 **17/17 통과** · 다크 **17/17 통과**.
가장 아슬아슬한 것이 각주 **5.19:1**(13px, 기준 4.5:1)이다.
⚠팔레트를 짜면서 두 값이 기준 미달이라 고쳤다: `ink-3` **4.40:1 → 5.19:1**(`#6e6e69`→`#5f656e`),
`clay` **4.48:1 → 5.11:1**(`#b8651f`→`#9c520f`, 라이트만).

**모션 감소**: `prefers-reduced-motion: reduce` 에서 `transform:none` · `animation-name:none` 실측.

**키보드**: 포커스→툴팁 열림 · Enter 토글 · Enter 재토글 · Escape 닫힘 — **현 사이트 동작 그대로**.
첫 포커스가 `skip` 링크. 표 5개 전부 `tabindex="0"` + `role="region"` + `aria-label`.
`th[scope="colgroup"]` 19개 · `th[scope="col"]` 38개 · 막대 `role="img"` 12개.

**표가 390에서 성립하는가** (표를 오른쪽 끝까지 민 상태에서 측정):
`spanAllSameY: 1` · `hdAllSameY: 1` · `bodyAllSameY: 1` → **세 행 모두 각각 한 줄**.
`cellsPerBodyRow: 10` → **팀 하나가 한 행에 10칸 전부**. 고정열 順位(x=12,w=29)·球団(x=40,w=64)이
붙어 있는 동안 3번째 칸은 x=−146 — **고정이 실제로 작동한다.** 라이트·다크 동일.

## 1. 읽은 HIG 절과 무엇을 가져왔는가

⚠**한국어 페이지(`/kr/design/human-interface-guidelines/…`)는 JS 렌더링이라 본문이 안 나온다** —
제목만 돌아왔다. 실제로 읽은 것은 사이트가 로드하는 원본 JSON
`developer.apple.com/tutorials/data/design/human-interface-guidelines/<절>.json` 이다.
**받은 것 7개, 실제로 읽고 쓴 것 5개** (`color` · `tab-bars` 는 받았지만 안 읽었다 — 정직하게 적는다).

### 읽은 절
1. **Typography** — Ensuring legibility / Conveying hierarchy / Using system fonts /
   Supporting Dynamic Type / **Specifications: iOS Large (default) 사이즈표 + SF Pro Tracking values 표**
2. **Layout** — Best practices / Visual hierarchy / Adaptability / Guides and safe areas
3. **Accessibility** — 대비표 · 컨트롤 크기표 · Reduce Motion 목록
4. **Segmented controls** — Best practices / Content
5. **Motion** — Best practices / Providing feedback

### 가져온 것

**(1) 활자 7단이 전부 HIG Large(default) 행에 대응한다.** 임의로 고른 크기가 하나도 없다.

| 이 안의 토큰 | 값 | 대응하는 HIG 행 |
|---|---|---|
| `--t-mast` | 30 / 32 | Title 1 = 28 / 34 |
| `--t-sec` | 17 / 22 | **Headline = 17 / 22** |
| `--t-body` | 13 / **23** | Footnote = 13 / 18 (⚠행송을 和文용으로 넓혔다) |
| `--t-data` | 13 / 18 | **Footnote = 13 / 18** |
| `--t-num` | 15 / 18 | Subhead = 15 / 20 (emphasized) |
| `--t-lab` | 11 / 14 | **Caption 2 = 11 / 13** |
| `--t-cap` | 10 / 13 | Caption 2 아래 — 단독으로 읽히지 않는 라벨에만 |

**(2) 트래킹표 — 이 안에서 가장 크게 작동한 발견.**
HIG의 SF Pro tracking values (1/1000 em): `6pt +41` · `11pt +6` · `12pt 0` · `14pt −11` ·
**`17pt −26`** · `20pt −23` · `24pt +3` · `28pt +14` · `32pt +13`.

> ⚠**표 전체가 ±0.041em 안에 있고, 12pt 이상은 전부 ±0.026em 안에 있다.**

현 사이트: `.block>h2{letter-spacing:.16em}` · `.rdlab{.14em}` · `.idline .nm{.08em}`
→ **HIG 표 전 범위의 4~6배 바깥**이다. 게다가 방향도 반대다(HIG는 큰 활자를 **좁힌다**).
`frontend-design` 스킬이 「생성된 페이지의 가장 흔한 신호」로 꼽는
**「자간 벌린 대문자 eyebrow 라벨」**과 정확히 같은 모양이다.

→ 이 안: `h2` **−0.012em** · `h1` **−0.022em** (둘 다 실측). 양(+)의 자간은
**11px 이하 일본어 마이크로 라벨에만 +0.04em** 남겼다. **페이지 최대 자간 0.16em → 0.045em.**

**(3) "Minimize the number of typefaces you use" → 서체를 **하나**로 줄였다.**
현 사이트의 `--f-num`(SFMono/Consolas 모노스페이스)을 **버렸다**. 모노스페이스는 *코드용* 서체이고
기록집의 숫자 조판이 아니다. 숫자는 **크기·굵기·`font-variant-numeric: tabular-nums`** 로 구분한다.
⚠**이건 취향이 아니라 결함 수정이기도 하다** — 현재 `.wlnum`(모노 13px)과 그 안의
`.wlnum s`(Yu Gothic 9.5px)가 붙어 있어서 **숫자 하나 안에 서체가 둘**이다.
그리고 산문에는 `proportional-nums`, 표에는 `tabular-nums` 로 갈랐다(현 사이트는 산문에도 모노를 쓴다).

**(4) "In general, avoid light font weights… prefer Regular, Medium, Semibold, or Bold"**
→ 서체 스택 첫머리를 `"Hiragino Kaku Gothic ProN", "Yu Gothic Medium", "Yu Gothic"` 로 잡았다.
Windows의 Yu Gothic **Regular는 실제로 너무 가늘다** — 현 사이트 스택은 `"Yu Gothic"` 부터 시작한다.

**(5) Layout / "Group related items": "you might use negative space, background shapes, colors,
materials, or **separator lines** to show when elements are related"**
→ **HIG가 괘선을 그룹핑 장치로 명시적으로 허락한다.** B안의 전제가 여기 서 있다.

**(6) Accessibility 대비표**(≤17pt → 4.5:1 / 18pt → 3:1 / Bold → 3:1)와
**컨트롤 크기표**(iOS 기본 44×44 · **최소 28×28**) — §0의 판정에 그대로 썼다.

**(7) Reduce Motion 목록**: "Replacing transitions in x-, y-, and z-axes with fades to avoid motion"
→ 감소 모드에서 유일한 로드 애니메이션을 최종 상태로 고정.

**(8) Segmented controls — 이 안의 UX 판정 근거.**
> "**Aim for no more than about five to seven segments in a wide interface and no more than about
> five segments on iPhone.**" · "**In general, keep segment size consistent.**"

현재 `.hjump` 는 **7개 · 폭이 제각각 · 390에서 가로 스크롤**이다.
→ **HIG 자신의 기준으로 이건 세그먼트 컨트롤이 아니다.** 그리고 뷰 전환도 아니라 문서 내 앵커다
("For switching between completely separate sections of an app, use a tab bar instead" — 그것도 아니다).
**남는 정답은 「순서 있는 목록」, 즉 目次다.**

**(9) Motion**: "Add motion purposefully… Don't add motion for the sake of adding motion" +
"in apps, generally avoid adding motion to UI interactions that occur frequently."

## 2. ⚠HIG와 편집 디자인이 어긋난 자리 — **이 안의 값어치는 여기 있다**

**T1. 트래킹표는 SF Pro *라틴* 기준이고, 이 화면은 대부분 일본어다.**
和文 견출 10~11px는 자간을 조금 벌리는 것이 실제로 읽기 쉽다 — 작은 한자가 덩어리로 뭉치기 때문이다.
HIG에는 그것에 대한 말이 **없다**. → **갈랐다**: 라틴·숫자는 HIG를 따르고(≤|0.02em|),
**일본어 11px 이하 라벨만 +0.04em**. 그래도 현재의 4분의 1이다.
⚠**미해결**: 일본어 조판 전문가 검토 없음. macOS Hiragino 에서 안 봤다.

**T2. 탭 영역: HIG는 44×44를 원하고, 연감은 좁은 행송을 원한다.**
실측 目次 행 **41px** · 내비 **36~37px** — HIG **최소치(28) 위, 기본치(44) 아래**다.
전부 44로 올리면 모바일 머리에 **약 90px**이 더 붙는다(= 코디네이터가 지적한 바로 그 비용).
→ **밀도를 골랐다. 이건 HIG로부터의 실질적 이탈이고, 이 안을 기각할 정당한 사유가 된다.**

**T3. HIG: "Extend content to fill the screen or window."** — **이 안은 정반대로 간다.**
각주는 **38字·行(527px)** 에서 멈추고, 6열 표는 **676px** 에서 멈춘다(지면은 1,128px).
앱 UI에서는 「덜 만든 레이아웃」으로 보이고, 책에서는 **欄外**이고 눈이 쉬는 자리다.
→ **이 안에서 미학적으로 가장 큰 베팅이고, 「구성된 여백」이 아니라 「빈 화면」으로 읽힐 위험이 가장 큰 지점이다.**

**T4. Dynamic Type: "Consider adjusting your layout at large font sizes… Reduce the number of
columns when the font size increases."**
이 안은 **고정 행송 22px + 괘선 사다리** 위에 서 있어 스택형 앱 레이아웃보다 **덜 유연하다.**
⚠**200% 확대·최소 글꼴 강제에서 테스트하지 않았다.**

**T5. HIG: "Differentiate controls from content. Take advantage of the Liquid Glass material."**
→ **거부했다.** glass 계열은 이 제품의 「AI틱함」 금지 목록이고, 데이터 화면에서 대비를 갉아먹는다.
대신 **반경이 「누를 수 있음」의 유일한 표식**이다 — 조작물만 `2px`, 구조물은 전부 `0`.
(루트 §7의 「모든 요소에 같은 border-radius」에 대한 이 안의 답이다.)

## 3. 무엇을 바꿨고 왜인가

### 3-1. 괘선 6단 — 이 안의 심장

굵기 **×** 잉크농도로 사다리를 만들었다. 괄호는 `--field` 대비 실측.

| 토큰 | 값 | 용도 | 대비 |
|---|---|---|---|
| — | 없음 | 같은 그룹 안 (정렬만으로) | — |
| `--r-hair` | 1px @ .10 | 표의 **행** 사이 | 1.23:1 |
| `--r-fine` | 1px @ .22 | **欄(열 그룹)** 구분 · 각주 위 | 1.60:1 |
| `--r-med` | 1px @ .55 | 欄見出し 아래 · **고정열 경계** | **3.95:1** |
| `--r-bold` | 2px @ 1.0 | **節의 경계** | 17.2:1 |
| `--r-mast` | 4px @ 1.0 | 紙面의 柱 (**한 면에 한 번**) | 17.2:1 |

⚠**아래 3단이 3:1 미만인 것은 의도다.** WCAG 1.4.11은 「UI 부품과 상태를 **식별하는 데 필요한**
시각 정보」에 3:1을 요구한다. 행 사이 hair 는 **마크업(`<tr>`)이 이미 갖고 있는 정보의 장식**이라
여기 해당하지 않는다. **식별에 필요한 것**(고정열 경계 · 절 경계 · 欄見出し)은 전부 **3.95:1 이상**이다.

### 3-2. 좁은 화면의 가로 스크롤 **4 → 1(종류)**

감사가 짚은 「첫 화면에 가로 스크롤 4개, 무엇을 밀어야 하는지 모른다」에 대한 답이다.

| | 현재 | 이 안 | 방법 |
|---|---|---|---|
| 내비 | 숨은 스크롤 | **없음** | 5×2 격자로 줄바꿈. 잘린 `他大…` 도 사라진다 |
| 시즌 띠 | 숨은 스크롤 | **없음** | 2자리 스텁(`'24`)로 한 줄. 4자리는 `aria-label` 에 |
| 탭 줄(7개) | 숨은 스크롤 | **없음** | **目次**로 대체 (HIG 근거는 §1-(8)) |
| 표 | 스크롤 | **스크롤** | 원리적으로 불가피 — 10열이 390에 들어가지 않는다 |

⚠**표는 못 고친다. 대신 「유일하게 만들었다」** — 밀 수 있는 것이 한 종류뿐이면
「어느 것을 밀어야 하는가」라는 질문 자체가 사라진다. 거기에 셋을 더했다:
① 고정열 오른쪽에 `--r-med`(3.95:1) 경계, ② **실제로 가려진 내용이 있을 때만** 켜지는 가장자리 그라데이션
(`data-more` 를 스크롤마다 다시 계산 — 끝까지 밀면 `0`으로 꺼지는 것 실측), ③ 좁은 폭에서만 나오는
한 줄 캡션 「この表は横に長いため、表の中だけが横にスクロールします。」(아이콘이 아니라 **글자**).

### 3-3. 目次 — 옛 탭 줄 자리

번호 · 제목 · **리더 점선** · 건수(2試合 / 6球団 / 12件 …). 건수는 **실제 데이터에서 센 값**이고
지어내지 않았다. 리더 점선은 목차 고유의 조판 장치라 「AI틱함」 목록의 어디에도 걸리지 않는다.
번호는 `frontend-design` 이 요구하는 조건("check the content really is a sequence")을 만족한다 —
**페이지의 목차는 실제로 순서다.**

⚠**sticky 를 버렸다.** 대신 **走り柱(running head)** — 題字를 지나치면 34px 띠가 내려와
`2025年 │ 지금 읽는 절 이름 │ 目次へ` 를 말한다. 연감의 장치이고, **세로를 0px 쓴다**
(sticky 탭 줄은 항상 자리를 먹는다). 실측: y=0, h=34, 절 이름 추종 정상.

### 3-4. 각주 — 「읽기 쉬움과 정직함을 동시에」

**한 글자도 지우지 않았다.** 대신 조판을 바꿨다.

| | 현재 | 이 안 |
|---|---|---|
| 크기 / 행송 | 11px / 미지정 | **13px / 23px** |
| 측정 | `max-width:64ch` (和文 11px면 700px 이상) | **38em = 38字·行** (실측 38) |
| 표식 | 없음 | **하잉 「注」** (여백에 매달린다) |
| ⚠ 경고 | 본문에 섞임 | 왼쪽 여백에 **`--stitch` 2px 세로 괘** |
| 대비 | 5.12:1 | **5.19:1** |

38字는 일본어 서적 조판의 고전적 一行字数(38~42)다. **긴 글을 읽히게 하는 것이 편집 디자인의 본업**이고,
이 안이 가장 강해야 하는 자리라고 판단했다.

### 3-5. 그 밖

- **세로 척도**: 전부 행송 22px에서 파생(`3 / 6 / 11 / 22 / 33 / 44`). 감사의 「눈에 보이는 척도가 없다」에 대한 답.
- **구단색은 언제나 「괘」**로만 나온다(도형 칩 폐지). 표 안에서도, 목록 안에서도 같은 장치.
- **欄(column group) 머리**: 順位表는 `球団 / 勝敗 / 得失点 / 近況 / 見通し` 5欄. 기록집의 스팬 헤드다.
  ⚠**머리가 한 행 늘 뿐 본문은 팀당 한 행 그대로**다(실측 `cellsPerBodyRow: 10`).
  가로로 밀 때 「지금 어느 欄인가」를 말해 주므로 스크롤의 비용도 낮춘다.
- **표는 지면을 채우지 않는다**: 6열 표를 1,128px로 늘리면 마지막 열이 시야 밖에 홀로 남는다(감사 §2-4).
  `--measure-table: 52em`(676px)에서 멈춘다. **順位表만 예외** — 막대가 비교의 실체라 폭을 다 쓴다.
- **행 hover**: 배경을 칠하지 않고 **그 행의 괘가 hair→med로 굵어진다.**
- **모션**: 현 사이트의 **절마다 `rise` 페이드를 없앴다**(그게 바로 「AI틱함」의 기본값이다).
  대신 **조판된 순간 하나** — 順位表의 승패 막대가 **순위 순으로 55ms씩 밀려 그려진다**(scaleX).
  움직임이 **순위**라는 뜻을 갖는다. 나머지 모션은 전부 사용자 동작의 응답이다.

## 4. 일부러 **안** 바꾼 것

- **도메인 팔레트** — 감청 승리막대 / 주황(土) 패배막대 / up·dn. 감사가 "개선하다 부수면 안 되는 것"으로
  꼽았다. 회색만 같은 청흑으로 다시 물들이고, **AA 미달 두 값만** 고쳤다(§0).
  ⚠`frontend-design` 이 AI 신호로 꼽는 **크림(#F4F1EA)+테라코타** 조합으로 흘러가지 않게
  종이를 **`#f2f1ea`(약간 황록 · 신문지)** 로 잡았다. 분홍-탄 계열이 아니다.
- **각주 문장 전부** — ⚠ 글자까지 원문 그대로.
- **값이 주역 · 라벨과 분모가 인접**(§6 도메인 예외). 크기 위계를 뒤집지 않았다.
- **상태를 글자로 말하기**(`終了したシーズンです`).
- **툴팁 키보드 계약**(focus/Enter/Escape) — 감사가 「전 단계 정상」이라고 확인한 것이라 그대로 옮겼다.
- 햄버거 · 드로어 · 아코디언 · 카드 그리드를 **넣지 않았다.**

## 5. ⚠이 안의 약점 — **여기를 안 읽으면 비교가 안 된다**

**W1. 모바일 첫 화면에 야구가 없다.** 머리 176px + 題字 + 目次(약 290px) → **390×844 에서 첫 화면은
전부 안내물이고, 데이터를 보려면 한 번 스크롤해야 한다.** 현 사이트가 더 빨리 표를 보여 준다.
가로 스크롤 함정 2개를 없앤 값이라고 판단했지만, **매일 점수만 확인하러 오는 사람은 그 비용을
매번 내고 目次는 두 번 다시 필요 없다.** 이 목업에는 「접기/기억」이 없다.
(⚠273px → 176px 로 이미 한 번 줄였다: 워드마크·검색·테마를 한 줄로, 내비를 5×2 격자로, 시즌을 한 줄로.)

**W2. 欄(스팬) 머리가 가장 위험한 부품이다.** ① **이번 세션에서 실제로 한 번 무너졌다** —
`.cols` 라는 클래스 이름이 「先週の顔」의 2단 격자와 `<tr class="cols">` 에 **동시에 걸려서**
머리 행이 `display:grid` 가 되고 `<th>` 10개가 세로로 쌓였다. ② 그룹 이름
`勝敗 / 得失点 / 近況 / 見通し` 는 **내가 지은 것이지 제품의 문구가 아니다** — 도메인 리뷰어가
다르게 나눌 수 있다. ③ 앞으로 어느 그룹에도 안 맞는 열이 생기면 이 장치가 어색해진다.

**W3. 같은 페이지의 표 폭이 서로 다르다**(1,128 vs 676). 의도지만 **「구성」이 아니라 「제각각」으로
읽힐 수 있고**, `--measure-table: 52em` 은 **고른 수이지 유도한 수가 아니다.**

**W4. `ranking.html`(42,703노드)에서 안 쟀다.** 이 안은 **모든 표에** 머리 한 행과 셀별 欄 경계와
hover 괘 변화를 더한다. 감사가 「모션·그림자를 전역에 얹을 때 이 화면이 먼저 무너진다」고 했는데,
**나는 홈(1,077노드)만 만들었다. 가장 무거운 화면에서의 비용은 미측정이다.**

**W5. 「애니메이션이 거의 없다」에 대한 내 답이 「더 줄이는 것」이다.** 절마다 페이드를 없애고
의미 있는 것 하나만 남겼다. **결과적으로 움직임의 총량은 지금보다 적을 수 있다.**
「읽히는 모션이 떠도는 모션보다 낫다」는 것이 내 입장이지만 **그건 베팅이지 사실이 아니다.**
사용자가 원한 것이 「부드러움의 체감」이라면 이 안은 그 요구에 정면으로 답하지 않는다.

**W6. 일본어 조판을 한 플랫폼에서만 봤다.** Windows Chromium + Yu Gothic Medium.
macOS는 Hiragino Kaku Gothic ProN, iOS는 Hiragino Sans — 자폭·`palt` 거동이 다르다.
**38字 측정과 22px 행송은 Windows 렌더링 위에서 맞춘 값이다.**

**W7. 目次 항목은 한 줄에 들어가야 한다.** `.toc-t{white-space:nowrap}` 이라 더 긴 절 이름이 생기면
리더 점선이 0폭이 되고 행이 넘칠 수 있다. **말줄임 대비가 없다.**

**W8. 4상태(M12) 중 하나만 그렸다.** `終了したシーズンです`(시즌외)만 있고 `.stale` 변형이 CSS에만 있다.
**로딩 / 데이터없음 / 수집실패는 이 목업에 없다.**

**W9. 구단색이 9px 사각형에서 3px 괘로 작아졌다.** 정보는 옆의 글자가 갖고 있어 1.4.11에 걸리지는
않지만, **색으로 훑던 사람에게는 눈에 덜 띈다.**

**W10. `position:sticky` 를 `<th>` 에 `border-collapse:collapse` 와 함께 쓰고 있다.**
이 파일에서 브라우저 간 차이가 가장 잘 나는 조합이고, **Chromium 에서만 확인했다.**

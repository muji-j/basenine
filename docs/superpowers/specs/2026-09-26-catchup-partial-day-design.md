## 1. 문제

수집 창의 기준점은 `SELECT MAX(game_date) FROM game WHERE status = 'played'`(= `since`)다.
`targetDates()` 는 **어제**를 늘 넣고, `since` 와 어제 사이가 2일 이상이면 그 사이(`since+1` ~ 어제 전날)를 더한다(`MAX_CATCHUP_DAYS = 7` 이하일 때만).

적재기는 **끝나지 않은 경기**(`box.status === "inProgress"`)를 저장하지 않고 건너뛴다(`packages/store/tools/load-archive.ts` 의 `inProgress` 카운터 · 로그 한 줄뿐).
그러므로 D 날 23:30 JST 실행이 D 의 경기 일부만 저장하면(끝난 것만) `since = D` 가 되고, **D 의 진행 중이던 경기는 DB 에 없다.**

정상 흐름에서는 다음 날(D+1) 아침 실행이 「어제 = D」를 받아 메운다. 그런데 **D+1 의 실행이 전부 실패**하고 다음 성공이 D+2 이후면:
- D+2 아침: 어제 = D+1, `since = D` → 간격 1 → 창 = [D+1] — **D 는 빠진다.**
- D+3 아침: 어제 = D+2, 간격 2 → 창 = [D+1, D+2] — **D 는 여전히 빠진다**(창이 `since` 다음 날부터).

→ D 의 그 경기는 **자동으로는 영원히 안 받힌다**(수동 `refetch_dates` 로만). 반증자 재현:
`targetDates(new Date('2026-09-12T22:00:00Z'), {collectedThrough:'2026-09-10'})` → `["2026-09-11","2026-09-12"]`(09-10 없음).

「하루 전체 실행 실패」는 실재한 적이 있다(2026-08-31 · Actions 분 소진으로 배포가 스텝 0개로 죽음 · CLAUDE.md §6).

⚠**부분 실패 경로**(2026-09-27 · 3중 검토 3차 P2 · 2차 F3 가 독립적으로 찾음) — 위 시나리오만이 아니다.
`update.ts` 는 **날짜마다 따로** 아카이버를 띄우고 실패도 따로 센다. 한 실행 안에서 D 의 재수집(진행 중이던 경기)은 실패하고
D+1 은 성공하면 `MAX(played)` 가 **D+1 로 전진**해, 다음 실행부터는 `since` 가 D+1 이라 **D 를 다시 보지 않는다.**
그 실행은 빨갛지만 **그 뒤 자동 복구가 없다** — 「since 하나만 본다」는 이 경로를 막지 못한다(§3 안 B 의 취소선).

## 3. 안

### 안 A — 간격이 있으면 `since` 도 넣는다 (반증자의 단기안) — **기각**
간격 1 이상이면 `since` 를 창에 넣는다. D+2 아침(간격 1)에 D 를 받으려면 **간격 1 에서도** 넣어야 하는데,
간격 1 은 **휴식일 다음 날마다** 생긴다(월요일 휴식 → 화요일 아침) — 그날마다 이미 다 받은 날의 경기 전부에 조건부 요청이 나간다
(경기 6 × 4장 ≈ 24요청). 약속 1 을 깬다.

### 안 B — 최근 날들이 **덜 받혔는지**를 아카이브와 DB 로 대조한다 — **채택**
~~`since`(= 마지막으로 경기가 저장된 날) **하나만** 본다~~ → **2026-09-27 에 바꿨다: 판정 범위 `[어제 − MAX_CATCHUP_DAYS, min(since, 어제)]` 의 날마다** 본다
(3중 검토 3차 P2 · 2차 F3 · §1 끝의 부분 실패 경로). 날마다:
- 아카이브의 그 날 경기 폴더 목록(`data/archive/npb/scores/<YYYY>/<MMDD>/<slug>/` — 폴더 경로가 곧 `game_id` 모양 `YYYY/MMDD/<slug>`)
- DB 의 그 날 `game` 행(상태 무관 — `played`·`notPlayed` 둘 다)

폴더는 있는데 행이 없는 경기가 **하나라도** 있으면 그 날은 「덜 받은 날」이다 → **그 날들을 전부 창에 넣는다**(4장 D4 — `include`).
⚠~~창 계산에 `since - 1일` 을 넘긴다~~ 는 **틀린 안이었다**(콜드 리뷰 ③ · 재현): 간격이 정확히 상한(7)일 때 `since - 1일` 로는 간격이 8 이 되어
**따라잡기가 통째로 꺼진다**(창이 [어제] 하나로 무너진다) — 예시로 든 간격 1~3 에서는 안 드러나는 결함이었다.

~~왜 `since` 하나만 보는가~~ — **두 근거 다 무너졌다**(2026-09-27):
- ~~위 실패 시나리오에서 덜 받은 날은 **정확히 `since`** 다 — D+1 에 실행이 하나라도 성공했으면 그 실행이 「어제 = D」로 메웠고, 성공한 게 없으면 `MAX(played)` 가 D 에 머문다.~~
  → **틀렸다.** 「D+1 의 성공」은 **날짜별 부분 성공**일 수 있다 — 같은 실행에서 D 의 재수집은 실패하고 D+1 은 성공하면
  「어제 = D」로 메우지 못한 채 `MAX(played)` 만 D+1 로 전진한다(§1 끝). 실행 단위의 성공/실패로 나눈 것이 잘못이었다.

⚠~~대개 304~~ 가 아니다(콜드 리뷰 ⑤) — 조건부 헤더를 보낼 자리는 있지만 **npb.jp 가 검증자(ETag·Last-Modified)를 하나도 안 준다**(같은 파일 주석의 실측 · 사이드카 3,000 표본에 둘 다 0건). 그래서 **매번 200 전체 본문 + sha 비교**다 — 덜 받은 날 한 번에 ~~경기 수 × 4장(대개 24~28장)~~ **경기 수 × 4장 + 월간 일정 2장(그 달 · 다음 달)** — 대개 26~30장을 온전히 받는다

## 4. 결정 (안 B)

D1. **판정 — 판정 범위의 날마다**(2026-09-27 새로 · 3중 검토 3차 P2 · 2차 F2·F3). 순수 함수는 `scripts/date-window.ts` 에 둔다:
   - `judgeDates(now, since): string[]` — 판정 범위 `[어제 − MAX_CATCHUP_DAYS, min(since, 어제)]`(오름차순 · 최대 8일).
     ⚠**아래 끝은 `since` 가 아니라 「어제 − 상한」이다** — 부분 실패로 `since` 가 전진해도 덜 받은 날이 범위에 남는다.
     ⚠위 끝은 **어제까지** — 오늘 이후는 창이 어차피 안 더한다(오늘은 22시 이후 실행의 몫). `since` 가 아래 끝보다 이르면(간격 > 상한)
     **빈 배열**(따라잡기가 꺼지는 범위에서는 판정도 안 한다) · `since` 가 `YYYY-MM-DD` 가 아니면 빈 배열(`isYmd` · 모양과 실재).
   - `dayStatus(archived, loaded): { status: "complete" | "incomplete" | "unknown"; missing: string[] }` — 그 날의 판정.
     `missing` 은 **폴더는 있는데 행이 없는 경기 id**(정렬 · 중복 없음 — 로그가 그 id 를 말한다).
     어느 쪽이든 `null` → `unknown` — **넓히지 않는다**. ⚠못 읽음을 빈 목록으로 두면(특히 DB 쪽) 그날 경기 전부를 「덜 받음」으로 오판한다(콜드 리뷰 ①).
   - **모름의 단위**(3중 검토가 정하라고 한 것): **DB 의 경기 목록**은 범위 전체를 한 번에 읽으므로 못 읽으면 **모든 날이 모름**이고 아무것도 더하지 않는다
     (`since` 는 지켜서 빠진 날 메우기는 그대로 돈다). **아카이브**는 날마다 따로 읽으므로 **못 읽은 날만 모름으로 빼고 나머지 날은 판정한다.**
     근거: 날마다의 증거(그날 폴더 목록 대 그날 DB 행)는 **서로 독립인 읽기**다 — 못 읽은 날은 어느 쪽으로도 추정하지 않고(M11),
     읽힌 날의 「폴더는 있는데 행이 없다」는 적극적인 증거다. 한 날을 못 읽었다고 범위를 통째로 버리면 읽힌 날의 덜 받은 경기를 다시 놓친다.
   - **그날 폴더가 없으면**(`ENOENT`) 아카이브의 경기일이 아니다 — 판정하지 않는다(완결 쪽 · 요청을 늘리지 않는다).
     ⚠DB 에 그날 행이 1개 이상이면 아카이브 손실·`--archive` 설정 오류의 신호라 **경고 한 줄**로 모아 말한다(2차 F2).
   ⚠~~`sinceStatus(archived, loaded): { status; missing: number }` — `since` 날 하나만~~ 는 2026-09-27 에 `dayStatus` 로 바꿨다(날마다 · 경기 id 를 돌려준다).
D2. **경기 폴더 판별은 적재기와 한 벌이다**(M1 · 콜드 리뷰 ②). 적재기의 `gameFromPath` 판정 — `<season>/<MMDD>/<slug>/box.html.gz` 가 있고
   slug 가 `-` 로 **3조각 이상**이며 **마지막 조각이 수**인 것 — 을 **가져오는 것이 없는 잎 모듈**(`packages/store/src/game-slug.ts` · 서브패스 `@bb-app/store/game-slug`)로 옮겨
   `load-archive.ts` 와 판정 모듈(`scripts/collected-through.ts`)이 같이 쓴다(PR #18 의 `refetch-limit` 선례). 임의 이름 폴더(`.staging` 등)는 경기가 아니다.
   ⚠**구현에서 정정한 두 가지**: ⑴ 「마지막 조각이 수」의 실제 판정은 `Number.isFinite(Number(조각))` 라서 빈 조각(→0)·`1e3`·`0x1f` 도 통과한다 —
   적재 결과를 안 바꾸려고 **그대로 옮겼다**(보유 7,805개 중 해당 0건). ⑵ 구단 코드 정규화(`canonicalTeamCode`)는 domain 을 가져와야 해서

## 6. 뒤집힐 조건

- 적재기가 진행 중 경기 말고도 **폴더만 있고 행이 없는** 경우를 정상적으로 만들게 되면(예: 새 상태를 행 없이 건너뜀), 안 B 는 그날을 매번 「덜 받음」으로 본다 — 그 상태를 행으로 남기거나 판정에서 뺀다.
- ⚠**적재 실패로 행이 안 생기는 경기도 같은 범주다**(1차 P3) — `PARSE ERROR` · `READ ERROR` · 취득 시각 못 읽음 · 새 경기의 세트·본문 불일치 · 구분 판정 실패는
  경기 행 없이 건너뛰므로 그날이 「덜 받음」이 된다(그 실행은 적재기 종료 코드 1 로 이미 빨갛다).
  ⚠**격리는 이 범주가 아니다**(코드 실측) — 격리 행은 `writeGameGuarded` 트랜잭션 안에서 **경기 행과 함께** 쓰이므로(`replaceQuarantine`) 격리된 경기도 행이 생긴다.
- ⚠**영구히 덜 받힌 날의 비용**(받아들인다): 서스펜디드처럼 **다음 경기일까지** 행이 안 생기는 경기나 위의 적재 실패가 난 날은,
  원래 창(어제)에서 빠진 뒤 판정 범위에서 밀려날 때까지 **7일 동안 매 실행** 다시 받는다 — 정시 수집은 하루 3회(07:00·14:00·23:30 JST · 재시도는 실패 때만)라
  최대 **21회 × (경기 수 × 4 + 2)요청**(6경기면 26 × 21 = 546요청 ≈ 하루 78요청 · 일주일). 로그가 그 날짜와 경기 id 를 말한다(D5).
  ⚠이런 날이 잦아지면 **안 C** 로 간다.

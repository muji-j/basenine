# 시즌별 드래프트 상세 페이지 — 설계 (2026-09-04)

**요구**(사용자): 각 구단이 1지망에 누구를 넣었는지 · 경합 시 **제비뽑기에서 누가 걸렸는지** ·
낙첨 구단이 **다음 1지망을 누구로 바꿨는지** · 2지망 이후를 **어떤 순번으로** 가져갔는지 · 育成 구별.

**전제가 되는 조사 두 건**(이 문서는 그것을 반복하지 않는다):
- `docs/sources/2026-09-04-draft-source-survey.md` — 소스 판정표
- `docs/sources/2026-09-04-draft-wikipedia-markup-rules.md` — **파싱 규칙의 정본**

## 0. 범위 — 무엇을 만들고 무엇을 안 만드는가

| | |
|---|---|
| **시즌** | **2005~2026** (사용자 결정) |
| **만든다** | 1순위 입찰·경합·추첨 당락·재지명 · 2순위 이후 지명과 순번 · 育成 · 교섭권 정정·입단 거부 |
| **안 만든다** | 2004 이전 · 선수 프로필(우리 선수 페이지가 이미 있다) · 드래프트 예상·평가 |

⚠**2004 이전을 자른 이유는 데이터가 아니라 구단이다.** `大阪近鉄`(`bu`)가 2004 시즌 후 소멸했고
`楽天`(`e`)은 2005에 생겼다. 소급하려면 **「그 시즌에 존재한 구단」 이력 마스터**가 선행 조건이고,
오릭스로 접으면 **2004 드래프트에 오릭스가 두 번 나온다.**

## 1. 이 기능이 기존 구조와 다른 점 (설계의 출발점)

⚠**드래프트는 `player` 의 속성이 될 수 없다.** 이미 `player.draft` 컬럼(`2000年ドラフト5位` 원문)이
있지만 그것으로는 요구 어느 것도 답할 수 없고, **원리적으로 답할 수 없는 것**이 있다:

- **「추첨에서 진 구단」은 그 선수와 아무 기록도 안 남긴다.** 선수 단위로 표현 자체가 불가능하다.
- **지명된 선수의 상당수가 우리 `player` 표에 영영 없다** — 입단 거부(2025 佐々木麟太郎·石川ケニー가
  둘 다 MLB로 갔다) · 은퇴 · 애초에 1군 미등록.

→ **독립 이벤트 표**로 만든다. 그리고 **`player_id` 는 nullable** 이다.

⚠**두 번째 차이: 갱신 주기가 연 1회다.** 하루 1회 배치에 얹으면 1년 중 대부분을 헛돈다.

⚠**세 번째 차이: 소스가 둘이고 신뢰 등급이 다르다.** npb.jp(공식) > ja.wikipedia(커뮤니티).
경기 데이터에는 없던 축이다.

## 2. 데이터 모델

```
draft_event      한 해 × 구획
  season INTEGER, kind TEXT, held_on TEXT NULL
    kind ∈ {shihaika, ikusei, koukousei, daigaku_shakaijin, jiyuu_kakutoku, kibou_nyudanwaku}
    ⚠**6종이다**(2026-09-05 정정 · 원안은 4종이었다). `自由獲得選手`(2001)·`希望入団枠獲得選手`(2006)는
      **회차가 없는 별도 제도**라 `shihaika` 로 접으면 「1巡目 지명」과 구별할 수 없다 —
      적재가 순번을 매기는 순간 둘이 같아진다. 구현 중 실측으로 드러났다.
    ⚠2005~2007 은 分離ドラフト라 한 해에 구획이 3~4개다
  source TEXT, fetched_at TEXT, revision TEXT, license TEXT NULL
    ⚠M4: 자체 컬럼이다. 경기와 달리 **부모를 타고 답할 상대가 없다**

draft_bid        1순위 입찰 (경합·추첨) ← 이 기능의 핵심
  season, kind, round_no INTEGER      -- 1巡目 몇 회차인가 (1·2·3·4)
  team TEXT, group_key TEXT NULL      -- 같은 회차·같은 경합 그룹
  won INTEGER NULL                    -- 1=당첨 0=낙첨 NULL=단독지명(경합 없음)
  name_display TEXT, name_canonical TEXT NULL
  origin TEXT                         -- 'npb' | 'wikipedia'  ⚠행마다 남긴다
  player_id TEXT NULL

draft_pick       확정된 지명
  season, kind, round_no INTEGER, team TEXT, pick_seq INTEGER NULL
  waiver_dir TEXT NULL                -- '→' | '←' (2순위 이후)
  name_display, name_canonical, position TEXT NULL, from_org TEXT NULL
  origin TEXT, player_id TEXT NULL

draft_note       사후 사실
  season, kind, team, name_display, note_kind TEXT, detail TEXT, source, fetched_at
    note_kind ∈ {kousyouken_teisei, nyudan_kyohi, shimei_hakudatsu, fugoui}
```

### 이 모델이 지키는 것

- ⚠**「지명」과 「입단」과 「정정」이 서로 다른 표다.** 섞으면 「입단 거부한 선수」가 지명 기록에서
  사라지거나 남게 된다. 시점도 다르다 — 2025 입단 거부는 **2026년 7월**에 확정됐다.
- ⚠**`won` 이 3값이다**(1/0/NULL). **단독지명과 낙첨을 같은 값으로 쓰면 안 된다**(M11).

### ⚠`group_key` 와 「단독지명」은 두 소스에서 다르게 나온다 — 유도 규칙을 못 박는다

두 소스가 같은 사실을 **반대 방향으로** 말한다:

| 소스 | 무엇을 말하는가 | 무엇을 안 말하는가 |
|---|---|---|
| **npb.jp 주석** | **경합한 것만** (`○○と重複、抽選で…`) | **단독지명은 한 줄도 안 적는다** |
| **wikipedia 색** | **경합한 칸만 칠한다** | 색 없는 칸이 단독인지 2순위인지는 행 라벨로만 안다 |

**유도 규칙**:
```
group_key = (season, kind, round_no, 경합 대상 선수)   -- 소스 무관하게 같은 키가 나온다
  npb       : 한 문장의 「구단 집합 + 대상 선수」가 한 그룹
  wikipedia : (같은 행, 같은 background-color) 가 한 그룹  ⚠표 전체로 묶지 마라 — 색은 다른 행에서 재사용된다

won = 1     그 그룹에서 교섭권을 얻은 구단   (npb `確定` / wikipedia 굵은 칸)
won = 0     같은 그룹의 나머지               (npb `外れる` / wikipedia font-weight:normal)
won = NULL  ⚠**어느 그룹에도 속하지 않은 1순위 지명** = 단독지명
            **소스가 「단독」이라고 말해서가 아니라, 경합 그룹의 여집합으로 유도한다**
```

⚠**이 유도가 INV-4 와 짝이다** — 「구획×구단마다 확정된 1순위 지명이 정확히 1건」이 성립하지 않으면
그룹을 잘못 묶은 것이다. **단독지명을 소스에서 직접 읽으려 하지 마라 — 어느 소스도 그걸 안 적는다.**
- ⚠**이름을 두 벌 저장한다**(`display`/`canonical`). 실측 8건이 서로 다르고
  **어느 쪽도 항상 옳지 않다** — `ラマルギービンラタナヤケ`(표시) ↔ `ラタナヤケ・ラマル・ギービン`(title)은
  **어순까지 다르다**. ⚠**이름 문자열로 조인하지 마라**(M10).
- ⚠**`origin` 을 행마다 남긴다.** 2023 이후는 wikipedia 단독이고 2022 이전은 npb 대조가 있다 —
  화면이 그 차이를 말할 수 있어야 한다.

## 3. 수집

| 무엇 | 어떻게 |
|---|---|
| 진입점 | `backnumber.html` 1장 → 연도 목록(2001~2026) |
| 시즌당 | `index` 1 + `schedule` 1 + `draftlist_{team}` 12 = **14장** + wikipedia 1장 |
| 소급 전체 | 2005~2026 = **22 × 15 ≈ 330장 ≈ 17분**(L1 3초) |
| 빈도 | **연 1회** + 개최 후 **7일간 1일 1회**. ⚠**하루 1회 배치에 얹지 않는다** |
| 조건부 요청 | wikipedia 만(`Last-Modified` 19/19). ⚠**npb.jp 는 `ETag`·`Last-Modified` 가 0/9 라 못 건다** |

⚠**구단 슬러그를 하드코딩하지 마라.** 연도 톱에서 `draftlist_([a-z]+)\.html` 을 **발견**한다 —
실측: **2013 오릭스 = `bs`**(`b` 는 404) / 2019·2023 = `b`. `CLAUDE.md` §2 의 「2018 오릭스 `bs`」와
같은 함정이 여기서 더 넓게 있다. 하드코딩하면 **그 구단이 통째로 빈다.**

### 소스 조합 — 정본은 npb.jp

```
2005~2022   npb.jp draftlist 의 <p> 주석  =  경합·추첨의 정본
            wikipedia 는 대조용(불일치는 기록하고 화면에 표시)
2023~       npb.jp 가 주석을 안 쓴다  →  wikipedia 단독
            ⚠빈 자리(<p id="comment"></p>)는 그대로 남아 있다. 부활하면 다시 정본이 된다
전 범위     지명 명단·순번은 npb.jp 가 정본 · schedule.html 이 웨이버 순서
```

⚠**「2024부터」가 아니라 「2023부터」다.** 2023 은 12구단 전수에서 렌더링된 주석이 **0/12** 다
(야쿠르트에 `<!-- -->` 로 감싼 잔해만 남아 있다).

## 4. 파싱

**규칙의 정본은 `docs/sources/2026-09-04-draft-wikipedia-markup-rules.md` §4 다.**
⚠**여기에 복사하지 않는다**(M1). 구현자는 그 문서의 S0~S9 를 그대로 옮긴다.

이 설계가 추가로 못 박는 것:

- ⚠**규칙군이 4종이다**(P/Q/R/S). **연도로 분기하지 말고 구조로 판정하라** —
  R과 S를 가르는 것은 「머리행이 배너 위인가 아래인가」이고, 연도 하드코딩은 다음 해에 깨진다.
- ⚠**파싱 실패는 실패로**(M7). 규칙군 어디에도 안 맞으면 **빈 값이 아니라 예외**.
- ⚠**`---` 는 미지명이고 미수집이 아니다**(M11). 셋을 구별해 저장한다.
- ⚠**`1巡目→`(育成 1라운드)와 `1巡目1`(支配下 1순위 입찰)은 다른 것이다.**
  화살표 유무가 유일한 구별이고, 틀리면 **육성 선수가 드래프트 1위가 된다.**

## 5. 화면

**경로**: 최신 시즌 `draft.html` · 과거 `{YYYY}/draft.html` (기존 페이지 관례와 같다)

### 구성 — 1순위 서사 + 전체 표

```
① 1순위 입찰 (회차별 서사)
   1회차 ── 宗山塁 に 5球団      楽天 当選 / 西武·中日·ロッテ·ソフトバンク 落選
            佐々木麟太郎 に 2球団  ソフトバンク 当選 / 日本ハム 落選
            (단독지명 7구단은 접어 둔다)
   2회차 ── 落選한 5구단이 다시 입찰 …
   3회차 ── …

② 2순위 이후 (구단 × 라운드 표)
   웨이버 방향(→ ←)을 라운드마다 표시

③ 育成

④ 사후 사실 (있는 해만) — 교섭권 정정 · 입단 거부
```

⚠**요구하신 「누가 걸렸고 다음 1지망을 누구로 바꿨는지」가 ①에서 그대로 드러난다** —
회차가 내려갈수록 낙첨 구단이 다시 나타나는 구조 자체가 그 서사다.

### 지켜야 할 표시 규칙

- ⚠**원본 표 레이아웃을 재현하지 않는다**(L2 · CC BY-SA 계승). wikipedia 그리드(행=회차 × 열=12구단)를
  그대로 옮기지 않고 **경합 그룹 단위로 재구성**한다.
- ⚠**출처를 화면에 명기한다**(L3). wikipedia 유래 행에는 **CC BY-SA 4.0 과 기사 링크**를 붙인다(BY).
- ⚠**빈 상태를 구별한다**(M12):
  - 2023~ 경합 = **「NPB가 공표하지 않는다」**(우리가 못 얻은 게 아니다)
  - 2005~2007 일부 = **「확인하지 않았다」**
  - ⚠**「데이터가 없습니다」로 뭉뚱그리지 마라.**
- **선수 이름은 우리 선수 페이지가 있을 때만 링크**하고, 없으면 **이름만 남긴다**.
  ⚠**행을 지우지 마라** — 그 지명은 실제로 있었다(통산 대전 표에서 쓴 규칙과 같다).
- ⚠**`origin` 이 wikipedia 뿐인 행은 그 사실이 보여야 한다** — 대조 상대가 없는 값이다.

## 6. 검증

**시험으로 고정한다. 위반은 빈 값이 아니라 실패**(M7).

| 종류 | 내용 |
|---|---|
| **INV-1~7** | 규칙 문서 §5. 101그룹·44쌍·264슬롯·397행에서 전수 성립을 확인했다 |
| **X-3** | 구단별 지명 명단이 npb·wikipedia 간 **인원·순서까지** 같다(72명단 실측 불일치 0) |
| **픽스처** | `packages/parser/test/fixtures/` 에 **규칙군 4종의 대표 연도**를 넣는다(2006·2008·2019·2025) + **예외 3건**(2007 rowspan · 2006 `不合意` · 2005 정정) |
| **경계** | `---` 미지명 · 단독지명(`won` NULL) · 育成 `1巡目→` · 전각 숫자 · 이체자 |

⚠⚠**INV-1~6 은 내부 정합성일 뿐이다.** 색을 통째로 잘못 읽어도 같이 통과한다.
**색의 의미를 지탱하는 것은 npb 대조(X-1) 하나뿐이고, 그것은 91그룹 중 20개(22%)에만 있다.**

→ **INV-7 이 2023 이후 남은 유일한 독립 검사다**: `schedule.html` 의 웨이버 순서와
wikipedia 열 머리를 **매년 대조**한다. 이게 없으면 색 해석이 흔들려도 알 방법이 없다.

## 7. 단계

| 단계 | 완료 판정 |
|---|---|
| **1. 스키마 + 파서(npb.jp)** | 2005~2026 지명 명단이 들어가고 **INV-4·INV-5** 가 통과. ⚠~~X-3 통과~~ 는 **여기서 불가능하다** — X-3 은 npb↔wikipedia 대조라 **3단계 없이는 못 돌린다**(2026-09-04 계획 작성 중 정정) |
| **2. 경합 파서(npb 주석)** | 2005~2022 경합이 들어가고 `X-1`(40문장) 재현 |
| **3. wikipedia 파서** | 규칙군 4종 픽스처 통과 · **INV-1~7 전수 성립** · 2005~2022 에서 npb 와 대조해 불일치 0 |
| **4. 2023~ 적용** | wikipedia 단독으로 2023·2024·2025 가 들어가고 INV 전수 성립 |
| **5. 화면** | 4상태 구별 · 출처 명기 · 링크 없는 이름 처리 · 페이지 무게 측정치 보고 |

⚠**3단계가 게이트다.** 거기서 불일치가 나면 4단계로 넘어가지 않는다 —
2023 이후는 **정답지가 없어서 틀려도 조용하다.**

## 8. 뒤집힐 조건 · 미확인

- **2026-10-22 개최 후에 npb.jp 가 주석을 다시 쓰면** 2026부터 정본이 npb 로 돌아온다.
  ⚠**빈 자리가 템플릿에 남아 있으므로 가능성이 있다.** 개최 직후 재확인한다.
- **wikipedia 스타일이 바뀌면** INV 가 붉어진다. ⚠**그게 이 설계의 유일한 조기 경보다** —
  위키는 사람이 쓰는 문서이고 바뀌어도 우리에게 알려주지 않는다.
- ⚠**미확인**: 91그룹 중 **71개(78%)에 대조 상대가 없다** · 2022 는 1구단만 봤다 ·
  2024·2025 는 4구단 표본 · **`action=raw` 위키텍스트나 구판 HTML은 구조가 다르다**(이 규칙은
  Parsoid 렌더링 한정) · 1965~2004 는 안 봤다(**1990 이 이미 다르다**).
- **CC BY-SA 계승(SA)** — 사실만 뽑아 재구성하면 1층으로 벗어날 여지가 있으나 **법률 판단은 우리 위치가
  아니다**(§2-5 태도). **S1(지인 한정)에서는 진행하되 S2(공개) 전에 재평가**한다.

# 운용 — 일일 갱신과 감시

## 매일 하는 일

```bash
node scripts/update.ts --contact <닿는-연락처>
```

1. **어제** 경기 페이지 아카이브
2. DB 적재 (멱등)
3. 새로 등장한 선수 프로필 아카이브·적재
4. 신선도 보고

소요 약 2분(요청 25건 × 3초 + 적재). 계정·클라우드 없이 로컬에서 돈다.

### ⚠왜 「오늘」이 아니라 「어제」인가

진행 중인 경기를 받으면 **미확정 성적이 `final`로 저장된다**(M9 위반).
그런데 npb.jp 경기 페이지에는 **그 경기 자신의 종료 여부를 가리키는 안정된 표시가 없다** —
헤더의 「試合終了」는 그날 전 경기 목록이라 구별되지 않는다.

감지기를 추측으로 만드는 대신 **구조적으로 안전한 시각**을 쓴다.
자정 이후에 돌리면 어제 경기는 확실히 끝나 있다.

만약 진행 중에 받아버려도 **수집은 멱등이고 내용 해시로 판정하므로** 다음 실행에서
확정판으로 갱신된다. 낡은 값이 몇 시간 보일 뿐 영구 오염은 아니다.

## 감시

```bash
node scripts/freshness.ts data/bb.sqlite 2
```

낡았으면 **종료 코드 1**. 크론이 그대로 실패로 잡는다.

### ⚠~~주 감시는 제품 화면이다~~ — **그 문장이 거짓이었다** (2026-09-09 정정)

**주 감시는 `heartbeat.yml` 이다.** 화면의 신선도 띠는 **감시 장치가 아니다.**

⚠**왜 거짓인가**: `packages/web/src/layout.ts:160` 이 `lagDays` 를 **`builtOn`**(빌드 시각) 기준으로
계산하고 이 사이트는 **정적 생성물**이다 — **파이프라인이 멈추면 페이지가 다시 안 구워지므로
그 값이 얼어붙는다.** 마지막 빌드 당시가 신선했으면 **영원히 초록**이다.
**정지를 그 배지로는 원리적으로 탐지할 수 없다.**
⚠**CLAUDE.md §6 이 2026-08-30 사고에서 같은 함정을 이미 적어 뒀다**
(「초록 띠는 그 화면이 만들어질 당시엔 신선했다는 뜻」) — **읽고도 이 문단을 그대로 뒀다.**
⚠**띠가 쓸모없다는 말이 아니다** — **「지금 보고 있는 화면이 며칠짜리인가」**는 여전히 말한다.
**「파이프라인이 살아 있는가」를 못 말할 뿐이다. 둘을 섞지 마라.**
⚠**임계도 둘이다**: 화면 배지는 `STALE_AFTER_DAYS = 3`(`layout.ts:125`),
`scripts/freshness.ts` 는 인자 기본 **2일**. **다른 장치의 수를 섞어 적지 마라.**

원래 조사가 무료 외부 감시 3종을 **전부 시한부**라며 탈락시킨 표는 그대로 유효하다:

| 수단 | 만료 |
|---|---|
| Cloudflare 헬스체크 | Free 플랜에 **없다** (Pro $20/월) |
| GitHub Actions 스케줄 | **60일 무활동 시 자동 비활성화** |
| healthchecks.io | **1년 무로그인 시 계정 삭제** (ping은 활동으로 안 침) |

⚠**그런데 그 표의 2행을 다시 채택했다**(`heartbeat.yml`). **판단이 바뀐 이유를 적어 둔다:**
그때 물음은 「제품이 낡은 것을 감시할 수 있는가」였고 답이 「제품 화면이 한다」였다 —
**그 답이 거짓이었다는 것이 이번 발견이다. 시한부라도 없는 것보다 낫다.**
⚠**대가**: `daily.yml` 이 멈추면 저장소 활동도 멈추고 **60일 뒤 둘이 함께 비활성화된다.**
`heartbeat.yml` 은 아무것도 커밋하지 않으므로 **활동을 만드는 것은 `daily.yml` 의 `ops/` 커밋뿐**이고,
**그것이 멈추는 것이 바로 이 감시기가 알리려는 상황이다** — **자기가 감시하는 것에 자기 수명이 걸려 있다.**

**`heartbeat.yml` 이 하는 일과 못 하는 일**

- 묻는 것: **「최근 24시간 안에 `collect` 잡이 한 번이라도 성공했는가」**. 아니면 실패 → **메일**.
- **탐지 지연**: 창 24h + 주기 6h = **30시간**이 하한이고, **스케줄 지연(실측 81~385분)을 얹으면
  약 36시간**, 한 회 탈락하면 **약 42시간**이다. ⚠**「최악 30시간」이라고 쓰지 마라 — 그건 하한이다.**
- **못 잡는 것**: 부분 장애(슬롯 하나만 죽는 것) · `deep` 의 영구 정지 · 予告先発 실취득 실패 ·
  지연 · 탈락(탐지만 된다) · **자기 자신의 정지**.
- ⚠**오프시즌에는 소음이 된다**(미관측 · 아래 「감시기를 사람이 확인한다」 참조).

### ⚠감시기를 사람이 확인한다 (자동으로는 못 한다)

1. **살아 있는가** — 가끔 `gh run list --workflow heartbeat.yml` 로 본다.
   **침묵이 「정상」과 「감시기 사망」 양쪽을 뜻하므로** 이건 자동화할 수 없다.
2. **메일이 실제로 오는가** — 이 장치 전체가 「워크플로가 실패하면 GitHub 이 메일을 보낸다」에
   걸려 있고 **그건 계정 알림 설정에 달렸다.** `workflow_dispatch` 로 한 번 일부러 실패시켜 확인한다.
   ⚠**확인 전에는 「탐지가 생겼다」고 쓰지 마라.**
3. ⚠**11월 초 전에 정해야 할 것** — `scripts/freshness.ts` 에 **시즌 종료 예외가 없다**
   (`staleDays` 기본 2). 일본시리즈가 끝나면 `MAX(game_date)` 가 낡아 `update.ts` 가 exit 1 →
   **`collect` 잡이 매일 실패** → 하트비트가 6시간마다 메일 → **오프시즌 약 4개월에 480통.**
   **그러면 3월에 진짜 정지가 왔을 때 그 메일을 아무도 안 본다.**
   ⚠**「관측된 적 없다」이지 「안 난다」가 아니다** — `ops/collection-log.jsonl` 은 전부 시즌 중 기록이다.
   올스타 휴식(연 1회 3~5일)도 같은 모양이다.

## 쓰기 예산

D1 무료는 **하루 10만 행**에서 **차단**된다(과금이 아니다).

| 작업 | 행 수 | 한도 대비 |
|---|---|---|
| 2026 시즌 전량 적재 | 70,821 | 70.8% |
| 일일 증분(6경기) | 약 700 | 0.7% |

한 시즌은 하루에 들어가고 **두 시즌은 안 들어간다.**
`--from` / `--to` / `--max-writes`로 나눠 넣는다 — 상한에 도달하면 **넘기기 전에 멈추고 재개 날짜를 알린다.**

## 알아둘 것

### 경기 페이지는 경기와 무관하게 매일 바뀐다
8/14 페이지에 8/15 경기 링크가 들어간다(헤더 내비). 그래서 하루 지나 다시 받으면 「신규」로 판정된다.
**파싱 결과는 그대로**이고, 「어제 본 숫자와 다른데?」에 답할 때는 **DB의 `revision`**을 보면 된다.

### 격리는 버그가 아니라 판단 요청이다
`quarantine` 표에 뭔가 쌓이면 원문을 보고 규칙을 늘릴지 정한다.
2026 시즌 전량에서 현재 **0건**이다.

## 화면 생성

```
npm run build:web            # data/bb.sqlite → dist/  (2026 현행 + 2025·2024 는 /{연도}/)
BB_CONTACT="..." npm run build:web
npm run preview              # http://127.0.0.1:4173
```

⚠**`dist/index.html`을 파일로 직접 열면 검색이 안 된다.** 선수 색인을 `fetch`로 받는데
`file://`에서는 브라우저가 막는다. 볼 때는 `npm run preview`를 쓴다.

| 항목 | 실측 (2026 시즌, 630경기 시점) |
|---|---|
| 출력 | 700파일 · 25.8MB · 선수 695명 |
| 집계 시간 | 1.8초 |
| 검색 색인 | `players.json` 48KB |
| D1 읽기 | 배포 때 1회. 요청마다 계산하지 않는다 |

**서버가 없다.** 데이터는 하루 1회만 바뀌므로 정적 파일로 낸다.
낡은 데이터로 생성하면 **종료 코드 1**과 함께 화면 상단에 경고 띠가 나온다.

⚠**`BB_CONTACT`를 설정하지 않으면 삭제·정정 요청 창구가 화면에 나오지 않는다**(L4).
가짜 주소를 넣지 않도록 비워 두면 화면이 「미설정」이라고 말하고, 빌드가 경고한다.
**공개 전 필수**다.

## 보관소

아카이브와 DB는 **비공개 리포의 릴리스 자산**(`data-store` 태그)에 둔다.
R2가 아닌 이유와 실측은 `docs/operations/deploy.md`에 있다 — 요약하면
Actions 캐시는 7일이면 지워지고, R2는 시크릿이 늘고, 릴리스는 추가 계정·시크릿이 0이다.

```bash
node scripts/archive-guard.ts count data/archive              # 지금 몇 건인가
node scripts/archive-guard.ts check data/archive ops/archive-manifest.json
```

⚠**줄어들면 멈춘다.** 복원이 조용히 실패한 채 덮어쓰면 소급 불가능한 자산이
한 번에 사라지고 로그에는 「정상 종료」가 남는다. 워크플로가 복원 직후와 수집 직후
**두 번** 검사하고, 통과하지 못하면 보관소에 올리지 않는다.

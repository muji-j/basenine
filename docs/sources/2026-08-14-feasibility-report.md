# NPB 데이터 서비스(Lunomel) 1단계 — 소스·스택 통합 판정 보고서

**작성 기준일 2026-08-14 / 입력: 소스 조사 6개 각도 + 스택 설계 2개 트랙**

**한 줄 결론:** 기본지표·순위·세이버(WAR 제외)는 npb.jp 1차 수집 + 자체 산출로 성립하고, 스택은 무료 Cloudflare 트랙으로 충분하다. **막히는 것은 인프라가 아니라 (a) 라이브 소스의 부재와 (b) npb.jp 푸터의 「二次利用 금지」 문구 두 가지이며, 둘 다 돈이나 스택 교체로 풀리지 않는다.**

## 3. 자동취득 불가 항목 — 왜 불가능한가 + 수동 비용

⚠ **아래 수동 비용은 전부 산술 추정이며 실측이 아니다.** 계산 근거를 함께 적는다.

### 3-1. 라이브 (현재 투수/타자/카운트/주자) — **수동으로도 불가**

- **왜:** ① npb.jp가 제공 자체를 안 함(6개 각도 중 3개에서 HTML 소스 실측) ② 유일한 무료 보유처 Yahoo 一球速報은 LINEヤフー 이용규약 제15조·スポナビ 免責이 명시 금지 ③ NPB「写真・動画等の撮影及び配信・送信規程」(2025-09-01 시행) 제2조(6)이 「試合データ」를 투구별 코스·구종·구속 + 타석별 결과로 정의하고 제4조1항(2)가 **리얼타임 배신을 정면 금지**.
- **수동 비용(추정):** 정규시즌 858경기 ÷ 1일 최대 6경기 = **143 경기일**. 경기당 3~4시간(박스스코어 실측 「3時間12分」) × 동시 6경기 = **약 24 인시/일** → **시즌 3,432 인시**. 일본 최저시급 수준 ¥1,100 가정 시 **약 ¥3,780,000/시즌**. → 예산(월 상한 ¥1,000 추정)과 3자리 자릿수 차이. **수동 대체는 성립하지 않음.**
- **대응:** v1에서 기능 제외. 또는 데이터스타디움/DSG 라이선스 문의(비용 미확인).

### 3-2. WAR — **수동 노동으로 메울 수 없는 유형**

- **왜:** 필요 성분 3개 중 (a) 수비 런밸류는 타구 낙구좌표·존·타구속도가 필요한데 공개 원시기록에 존재하지 않음, (b) 주루 런(UBR)은 주자 진루 상황 로그가 필요, (c) 포지션 보정·대체수준 상수는 리그 전체 재계산 필요. **입력 데이터가 없으므로 사람이 계산해도 나오지 않는다.**
- **수동 비용:** 산정 불가(입력 부재).
- **대응 3안:** ① 표시하지 않음 ② npbstats.com 값을 **출처 명기 후 참조 표시**(단 갱신주기·최신시즌 커버리지 미검증, HTTPS 미지원) ③ npbbasement 값(취득 경로 자체가 미확인).

### 3-3. 구종·구속·코스 — **수동으로도 불가**

- **왜:** Yahoo PC web raw HTML에서 球種/ストレート/スライダー/フォーク/km/h 인덱스 전부 -1 실측. LINEヤフー 2026-02-20 릴리스가 「ストレート最高球速および平均球速」「球種別投球数・割合」을 **iOS/Android 앱에** 추가했다고 명시 → 앱 전용 기능.
- **수동 비용(추정):** 1시즌 약 25만 구. 1구당 5초 입력 가정 시 **347 인시/시즌**, 실황을 보며 구종을 판정해야 하므로 실제로는 이보다 크고 정확도가 담보되지 않음. **불가.**

### 3-4. 2024년 이전 타석 단위 로그 — **수동으로도 불가(정보 자체가 없음)**

- **왜:** NPB 공식 playbyplay는 **2025년 이후만** 존재(2025-08-14 = HTTP 200 / 2024-08-14 동일형식 = HTTP 404 실측). 2024년 이전 아카이브 `/bis/{year}/games/`는 이닝별 득점·선수별 打数/安打/打点 수준의 박스스코어뿐이며 **打席ごとの結果·アウトカウント·B-Sカウント·走者 상세가 전부 없음**(2015년 경기 실측).
- **수동 비용:** 복원 불가. 원본 정보가 존재하지 않으므로 인력 투입으로 만들어낼 수 없음.
- **유일한 대안:** nf3의 사전집계 결과(2005/2006~2026)를 **운영자 허락 하에** 사용.

### 3-5. 선수별 ROE(失策出塁) — 항 생략으로 대응

- **왜:** npb.jp를 포함해 확인한 어떤 공개 소스에도 선수별 ROE가 없음.
- **대응:** 업계 관행대로 wOBA 산식에서 `0.966×失策出塁` 항을 생략. **1.02 공표치와 소수점 3자리 수준의 괴리가 발생함을 UI 각주로 명시.** 수동 비용 0.

### 3-6. 선수 ID 크로스 매핑 — **수동 필요, 비용은 감당 가능**

- **왜:** 3개 체계가 상이. NPB 공식 8자리(`51655153`) / Yahoo·baseballdata 공용 7자리(`2000051`) / nf3 **등번호 기반 URL**(`Central/D/f/1_stat.htm`). nf3는 등번호가 키라 이적·등번호 변경 시 연도 간 동일 선수 추적이 URL만으로 불가.
- **수동 비용(추정):** 1군 등록 규모 약 840~900명. 선수당 45초 검증 가정 → **초기 구축 약 11 인시(1.5일)**. 연간 유지는 신인·이적 약 150명 → **약 2 인시/년**. **감당 가능하며, 이것이 v1 착수 전 반드시 만들어야 할 산출물.**

### 3-7. 12구단 URL 코드 매핑 — **수동 1회성, 1시간 미만**

- **왜:** `idb1_t.html`(t=阪神)만 실측 검증. 나머지 11구단 코드는 미검증.
- **수동 비용:** 12페이지 확인 = **약 0.5~1 인시(1회성)**. 착수 전 즉시 해소 가능.

### 3-8. 파크팩터 / wOBA 시즌계수 — **자동 산출 가능(불가 항목 아님)**

- 파크팩터: NPB 미공표이나 `/scores/{year}/index.html`의 경기별 스코어+구장명으로 자체 산출 가능(제3자 구현 사례 확인됨). **1년치는 편차가 커 3~5년 합산 필요.** nf3 기성 PF값은 크로스체크용으로만.
- wOBA 계수: 1.02 공개 계수 1세트(0.692/0.73/0.966/0.865/1.334/1.725/2.065)만 존재하고 시즌별 재추정치는 비공개. **고정계수를 쓰되 wOBA 절대치가 아니라 리그평균 대비 상대치(wRAA/wRC+)로 제시하는 설계가 안전.**

## 5. GAS 판정 — 「GAS가 가장 쌀 것」에 대한 답

### 결론: **가격은 맞다. 그러나 전제가 틀렸다 — GAS의 가격 우위는 0이다.**

GAS는 ¥0이 맞다. 그런데 **경쟁 무료 스택도 ¥0이다.** Cloudflare Workers + D1(무료: 5GB·5M행 읽기/일·100K행 쓰기/일)은 10시즌 타석 로그를 여유롭게 담고, 동시접속·실행시간·라이브 지연 천장을 통과하면서 같은 ¥0이다. 도메인 비용도 양쪽 공통이다.

**즉 비용은 두 안을 구분하지 못한다. 구분하는 것은 능력과 실패 모드뿐이다.**

추가로: GAS의 한도는 초과 시 **과금이 아니라 정지**다. 장애 중에 돈으로 살 수 있는 여유분이 존재하지 않는다.

### 감당 가능한 범위 (여기서는 GAS/Sheets가 실제로 최적)

| 용도 | 근거 |
|---|---|
| **수동 입력 콘솔** | 자동 취득 불가 항목(3장)의 입력 경로. 사람이 표를 직접 고치는 UI를 공짜로 얻는다. 대체재보다 낫다 |
| **소규모 집계 테이블의 백업 미러** | 리그 순위·시즌 성적 라인(수천 행 규모)의 사람이 읽을 수 있는 사본 |
| **소스 조사 단계의 스크래핑 프로토타입** | robots/약관/갱신주기를 재는 일회용 도구 |

### 불가능한 범위

| 용도 | 왜 불가능한가(수치) |
|---|---|
| **타석(PA) 단위 저장소** | 요구 「수백만 행」 = 30컬럼 기준 9,000만 셀 = **상한 1,000만의 9배**. 5시즌만으로도 978만 셀(98%). ⚠ 2,000만 셀은 GA가 아니라 **조직 등록 폼 기반 opt-in 베타**이므로 개인 gmail 계정은 1,000만이 확정 상한 |
| **세이버·스플릿 집계 엔진** | 6분/실행 상한(어떤 요금제에서도 불변) + 트리거 90분/일. **투수x타자 상대전적은 본질적으로 조인인데 Sheets에 쿼리 엔진이 없다** — `getValues()` 후 JS 수동 조인이 6분 상한에 걸림 |
| **공개 서빙 계층** | 30 동시실행이 천장이며 execute-as-me 익명 배포에서는 **전 방문자가 소유자 1버킷 공유**. 화제의 경기에 동시 100~300명 = **「지인이 지인에게 공유하는 순간」과 정확히 겹침** → 1단계 성공이 곧 장애 조건 |
| **라이브 경로** | 트리거 최소 간격 1분 + 발화 시각 랜덤화. NPB 타석 1회 소요 3.5~4분 대비 75~150초 지연 = 「현재 타자」가 이미 끝난 타석 |

### ⚠ 「일단 GAS로 띄우고 나중에 옮긴다」에 대한 경고

형제 프로젝트가 `.gs` 31,254행 + 클라 91,877행을 쌓은 뒤 탈출하며 치른 비용이 실증 반례다. 이 전략이 성립하려면 **① 지표 계산식을 GAS API에 의존하지 않는 순수 함수로 격리 ② Sheets 접근을 저장소 인터페이스 1겹 뒤로** — 이 2개가 코드로 강제되어야 한다. 강제되지 않으면 **1단계 GAS 채택은 2단계의 전면 재작성을 예약하는 것**이다.

또한 모듈 전역 락 깊이(`SCRIPT_LOCK_DEPTH_`) 패턴은 **GAS에서는 안전했다**(실행마다 글로벌 재생성). 결함이 되는 것은 Node로 옮길 때다. **GAS 채택은 이 부채를 없애는 게 아니라 연기한다.**

- 크롤 예산: 약 1,820 req/시즌 × 22시즌 ≈ 4만 req / 3.4GB / 3초 딜레이 기준 **약 33시간(1회성)**
- ⚠ **2028-01-24 폐쇄 예고가 사실이라면 아카이브 일괄 선확보가 전제.** 항구 의존처로 삼는 설계는 불가
- ⚠ nf3 자체가 Yahoo·日刊·スポニチ·NPB의 2차 가공물이므로 **nf3의 허락만으로 원출처 권리가 해소되지 않음**

**옵션 3 — 라이브를 반드시 넣고 싶다면**

- 데이터스타디움 또는 Data Sports Group에 라이선스 문의(DSG는 무료 트라이얼 CTA 존재 → **트라이얼로 NPB 실제 입도부터 검증**)
- ⚠ 4개 벤더 전건 가격 비공개. 추정 예산 상한 ¥1,000/월을 넘길 개연성이 높음
- ⚠ **NPB 규정 제4조1항(2)가 리얼타임 試合データ 배신을 금지**하고 NPB엔터프라이즈가 DMP 라이선스 사업을 하고 있으므로, 무허락 라이브는 **경고·정지요청의 1순위 타깃**

**옵션 4 — GAS는 보조 역할로만**

- 수동 입력 콘솔 + 소규모 백업 미러로 한정. 저장소·집계·서빙·라이브에는 투입하지 않음

**권장 조합: 게이트 G1~G4 → 옵션 1로 착수 → G2 결과에 따라 옵션 2로 확장 → 라이브는 v2 이후 옵션 3 재평가 → GAS는 옵션 4 범위로만.**

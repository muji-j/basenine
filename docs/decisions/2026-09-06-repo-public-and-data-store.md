# 저장소 공개와 데이터 보관소 이전 (2026-09-06)

**결론: 공개해도 된다 — 단 릴리스 자산 1.34 GiB 를 먼저 옮긴 뒤에.**

사용자 판단(2026-09-06): 「깃허브가 프라이빗이라 배포 한도가 걸리는 거니까, **DB 정보 자체가
그대로 이용되는 문제만 없으면 퍼블릭으로 돌려서 배포를 마음껏 하는 게 낫다**」 — **그 조건이 핵심이고,
지금은 성립하지 않는다.** 아래는 무엇이 막고 있으며 어떻게 푸는가다.

> ⚠⚠**이 문서는 「사이트 공개」가 아니다.** 그건 `2026-08-16-public-release-assessment.md` 가 다루고
> 게이트가 **일본 변호사 확인·개인정보처리방침·운영 주체 표시**다. **저장소를 공개해도 사이트는
> 그대로 Cloudflare Access 뒤에 있다.** 두 결정을 섞지 마라 — 섞으면 한쪽 게이트로 다른 쪽을
> 통과시키게 된다.

## 1. 왜 지금 이 이야기가 나왔나 — CI 한도가 실제로 물린다

비공개 저장소는 Actions 무료분이 **월 2,000분**이고, 공개 저장소는 **표준 러너 무료·무제한**이다.

| 실측(벽시계 · 2026-09-06) | 값 |
|---|---|
| 8월 전체 | 실행 196건 · **1,952분** — 한도 직전 |
| 9월 1~6일(5.2일) | 실행 33건 · **367분** → 하루 약 **70분** → 월 **약 2,100분** |
| 실제 사고 | **2026-08-31 소진**으로 배포가 스텝 0개로 죽었다(`deploy.md` §7-C) |

⚠**이 수치는 과금 카운터가 아니다.** `users/…/settings/billing/actions` 는 `user` 스코프가 없어 못 읽었고
(스코프를 임의로 넓히지 않았다), 실행별 `timing` 의 `billable.total_ms` 는 **이 저장소에서 0을 낸다**
(소진 사고 때도 0이었다). **위는 `run_duration_ms` 합계이고 과금은 잡별 올림이라 실제는 조금 더 크다.**

### ⚠P1 이 왜 블로커인가 — 수집과 재배포는 다른 층이다

사용자 논거 중 「어차피 메일 기입해서 정보 가져온다」는 **L1(예의 있는 수집)**에 대한 말이고,
릴리스 자산을 공개하는 것은 **§2-5 2층(편집물로서의 DB)·3층(데드카피)**의 문제다. **다른 층이다.**
`L6` 이 「원시 아카이브는 내부 보관, 외부 노출은 파생값 위주」라고 정한 그 경계이고,
**`daily.yml` 에 리포가 공개면 `exit 1` 하는 게이트가 이미 있다.**

⚠**되돌릴 수 없다.** 공개로 돌린 뒤 다시 비공개로 바꿔도 **이미 받아 간 사본은 못 되돌린다.**

## 3. 두 트랙 (§0 제약2)

### 무료 최선안 — **별도 비공개 저장소의 릴리스로 옮긴다**

- 코드 저장소는 공개, **데이터는 비공개 저장소의 릴리스**에 둔다.
- 공개 저장소의 워크플로가 **PAT**(그 비공개 저장소 읽기·쓰기)로 받아 간다.
- **월 0엔.** 새 벤더 없음. 새 결제 없음.
- `gh release` 명령을 그대로 쓰고 **`--repo <데이터저장소>` 만 붙이면 된다** — 이전 규모가 가장 작다.
- ⚠**대가**: 시크릿에 PAT 이 하나 는다. 만료·회전 관리가 생긴다.
- ⚠**GitHub 릴리스 자산 총량에 명시적 상한이 문서화돼 있지 않다** — 지금 1.34 GiB 는 문제없지만
  **재 본 적 없다.**

### 유료 최선안 — **Cloudflare R2**

- Cloudflare 는 **이미 배선돼 있다**(`CLOUDFLARE_API_TOKEN`·`CLOUDFLARE_ACCOUNT_ID` 시크릿 ·
  `wrangler` 4.123.0 고정). 새 벤더가 아니다.
- **월 추정액: 0엔**(무료 구간 안이라면). 저장 10GB·읽기 무료 구간에 1.34 GiB 는 들어간다.
  ⚠**단 R2 는 계정에 결제 정보 등록을 요구할 수 있다 — 제가 확인하지 못했다.**
- ⚠**`wrangler r2 object put` 은 단일 업로드 크기 상한이 있어 330MB tar 가 걸릴 수 있다.**
  그러면 S3 호환 엔드포인트에 멀티파트(`aws s3 cp`)를 써야 하고 **작업이 커진다.**
- ⚠**새 권한의 토큰을 사용자가 발급해 시크릿에 넣어야 한다** — 내가 못 하는 일이다.

### 비교

| | 무료안(비공개 저장소) | 유료안(R2) |
|---|---|---|
| 월 비용 | **0엔** | **0엔**(무료 구간) · 결제 정보 등록 필요 여부 미확인 |
| 사용자가 해야 할 일 | PAT 발급 1회 + 저장소 1개 생성 | R2 활성화 + 토큰 발급 |
| 이전 작업 규모 | **작다** — `gh release` **16곳**에 `--repo` 추가 | 크다 — 업/다운로드 로직 교체 + 멀티파트 |
| 새로 생기는 실패 모드 | PAT 만료 | R2 API·멀티파트·요금 |
| L6 경계의 또렷함 | **가장 또렷** — 원시 아카이브가 물리적으로 다른 저장소 | 또렷 |

### 참고 — 이전을 안 하는 길

**GitHub Pro 로 한도를 올린다**(무료 2,000 → 상향). **월 약 600엔**으로 §0 의 **1,000엔 상한 안**이다.
⚠**정확한 분수와 가격을 제가 확인하지 않았다.** 이전 작업이 0이고 위험도 0이지만 **근본 해결은 아니다** —
쓰는 양이 늘면 다시 걸린다.

## 4. 권고

**무료안(별도 비공개 저장소)으로 간다.**

이유 셋:
1. **사용자가 해야 할 일이 가장 적고**(PAT 하나), 내가 못 하는 단계가 하나뿐이다.
2. **이전 규모가 가장 작다** — `gh release` 에 `--repo` 를 붙이는 것이라 16곳이 기계적이다.
   R2 는 업로드 경로를 다시 쓰는 일이고 **330MB 멀티파트라는 미지수**가 붙는다.
3. **L6 경계가 물리적으로 또렷해진다** — 「원시 아카이브는 내부 보관」이 저장소 분리로 강제된다.

⚠**R2 가 더 나은 경우도 있다**: 자산이 더 커지거나(백필로 2018 이전을 넣으면 330MB 가 몇 배가 된다)
GitHub 릴리스 총량이 걸리기 시작하면 그때는 R2 다. **그때 이 문서를 다시 연다.**

## 5. 공개 전 체크리스트 — **전부 만족해야 스위치를 넘긴다**

| # | 무엇 | 누가 |
|---|---|---|
| **C1** | 데이터 저장소를 옮기고 **원 저장소 릴리스에서 자산을 지운다** | 나 + 사용자(PAT) |
| **C2** | ⚠**지웠는지 실측한다** — `gh release view` 로 자산 0건 확인 | 나 |
| **C3** | 개인 메일 3곳을 대체(브랜드 주소 또는 환경변수 참조) | 나 · **사용자 결정** |
| **C4** | 최근 워크플로 로그를 훑어 **마스킹 안 된 값**이 없는지 확인 | 나 |
| **C5** | `daily.yml` 의 **L6 게이트를 재조준** — 「리포가 공개면 죽는다」에서 「**원시 아카이브가 공개 저장소에 있으면 죽는다**」로 | 나 |
| **C6** | 공개 전환 자체 | **사용자** |

⚠**C5 를 빼먹고 C1 만 하면 게이트가 공개 전환을 막는다**(설계대로다). ⚠**C5 만 하고 C1 을 안 하면
게이트가 사라진 채 원본이 나간다** — **순서가 안전을 만든다. C1 → C2 → C5 다.**

## 6. 뒤집힐 조건

- **GitHub 릴리스 총량 제한에 걸린다** → R2 로 간다.
- **자산이 몇 배로 커진다**(2018 이전 백필) → R2 로 간다.
- **PAT 관리가 사고를 낸다**(만료로 배치가 죽는 일이 반복) → R2 또는 Pro 로 간다.
- **사이트를 공개하기로 한다** → 이 문서가 아니라 `2026-08-16-public-release-assessment.md` 의
  게이트를 본다. **이 결정은 그것을 앞당기지 않는다.**

## 설계안

### stack

【採用】単一VPS・全部入り・JPY建て固定上限型

- ホスティング: **KAGOYA CLOUD VPS「2GBプラン」**(2コア / 2GB RAM / 200GB NVMe SSD / 京都DC / 日額28円・月額上限770円税込・初期費用0円)
  https://www.kagoya.jp/cloud/vps/price/
- OS/実行基盤: Ubuntu LTS + **Docker Compose**(4コンテナ: caddy / api / postgres / batch)
- リバースプロキシ: **Caddy 2**(Cloudflare Origin Certificate + Full(strict)。ACME不要)
- ランタイム/サーバ: **Node.js LTS + Fastify**(兄弟プロジェクト PPS_NEW_PORTAL と同一。運用知識を実利で再利用)
- DB: **PostgreSQL 17**(self-hosted, 同一VPS内)。shared_buffers 512MB / effective_cache_size 1200MB / work_mem 32MB / max_parallel_workers_per_gather 1 / swap 4GB
- スキーマ層: **Drizzle ORM**(マイグレーションをgit管理・型共有)。ただし**集計クエリはDrizzleを使わない** — セイバーメトリクス/スプリット/対戦成績は versioned `.sql` の materialized view として手書きSQLで持ち、Drizzleは read model の型付けだけ担当する(ORMで集計を書くのがこの種のプロジェクト最大の失敗パターン)
- フロント: **React 19 + Vite**。ただし**SPA単体では出さない** — Fastify から SSR し、Cloudflare エッジで丸ごとキャッシュ。データは1日1回しか変わらないので実質静的配信になる(公開サービス+SEO+日本語単一ロケールという条件では、兄弟プロジェクトの社内ポータル型CSR構成をそのまま踏襲するのは不適切と判断)
- CDN/DNS/TLS/WAF: **Cloudflare Free プラン**(0円)。HTMLをキャッシュさせるため Cache Rule を明示設定し、バッチ完了時にAPIでパージ
- スケジューラ: **systemd timer**(OnFailure=フック・journald・RandomizedDelaySec が使えるので cron コンテナより優位) + **GitHub Actions scheduled workflow** を冗長な外部トリガとして併用(VPS側タイマー死亡を検知できる)
- バックアップ: nightly `pg_dump -Fc` → **Cloudflare R2 無料枠10GB**(0円, egress無料)。**KAGOYAの有料スナップショットは使わない**(理由は limits 参照)
- 死活監視: healthchecks.io 無料枠のデッドマンズスイッチ + Cloudflare ヘルスチェック(0円)

【この構成が「金を払って買っているもの」】
1. **本物のPostgreSQL**。打席単位ログ数百万行に対する window 関数 / FILTER 集約 / CTE / partial index / materialized view。スプリットと対戦成績を自前集計する要件は、これがあるかないかで実装量が一桁変わる。D1/Turso(SQLite系)ではアプリ層集計に落ちる
2. **常駐プロセスと時間無制限バッチ**。コールドスタートなし、CPU時間課金なし、15分制限なし
3. **行読み書き課金がない**こと。打席単位ログの再集計は行スキャンが本質なので、従量課金DBとは構造的に相性が悪い
4. **JPY建ての契約上限**。為替リスクゼロ、超過課金の発生経路そのものが存在しない
5. **v2ライブのための常駐ワーカー枠**(後述)

### limits

【KAGOYA CLOUD VPS 2GB】
- 上限770円は**インスタンス本体のみ**。日額28円×日数で課金され、月額上限に達したらそれ以上請求されない = **ハードキャップとして機能する**(超過課金・自動従量なし)
- CPU 2コア(共有) / RAM 2GB / NVMe 200GB。**スペックは上位への変更のみ可、ダウングレード不可**(プランごとにディスク割当が異なるため)
- データ転送量課金なし。追加グローバルIP 11円/日、ロードバランサ 1,100円/月、スナップショット **4.4円/日(10GBごと)** — **これらは全て月額上限770円の外側で加算される**
- 出典: https://www.kagoya.jp/cloud/vps/price/ , https://support.kagoya.jp/vps/charge/charge_kvm.html
- 超過時の挙動: **停止も遅延もしない。単に上限770円で頭打ちになる**。これが本トラックで最も価値のある性質

【スナップショットを買わない理由(重要)】
スナップショットは「日ごとに保存容量が最大となった容量を10GB単位で切り上げ」課金。OS+Docker+PostgreSQLで実使用20〜30GB → 8.8〜13.2円/日 → **264〜396円/月**。770+396=1,166円で**上限突破**。しかもデータ増加に伴い*何もしていないのに*請求が上がる。
→ 代替: OSは Docker Compose + セットアップスクリプトを git 管理して**使い捨て可能**にし、守るのはデータのみ。pg_dump圧縮ダンプをR2無料枠(10GB)へ。復旧はワンクリック30秒ではなく**30〜60分の再構築**になる。これが770円で買える範囲の現実。

【Cloudflare Free】
- 帯域無制限・DDoS防御・Universal SSL。ただし**HTMLはデフォルトでキャッシュされない** → Cache Rule を明示設定する必要あり(Freeでもルール数制限内で利用可)
- 超過概念なし(Freeは従量課金経路がない = 請求事故が起きない)

【Cloudflare R2 無料枠】
- 10GB-month / Class A 100万 / Class B 1000万 / egress無料。超過は Standard $0.015/GB-month
- 超過時の挙動: **自動課金**。ただし圧縮pg_dumpは数百MB規模で、世代管理(日次7 + 週次4 + 月次6)しても10GB以内。ライフサイクルルールで自動削除を必ず設定すること

【意図的に諦めたもの(포기 목록 — これがない答えは嘘だという指摘への回答)】
1. **マネージドDB** — 自動フェイルオーバー、PITR、ベンダー管理バックアップを放棄。PostgreSQLの運用責任を自分で持つ
2. **冗長化/HA** — 単一VPS・単一AZ・単一リージョン(京都)。ホストノード障害 = サイト停止。スタンバイなし。ロードバランサ(1,100円/月)は単体で上限超過のため不可
3. **オートスケール** — 2vCPU/2GB固定。バーストはCloudflareキャッシュで吸収する設計であり、キャッシュミスするバーストには耐えない
4. **スナップショットによる完全バックアップ** — 上記の通り予算を食うため放棄。RTOが分単位→時間単位に劣化
5. **ステージング環境** — 専用サーバ(+550円)を持たない。ステージングは開発機のDocker Compose、本番はコンテナ差し替え
6. **海外リージョン/グローバル低遅延** — 京都のみ。日本の読者向けなので許容
7. **サーバーレス/エッジの「運用ゼロ」** — OSパッチ、Docker更新、証明書、監視、深夜の障害対応を自分で背負う(実測 月1〜2時間)
8. **マネージドcron/キュー** — systemd timer + GitHub Actions で自作
9. **意味のあるSLAと24/365サポート** — KAGOYAは電話サポートありだが格安VPS帯に返金を伴うSLAはない
10. **Hetznerの20TB転送枠と欧州コスパ** — 円安で価格的に脱落
11. **読み取りレプリカ / 分析用DB分離** — 集計バッチと配信が同一インスタンスを共有する

### v2_live_headroom

【結論: 追加費用0円で載る。ただし「Redisを入れない」「SSEを使う」という2条件付き。この2条件を外すと上限を破って引っ越しになる】

■ 載せ方(追加課金なし)
- 常駐ポーラー: `worker` コンテナを1つ追加し、試合時間帯のみ30〜60秒間隔でポーリング。RSS実測見込み **約80MB**
- クライアント配信: **WebSocketではなくSSE(Server-Sent Events)**。既存Fastifyプロセス内で完結し、自動再接続があり、Cloudflare Free を透過する。同時接続20〜100で追加 **約50MB**
- プロセス間ファンアウト: **PostgreSQL LISTEN/NOTIFY**。この規模ならRedisは完全に不要(Redisを足すと+150〜250MB RAMで2GBが破綻する)
- 書き込み負荷: 1試合1時間あたり数百行。日次バッチの取込量と同オーダーで、NVMe 200GBに対して無視できる

■ メモリ収支(2GBに対して)
PostgreSQL 約700MB(shared_buffers 512MB込) + Fastify/SSE 約350MB + worker 約80MB + Caddy 約30MB + OS 約250MB = **約1.41GB**。残余約590MB + swap 4GB。**成立するが余裕は大きくない**。

■ 追加費用
**0円**(同一インスタンス内でコンテナを1つ増やすだけ。KAGOYAの月額上限770円は変わらない)

■ 引っ越しが必要になる条件(正直に言う)
以下のいずれかを踏むと2GBでは足りず、KAGOYA 4GBプラン **1,760円/月** への移行 = **上限1,000円の再交渉が必要**になる:
- Redis/BullMQ等のキュー基盤を導入する
- SSE同時接続が300を超える
- ポーリング間隔を10秒未満にする、または全12球団を並列に常時追跡する
- ライブ集計を事前計算ではなくリクエスト時計算に変える
なお移行自体は**同一事業者内のプラン変更**(上位のみ可)であり、IP・OS・Docker構成そのままで、データ移行を伴わない。**引っ越しではなくプラン変更で済む**点は本構成の重要な利点。

■ v1設計がv2を塞がないための具体的な担保(スキーマ・型変更なしで増築するための条件)
1. `pa_events`(打席単位原始ログ)を**追記専用のイベントテーブル**とし、シーズン単位の**宣言的パーティション**にする
2. 最初から `status` 列を持たせる(`'final'` デフォルト)。**v1は 'final' しか書かない。v2は 'live' を書き、確定後に 'final' へ昇格させる**。列は初日から存在するので v2 で **DDL変更が発生しない**
3. `status` は**ネイティブenumにしない**(`ALTER TYPE ADD VALUE` は非トランザクショナルで扱いづらい)。`text` + CHECK制約 か小さな参照テーブルにする
4. 自然キー `(game_id, pa_seq)` に UNIQUE を張り、取込は必ず **UPSERT(冪等)**。`revision` / `ingested_at` / `source_hash` を持つ。ライブデータは記録訂正で**必ず後から変わる**ので、冪等性がv1バッチとv2ライブの両方を安全にする唯一の設計
5. 集計層は `(scope, entity_id, split_key, season)` をキーとする materialized view / summary table に統一。v2は「更新頻度を上げる」か「ライブ差分を上に重ねる」だけで、**キー構造も型も変えない**
6. APIレスポンスに最初から `as_of`(データ時点)と `is_live`(v1は常にfalse)を含める。**v2でレスポンス型が変わらない**

### failure_modes

【この構成が「エラーを出さずに」壊れる場所 — 監視すべきはここ】

1. **バッチが静かに失敗し、昨日の数字を出し続ける(最悪かつ最も起きやすい)**
NPB側のHTML構造が変わるとスクレイパのセレクタが外れ、**0件取込のまま exit 0** で終わる。サイトは200を返し続け、見た目は完全に健康なまま、順位表だけが昨日のまま凍る。統計サイトにとってこれは「落ちる」より悪い。
→ 対策: ①全ページに `最終更新` をデータ自身から出す ②バッチが「対象日Dの試合数N件を取り込めたか」を**アサートして失敗させる** ③healthchecks.io のデッドマンズスイッチ(*来なかったこと*を検知する。来たエラーを検知するのでは不十分)

2. **PostgreSQLのOOM killが自己修復してしまう**
2GBで索引の効かない集計が走ると work_mem×並列ワーカーでOOM killer が postgres を殺し、Docker が再起動し、**サイトは復旧するので誰も気づかない**。だが夜間バッチはその回だけ何も生成していない。
→ 対策: swap 4GB、`max_parallel_workers_per_gather=1`、`restart: unless-stopped` の再起動回数を監視、バッチ完了ハートビート行を必須化

3. **Cloudflareが古い集計を配り続ける**
バッチ成功後にパージしないと、エッジTTLが切れるまでユーザーは旧データを見る。オリジンは正しいので**開発者の手元では再現しない**。
→ 対策: キャッシュキーにデータバージョンを含め、バッチの**最終ステップ**でCloudflare APIパージ。パージ失敗も失敗として扱う

4. **materialized view の部分更新による内部矛盾**
8本のMVを順に更新して5本目で失敗すると、1〜4は新・6〜8は旧。順位表とスプリットが食い違うが、どちらも「もっともらしい数字」なので気づけない。
→ 対策: 全MVを**単一トランザクション**で更新するか、新スキーマに構築して**アトミックにスワップ**

5. **有料オプションによる上限の静かな突破**
770円は*インスタンスの*上限。「念のため」スナップショットを有効化した瞬間、4.4円/日/10GB が上限の外で加算され、しかも**データ増加に比例して勝手に増える**。追加IP(11円/日=330円/月)も同様。
→ 対策: 有料オプションは原則禁止。KAGOYA管理画面の請求額を月次で目視確認

6. **バックアップはあるが復旧できない**
pg_dump は毎晩成功しているが、一度も restore を試していない状態。pg_dump の対象スキーマ漏れ、拡張機能未インストール、ロール未作成で本番復旧時に初めて失敗する。
→ 対策: **四半期ごとにローカルDockerへリストア訓練**。訓練していないバックアップは存在しないのと同じ

7. **ディスクが1年かけて静かに埋まる**
200GBは十分に見えるが、PostgreSQL WAL・Dockerログ(json-file はデフォルト無制限)・Caddyアクセスログが無回転で蓄積する。埋まった瞬間にPostgreSQLが書き込みを拒否する。
→ 対策: Docker の `log-opts max-size/max-file` 設定、logrotate、使用率70%アラート

8. **無料枠依存物の静かな縮小**
R2無料10GB、Cloudflare Free、healthchecks.io無料枠、GitHub Actions無料枠。今日無料でも規約は変わる。特に**バックアップ先が消えるのが致命的**。
→ 対策: R2に加えて月次で開発機ローカルにもダンプを引く(0円の二重化)

9. **日額課金の誤解**
インスタンスを停止しても課金が止まるとは限らない(リソースは占有され続ける)。770円上限なので破綻はしないが「止めたから無料」は誤り。

10. **単一VPSゆえの、障害の相関**
バッチ・DB・API・リバースプロキシが同一2コアを共有する。夜間の重い全再構築が走っている最中にアクセスが来ると、**バッチもAPIも両方遅い**。v1は深夜帯なので実害は小さいが、v2ライブでは同時に起きうる。
→ 対策: バッチコンテナに `cpus: 1.0` の上限を課し、APIを飢えさせない

### scaling_ceiling

【壁に当たる順序: RAM → CPU(バッチ時間) → ディスク。第一の壁は必ずRAM】

■ 同時接続 / スループット
事前計算済み集計を返すだけなので、Fastify 2コアで理論 2,000〜4,000 req/s。実際の律速はPostgreSQL接続プール(10〜20に設定)。Cloudflareキャッシュ90%ヒット前提でオリジン到達はさらに1/10。
**実用上限: 同時200〜500ユーザー。要件の同時20は容量の約2〜4%** — ここは全く問題にならない。ボトルネックではない。

■ DB容量(ディスク)
200GB NVMe。打席単位ログ1行200〜250B+索引で、10シーズン150万行 ≈ 2.5GB、投球単位600万行でも ≈ 12GB。**使用率6%以下**。
→ **ディスクは当面まったく壁にならない**(これがIndigo 40GBやD1 10GB上限に対する明確な優位点)

■ RAM(= 真の天井)
2GB。内訳は PostgreSQL 約700MB + Node 約350MB + Caddy 30MB + OS 250MB。
決定的なのは**ワーキングセットがページキャッシュ(実効 約1.2GB)を超えた瞬間**。それ以降、スプリット/対戦成績の再集計がディスクI/Oに落ちる。NVMeなので致命傷にはならない(SATAなら致命傷)が、バッチ時間が非線形に伸び始める。
**実質天井: 打席単位で約20〜30シーズン分**。投球単位まで保存するなら **約8〜12シーズン分**でRAM圧に到達する。

■ CPU(= 第二の壁)
共有2コア。全historical再構築(150万行×複数集計)で数分〜15分想定。日次差分更新は1分未満。
**壁: 全再構築が30分を超えたとき**。そこからメンテナンス窓と衝突し始め、失敗時のリトライ余地が消える。

■ 帯域
KAGOYAはデータ転送量課金なし、静的資産はCloudflareが吸収。**壁にならない**。
(対比: さくらのVPSはアウトバウンド 500GiB/アカウント無料、超過5円/GiB という従量面がある)

■ v2ライブ追加後の天井
SSE同時接続 **約300** が2GBでの実用限界。これを超えるとFastifyプロセスのRSSが膨らみPostgreSQLを圧迫する。

■ 天井を越えたときの逃げ道(コスト順)
1. Cloudflareキャッシュ強化・集計粒度の見直し(0円)
2. 古いシーズンをパーティション単位でR2へアーカイブし、ホットデータを圧縮(0円)
3. KAGOYA 3GBプラン **1,430円/月**(3core/3GB/400GB) — 上限超過
4. KAGOYA 4GBプラン **1,760円/月**(4core/4GB/600GB) — 上限超過
いずれも**同一事業者内のプラン変更(上位のみ可)で、IP・OS・データそのまま**。移設作業は発生しない。

## 4. PostgreSQL 17은 2GB에서 도는가 → 돈다. 하지만 선언된 설정에 실제 결함 2건
**전제:** 1GB 미만 데이터셋 + shared_buffers 512MB(=25%)는 완전히 평범한 구성. "PG가 안 돈다"는 반증은 성립하지 않는다. 문제는 아래.

**(a) work_mem 32MB가 실제로는 64MB — hash_mem_multiplier 기본값 2.0 누락**
PG17 공식 문서: "The memory limit for a hash table is computed by multiplying work_mem by hash_mem_multiplier" / 기본값 **2.0**. 또한 "Resource limits such as work_mem are applied individually to each worker" (https://www.postgresql.org/docs/17/runtime-config-resource.html).
→ 해시 노드 1개당 실효 **64MB**. 세이버메트릭스/스플릿 MV가 해시집계 3 + 소트 1을 병렬(leader+worker 2프로세스)로 돌리면 **(3×64 + 32) × 2 = 448MB 피크**. 원안 메모리 수지에는 이 항목이 아예 없다. maintenance_work_mem도 미지정(기본 64MB).

**(b) Docker `shm_size` 미설정 → 병렬 쿼리가 야간 배치에서만 죽는다**
Docker 컨테이너의 /dev/shm 기본값은 **64MB**. PG는 shared_buffers를 익명 mmap에 두므로 512MB는 무관하지만, `dynamic_shared_memory_type=posix`(리눅스 기본)의 **병렬 쿼리 DSM 세그먼트는 /dev/shm을 쓴다**. 원안은 `max_parallel_workers_per_gather=1`로 병렬을 **켜둔 상태**이고 compose에 shm_size 언급이 없다 → 대용량 MV 재구축 시 `could not resize shared memory segment ... No space left on device`로 실패.
출처: https://github.com/docker-library/postgres/issues/416 , https://www.sqlpassion.at/archive/2024/12/09/how-to-fix-the-postgresql-could-not-resize-shared-memory-segment-error-in-docker/ , https://www.instaclustr.com/blog/postgresql-docker-and-shared-memory/
→ 소량 데이터의 개발 환경에서는 재현되지 않고 **프로덕션 야간 배치에서만** 발현. 즉 원안이 "최악"이라 지목한 failure_mode #1(0건 취득 후 조용히 성공) / #4(MV 부분 갱신)를 **본인 설정이 직접 유발**한다. 수정: `shm_size: 256m`(2GB 박스이므로 1g는 금물, tmpfs는 RAM 소비).

## 5. 메모리 수지가 틀렸다 — OOM 리스크의 실체
**(a) 배치 컨테이너가 장부에서 누락.** 스택은 컨테이너 4개(caddy/api/postgres/batch) + v2 worker = 5개인데, v2 수지는 postgres 700 + fastify 350 + worker 80 + caddy 30 + OS 250 = 1.41GB로 **batch를 세지 않았다**. Node 스크래퍼+파서는 150~300MB.
**(b) OS 250MB 과소.** Ubuntu + dockerd(~80MB) + containerd(~40MB) + shim 5개(~50MB) → 현실 **350~400MB**.
**(c) 2GB는 2,048MB가 아니다.** KVM 게스트 MemTotal은 통상 1,950~2,000MB.

수정 장부(v2 idle): OS/Docker 400 + PG 700 + api/SSE 350 + worker 80 + caddy 40 = **약 1,570MB / 1,950MB → 잔여 약 380MB**(원안 주장 590MB보다 200MB 부족). 여기에 batch(150~300MB)와 PG 쿼리 작업 메모리(최대 448MB)가 얹히면 **1,990MB로 MemTotal을 초과** → 02:00에 정확히 OOM.
결정적으로, 원안 자신의 역전 조건 **"PG RSS + Node RSS 합계 1.5GB 초과"는 v2 아이들 상태에서 첫날 발동한다.** 설계점이 자기 임계치 위에 있다 = 수지가 내부적으로 자기모순.

**(d) V8 기본 힙 상한이 통제되지 않음 (가장 큰 단일 리스크).** Node는 컨테이너 인지형이며 기본 힙은 **컨테이너/시스템 메모리의 50%(최대 2GB)** (https://developers.redhat.com/articles/2025/10/10/nodejs-20-memory-management-containers). 원안은 `cpus: 1.0`만 걸고 **어떤 컨테이너에도 mem_limit이 없다** → api·batch·worker 3개 V8이 각각 호스트 2GB를 보고 **약 1GB 힙 상한**을 갖는다. 350MB/80MB는 *희망치이지 제약이 아니다.* V8은 1GB 근처까지 GC 압력을 느끼지 않으므로 프로세스 하나가 박스 절반을 합법적으로 먹는다. 필수 수정: 컨테이너별 `mem_limit` + `--max-old-space-size=192~256`.

**(e) 커널 파라미터 부재.** Ubuntu 기본 `vm.swappiness=60`(DB 호스트엔 과다), `vm.overcommit_memory=2` 미설정, postmaster `OOMScoreAdjust=-1000` 미설정. swap 4GB는 OOM을 막는 게 아니라 **OOM을 스래싱으로 바꾼다** — shared_buffers/해시 테이블이 스왑되면 쿼리 지연이 초 단위가 되고 헬스체크 타임아웃 → 컨테이너 재시작(원안 failure_mode #2가 말한 "자기 치유되어 아무도 모름"). 대책 목록에 이 3개가 빠져 있다.

**(f) effective_cache_size 1200MB 과대.** 자기 장부(1.41GB 사용)대로면 페이지 캐시 여유는 약 500MB → 실효값은 512+500 ≈ **1,000MB, 현실 800MB**. 1200MB는 플래너를 인덱스 스캔 쪽으로 편향시키는데, 이 워크로드(전건 집계)에는 **잘못된 방향의 편향**.

## 6. MV 갱신 잠금 — failure_mode #4의 처방이 새 문제를 만든다
PG17 문서: CONCURRENTLY 없는 REFRESH는 "could block other connections which are trying to read from the materialized view" (https://www.postgresql.org/docs/17/sql-refreshmaterializedview.html). 원안의 처방 "8본 MV를 단일 트랜잭션으로 갱신"은 첫 MV의 ACCESS EXCLUSIVE를 **커밋까지 유지** → 재구축 전 구간 동안 read model이 잠긴다. v1(02:00+CDN)에서는 무해하나 **v2에서 재구축이 경기 시간과 겹치면 SSE 읽기가 정지**한다(원안 failure_mode #10이 지적한 상관 장애의 구체적 형태). CONCURRENTLY는 무료 대체재가 아님: 모든 MV에 UNIQUE 인덱스 필수, 미populate MV 불가, 임시 복사본+diff로 **CPU·WAL이 크게 증가** — 즉 제2의 벽(CPU)을 직접 압박.

## 7. v2 라이브 — 여기서 반증 성립 (핵심)
v2 headroom 전체가 "SSE라서 Fastify 내부로 끝나고 **Cloudflare Free를 투과**하므로 추가 0円"에 의존한다. 이 전제가 문서화된 동작과 충돌한다.

**(a) Cloudflare Free/Pro는 100초 타임아웃(524)이며 조정 불가.** 원안은 하트비트 간격을 어디에도 명시하지 않았다(필요: ≤50초 keep-alive 코멘트). 출처: https://smartscope.blog/en/Infrastructure/sse-timeout-mitigation-cloudflare-alb/
**(b) Cloudflare 프록시가 `text/event-stream`을 버퍼링한다는 다수 보고** — 약 100KB가 쌓일 때까지 플러시하지 않는 사례가 반복 보고됨. 라이브 스코어는 이벤트당 수백 바이트이므로 100KB 버퍼 = 실질적으로 **라이브가 동작하지 않는다.** 게다가 오리진 직결인 개발자 손에서는 **재현되지 않는다** — 원안 스스로 "가장 나쁜 실패"라고 정의한 부류인데 failure_modes 목록에 없다. 출처: https://community.cloudflare.com/t/sse-endpoint-breaks-after-recent-update-cloudflare-buffers-text-event-stream-desp/810790 , https://community.cloudflare.com/t/cloudflare-buffering-sse-streams/506921 , https://github.com/cloudflare/cloudflared/issues/199
**(c) 표준 회피책(SSE 서브도메인 grey-cloud로 프록시 우회)이 자기 TLS 선택으로 봉쇄돼 있다.** Cloudflare Origin CA 인증서는 브라우저가 신뢰하지 않는다 — 공식 문서: "Site visitors may see untrusted certificate errors if you pause Cloudflare or disable proxying on subdomains that use Cloudflare origin CA certificates" (https://developers.cloudflare.com/ssl/origin-configuration/origin-ca/). 즉 프록시 우회를 하려면 **원안이 명시적으로 버린 ACME/Let's Encrypt를 되살려야** 한다("ACME不要"가 장점으로 적혀 있음).
**(d) 남은 문서화된 회피책은 Workers 경유** — 원안이 원칙적으로 거부한 종량·상한 없는 경로.
**(e)** SSR용 공격적 HTML Cache Rule을 건 존에서 SSE 엔드포인트를 명시 제외하지 않으면 엣지가 스트림을 캐시/합류시킨다. 미언급.

→ v2의 병목은 원안이 지목한 RAM(SSE 동시 300)이 **아니다**. 동시 20~100 규모의 RAM은 (수정 장부로도) 버틴다. 진짜 벽은 **Cloudflare Free의 배송 경로**이며, VPS RAM을 늘려도 해결되지 않는다. "추가 비용 0円으로 載る"은 입증되지 않았다.

## 필수 수정 (v1을 성립시키기 위한 최소 조건, 모두 0円)
1. compose: `shm_size: 256m`(postgres), 전 컨테이너 `mem_limit`, Node 3개에 `--max-old-space-size=192~256`
2. `hash_mem_multiplier=1.0`로 낮추거나 work_mem을 16MB로, 또는 배치 세션에서만 `SET LOCAL`
3. `vm.swappiness=1~10`, `vm.overcommit_memory=2`, postmaster `OOMScoreAdjust=-1000`
4. effective_cache_size를 800~1000MB로 하향
5. 배치 컨테이너를 메모리 장부에 계상하고, 배치 시간대 PG 최대 사용량을 실측
6. MV는 전건 UNIQUE 인덱스 + CONCURRENTLY, 또는 신스키마 빌드→아토믹 스왑(단일 트랜잭션 일괄 REFRESH는 금지)
7. v2 전에 SSE를 Cloudflare 프록시 뒤에서 **실측 검증**(≤50초 하트비트, `Cache-Control: no-cache, no-transform`, 압축 비활성, Cache Rule 제외) — 통과하지 못하면 v2는 0円이 아니다

### F. 그 밖의 조용한 사망 경로

- **NPB 스크레이핑이 무방비 SPOF.** 서비스 전체가 단일 고정 IP에서의 NPB 스크레이핑에 의존한다. IP 차단이나 이용약관 집행 한 번이면 영구 정지이고, 대체 egress 경로·폴백이 설계에 없다. 원안 failure_modes #1은 *탐지*만 다루고 *구제*를 다루지 않는다.
- **effective_cache_size 1200MB는 2GB 박스에서 과대 신고다.** shared_buffers 512MB + Node SSR 350MB + worker 80MB + Caddy 30MB + OS 250MB를 빼면 실제 페이지 캐시는 300~600MB 수준인데 플래너에게 1200MB가 있다고 알린다. 결과적으로 캐시를 빗나가는 인덱스 스캔을 과선호해 **배치 시간이 비선형으로, 에러 없이 느려진다.** 정확히 "조용한 열화"다.
- **work_mem 32MB가 RAM 예산에 아예 안 잡혀 있다.** work_mem은 커넥션당이 아니라 **정렬/해시 노드당**이다. 윈도우 함수·CTE·MV 리프레시처럼 노드가 여럿인 분석 쿼리 × 풀 10~20이면 shared_buffers 밖에서 수백 MB가 추가로 뜬다. 원안의 "PostgreSQL 약 700MB"에는 이 몫도, maintenance_work_mem(REFRESH MV/CREATE INDEX 사용, autovacuum 워커 3개도 각각 사용)도 없다. v2에서 여유 590MB는 실제로는 더 얇다.
- **사업자의 제품군 정리 습관.** 2026-07-31 구 공용서버 B플랜·전용서버 3G 701·061s Hexa·121 Hexa x2 종료, 2026-08-31 KAGOYA FLEX ν 스냅샷 기능 종료(VMware→Nutanix 이행). CLOUD VPS는 현행 주력이라 즉시 위험은 아니지만, 규약 제13조2항의 3개월 통지 종료권과 합치면 "동일 사업자 내 플랜 변경으로 끝난다"는 원안의 이주 안전판은 무조건적이지 않다.

### 판정 근거 요약

비용 산식은 검증을 통과했고 아키텍처도 워크로드에 적합하다. 그럼에도 **refuted=true**로 판정하는 이유는 두 가지다.

1. 원안이 스스로 "최악이자 가장 일어나기 쉽다"고 규정한 실패모드에 대한 방어 3중 중 **하나는 무료로 존재하지 않고(A-1), 둘은 각각 60일·13개월 후 무활동으로 자동 소멸한다(A-2, A-3).** 감시가 없는 통계 사이트는 "죽은 것보다 나쁘다"는 원안 자신의 기준을 1년 내에 충족하게 된다.
2. "초과 과금 경로가 원리적으로 존재하지 않는다"는 채택의 핵심 근거가 **550円 払込書 수수료라는 실측 반례로 무너진다(B).** 게다가 결제 실패는 사전 통지 없는 정지와 통지 없는 데이터 삭제로 이어지며(C), 백업처가 같은 카드에 묶여 있어 **상관 실패**한다(D).

수리 가능한 결함이다(무료 외부 모니터로 A-1 대체, GH Actions keepalive, healthchecks.io 로그인 캘린더 알림, 카드 만료 관리, 분기 복구 훈련, 로컬 3중 백업). 다만 **원안에 적힌 그대로 운용하면 1년 내에 감시 없이 낡은 데이터를 배포하는 상태로 조용히 수렴한다.**
